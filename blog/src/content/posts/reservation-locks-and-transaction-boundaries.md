오늘은 예약과 취소를 구현하면서 낙관적·비관적 락에 대해서 한번 공부하는 시간을 가져볼 수 있었다.
기존에도 알고 있었던 내용이지만, 실무에서 락을 직접 써볼 기회가 없었기에 아스트라가 마련해준 문제에서 실제로 사용해보며 좀 더 딥다이브해보고자 했다.

## 예약과 취소의 요구사항

일단 요구사항은 다음과 같았다.

- 예약에 성공하면 예약 한 건을 생성하고 잔여 좌석을 1 줄인다. 잔여 좌석은 음수가 될 수 없다.
- 같은 이벤트에 같은 사용자의 예약 요청이 겹쳐도 예약은 한 건만 생성한다. 재요청에는 기존 예약을 반환하고, 이미 매진됐더라도 추가로 좌석을 차감하지 않는다.
- 취소에 성공하면 해당 예약을 삭제하고 잔여 좌석을 1 늘린다. 이미 취소했거나 없는 예약, 다른 이벤트에 속한 예약이면 변경 없이 `NOT_FOUND`를 반환한다.
- 같은 예약의 취소 요청이 겹치면 좌석은 한 번만 반환한다. 같은 이벤트의 서로 다른 예약 두 건을 동시에 취소하면 잔여 좌석은 2 늘어나야 한다.
- DB 저장에 실패하면 예약 생성·삭제와 좌석 변경을 모두 원복하고 예외를 전달한다. 이 조건들은 서로 다른 서비스 인스턴스가 같은 DB에 접근할 때도 지켜야 한다.

## 낙관적 락에서 비관적 락으로

그래서 최초에 구현을 시도할 때는 `@Version`을 통해 낙관적 락을 적용하고 재시도를 처리하려고 했다. 그런데 이번 요구사항에 맞게 구현하려면 충돌 이후의 재시도와 응답 처리까지 필요해서, 일단 비관적 락으로 구현을 시도해보고자 했다.

물론 비관적 락은 같은 데이터에 대한 요청을 직렬화하면서 대기 시간이 길어질 수 있다는 점을 알고 있었지만, 오늘은 실습이니까 좀 더 공부하고자 했다.

아래는 버전 3을 읽은 두 요청이 같은 이벤트를 수정할 때, 버전을 검사하는 방식을 보여주는 간단한 예제다.

```java
// Event 엔티티의 필드 일부
@Version
private long version;
```

```sql
UPDATE event
SET remaining = 1, version = 4
WHERE event_id = 1 AND version = 3;
```

위 SQL은 버전 검사를 보여주는 예시다. A가 먼저 버전을 4로 바꾸면, B의 `version = 3` 조건에 맞는 행은 0개가 되어 충돌로 처리된다.

일단 비관적 락을 시도할 때 내가 기억한 건 `@Lock` 어노테이션을 통해 락을 거는 방식이었다. `LockModeType`에서 당연히 `PESSIMISTIC_READ`라고 생각하고 걸었는데, 웬걸, 동시 재요청 요구사항이 충족되지 않았다.

당시에는 `PESSIMISTIC_READ`의 공유 락 동작과 함께, 락을 얻기 전에 기존 예약을 먼저 확인하던 순서도 살펴봐야 했다. 내가 원하는 건 수정 요청들이 같은 이벤트를 기준으로 순서대로 판단하고 처리하는 흐름이었다.

이벤트 조회 메서드에 `PESSIMISTIC_READ`를 지정하면 아래처럼 작성할 수 있다.

```java
@Lock(LockModeType.PESSIMISTIC_READ)
@Query("select e from Event e where e.id = ?1")
Optional<Event> findByIdWithLock(Long id);
```

## 공유 락은 어떻게 동작할까

그럼 공유 락과 배타 락, 읽기 락과 쓰기 락은 어떻게 다를까?
일단 읽기 락은 읽은 데이터를 보호하기 위한 락이고, 공유 락이라는 이름에 알맞게 여러 트랜잭션이 같은 레코드에 공유 락을 함께 보유할 수 있다.

근데 무슨 락이야? 라고 할 수 있겠지만, 공유 락을 보유하는 동안 다른 트랜잭션의 배타 락 획득을 막는다. 따라서 다른 트랜잭션이 해당 레코드를 수정하려면 공유 락이 해제될 때까지 기다렸다가 배타 락을 얻어야 한다.

공유 락을 가진 트랜잭션이 직접 수정할 때는 배타 락으로의 전환을 시도한다. 두 트랜잭션이 공유 락을 얻은 뒤 동시에 전환을 시도하면 교착 상태가 생길 수 있다.

그래서 이 트랜잭션이 특정 컬럼의 A라는 값을 읽고 공유 락을 유지하면, 트랜잭션이 끝날 때까지 다른 트랜잭션의 변경을 막아 그 값을 보호할 수 있다.
다만 아까 말한 것처럼 공유 락은 여러 트랜잭션이 함께 얻을 수 있으므로, 같은 값을 읽고 수정 여부를 판단하는 과정까지 동시에 진행할 수 있다.

아래는 A와 B가 같은 이벤트에 공유 락을 얻고, 각각 수정을 시도하는 과정을 순서대로 적은 예제다.

```text
A: 공유 락 획득 → remaining = 1 확인
B: 공유 락 획득 → remaining = 1 확인
A: 수정하려고 배타 락 요청 → B의 공유 락 때문에 대기
B: 수정하려고 배타 락 요청 → A의 공유 락 때문에 대기
   → 교착 상태 감지 시 한 트랜잭션이 롤백될 수 있음
```

## 배타 락으로 요청을 순서대로 처리하기

그러면 쓰기 락은 뭘까? 쓰기 락은 배타 락이라는 이름 그대로, 같은 레코드에 대한 다른 트랜잭션의 공유·배타 락 요청을 기다리게 한다.
따라서 트랜잭션 안에서 `SELECT ... FOR UPDATE`로 레코드나 범위를 잠갔다면, 다른 트랜잭션이 같은 레코드를 수정하려고 배타 락을 얻는 과정에서 줄을 서게 된다. MVCC로 스냅샷을 읽는 일반 조회는 진행할 수 있다.

이때 락을 얻은 뒤 필요한 값을 확인하고 수정하면, 같은 잠금 순서를 따르는 요청들이 차례로 처리된다. 예약 변경과 좌석 변경을 함께 커밋하거나 롤백하는 원자성은 트랜잭션으로 보장한다.

공유 락은 S(Shared), 배타 락은 X(Exclusive)로도 표기한다. 아래는 MySQL InnoDB에서 같은 레코드에 대해 서로 다른 트랜잭션이 S 락과 X 락을 요청할 때의 호환 관계를 정리한 표다.

| 먼저 획득한 락 | 다른 트랜잭션의 S 락 요청 | 다른 트랜잭션의 X 락 요청 |
| --- | --- | --- |
| S 락 — 공유 락 | 함께 획득 가능 | 기존 락 해제까지 대기 |
| X 락 — 배타 락 | 기존 락 해제까지 대기 | 기존 락 해제까지 대기 |


이번에는 A와 B가 각각 새 트랜잭션에서 이벤트의 쓰기 락을 먼저 얻고, 같은 예약을 취소하는 과정을 살펴보자. 요청이 처리되는 순서는 아래 표와 같다.

| 순서 | 요청 A의 트랜잭션 | 요청 B의 트랜잭션 |
| --- | --- | --- |
| 1 | 이벤트 쓰기 락 획득 | |
| 2 | | 같은 이벤트 쓰기 락 요청 → 대기 |
| 3 | 예약 확인 → 삭제 → 좌석 반환 | 대기 |
| 4 | 커밋, 락 해제 | 락 획득 |
| 5 | | 예약 조회 → 이미 삭제되어 `NOT_FOUND` |
| 6 | | 커밋, 락 해제 |

## MVCC와 공유 락의 차이

그럼 여기까지는 좋은데, 공유 락의 설명을 보면서 뭔가 하나 이상한 게 느껴지지 않는가?
보통 MySQL InnoDB에서는 MVCC를 활용해서 REPEATABLE READ에서 일반 `SELECT`가 같은 스냅샷을 읽도록 한다는데, 미묘하게 공유 락의 설명과 닮아 있다.

즉, 한 트랜잭션에서 같은 값을 반복해서 읽을 수 있다는 점이다. 이 격리 수준에서는 첫 일반 `SELECT`에서 만든 스냅샷을 이후 일반 `SELECT`에서도 사용해, 다른 트랜잭션이 나중에 커밋한 변경을 가려준다. 자기 트랜잭션에서 변경한 값은 읽을 수 있다.

다만 락과 다른 점은, 보이는 값은 스냅샷의 값이지만 실제 데이터는 다른 트랜잭션에 의해 변경될 수 있다는 사실이다.

공유 락은 이와 다르게, 다른 트랜잭션이 해당 레코드를 수정하는 데 필요한 배타 락을 얻지 못하게 한다. 그래서 공유 락을 유지하는 동안에는 다른 트랜잭션에 의해 이 값이 실제로 바뀌는 것을 막을 수 있다.

아래는 MySQL InnoDB의 REPEATABLE READ에서 일반 조회와 공유 락을 사용한 조회를 비교한 예제다. 두 경우 모두 잔여 좌석이 1인 상태에서 시작하며, A는 조회만 수행한다.

| 순서 | A가 일반 SELECT로 읽은 경우 | A가 SELECT … FOR SHARE로 읽은 경우 |
| --- | --- | --- |
| 1 | A가 1을 읽고 스냅샷 유지 | A가 1을 읽고 공유 락 유지 |
| 2 | B가 0으로 UPDATE하고 커밋 | B의 UPDATE가 A의 공유 락 때문에 대기 |
| 3 | A가 다시 일반 조회 → 스냅샷의 1 | A가 다시 조회 → 보호 중인 1 |
| 4 | A가 끝나기 전에도 DB의 커밋된 값은 0 | A가 끝나 락을 해제하면 B의 변경 진행 |

## 마무리

예약과 취소를 구현하면서 락의 이름뿐 아니라 어떤 요청이 함께 진행할 수 있는지, 어떤 요청이 기다려야 하는지를 살펴봤다. 특히 MVCC로 같은 값을 읽는 것과 공유 락으로 다른 트랜잭션의 변경을 막는 차이를 구분할 수 있었다. 다음에는 실제로 어떤 범위에 락이 걸리는지도 확인해보려고합니다.
