요즘 예약-취소로 여러가지를 테스트해보고 있다. 저번에는 비관적 락에 대해서 테스트해봤다면 이번에는 낙관적 락과 비관적 락을 둘다 비교해보고싶었다.

일반적으로 말하는 '비관적 락은 충돌 상황에 강하고 낙관적 락은 일반적인 상황에 강하다' 라는 얘기를 실제로 한번 확인해보고싶었기 때문이다.

## 경합 상황에서의 비관적 락

최근 공부하면서 '일반적으로는 낙관적 락을 많이 씁니다. 비관적 락은 잘 안써요.' 라는 얘기를 들어서 사실 조금 의문이 들었다.

비관적 락에서는 hot row 에 요청이 몰릴 때 대기 시간이 길어질 수 있다는 점이 신경쓰였다.

만약에 hot row 가 생긴다면 대기도 어마어마하게 길어질 수 있고, 이는 어플리케이션 전체 장애로 이어질 수도 있다. 꽤나 중요한 얘기였고, 성능을 측정하면 얼마나 차이가 날지도 궁금했다.

## 예약 생성 부하 테스트 해보기

그래서 구현해둔 예약 기능에 k6로 부하를 걸어봤는데 결과는 의외였다.

| 지표 | 비관적 1 | 낙관적 1 | 낙관적 2 | 비관적 2 |
| --- | ---: | ---: | ---: | ---: |
| 예약 성공 | 24,260건 | 3,643건 | 3,831건 | 13,653건 |
| 예약 성공/초 | 403.7건 | 60.5건 | 63.6건 | 226.9건 |
| 충돌률 | 0% | 96.5% | 96.4% | 0% |
| 성공한 예약 HTTP p95 | 2,190ms | 576ms | 751ms | 4,078ms |

![예약 성공 처리량과 성공한 예약의 HTTP p95 비교](/images/posts/locking-comparison/reservations.svg)

오 생각보다 낙관적 락은 성공한 요청의 응답 속도에서는 장점을 보였다. 하지만 전체 요청의 약 96%가 충돌 응답으로 끝나고 있었다. 비관적 락은 같은 Event의 수정 요청이 순서대로 처리되면서 이번 테스트의 예약 요청을 모두 성공시켰다.

내 생각보다는 낙관적 락의 성능이 아쉬웠다.

## DB와 어플리케이션 부하 살펴보기

다만 k6 대시보드만으로는 요청이 처리되는 내부 과정까지 알기 어려웠다. 그래서 옵저버빌리티를 좀더 확장해서 DB와 어플리케이션까지 확인해봤다.

| 지표 | 비관적 1 | 낙관적 1 | 낙관적 2 | 비관적 2 |
| --- | ---: | ---: | ---: | ---: |
| 앱 JVM 누적 CPU 시간 | 32.1초 | 80.4초 | 76.4초 | 32.1초 |
| DB 롤백 | 0건 | 100,545건 | 103,807건 | 0건 |
| 행 잠금 대기 횟수 | 24,238회 | 103,960회 | 107,339회 | 13,637회 |
| 행 잠금 누적 대기시간 | 1,734.6초 | 1,244.0초 | 1,260.0초 | 1,736.1초 |

![예약 쓰기 실험에서 측정한 앱 JVM 누적 CPU 시간](/images/posts/locking-comparison/app-cpu.svg)

확실히 이번처럼 충돌이 많은 테스트에서는 낙관적 락이 앱 CPU 시간을 더 많이 사용하고 있었다.

DB 롤백은 낙관적 1·2에서 각각 약 10만 건씩 발생했다. 행 잠금 대기도 낙관적에서 더 자주 발생했지만, 누적 대기시간은 비관적에서 더 길었다. 비관적은 기다린 뒤 예약을 성공시키는 흐름이었고, 낙관적은 많은 요청이 충돌과 롤백으로 끝나고 있었다.

행 잠금 누적 대기시간은 여러 요청이 기다린 시간을 합친 값이다. 동시에 기다리는 요청이 많으면 60초짜리 테스트에서도 수천 초로 집계될 수 있다.

![예약 실험의 DB 롤백 횟수와 행 잠금 누적 대기시간](/images/posts/locking-comparison/db-locks.svg)

아무래도 더 많은 요청을 처리하면서 예외와 응답을 만들고, DB 에서는 쓰기 시도와 롤백 같은 작업도 수행하기 때문일 것 같다. 어느 작업이 CPU를 얼마나 사용했는지는 추가로 살펴볼 부분이다. 예상과 다른 결과여서 조금 놀랐다.

이번 테스트에서는 비관적 락이 더 많은 예약을 성공시켰다. 낙관적 락은 많은 요청이 충돌로 끝나면서 성공량이 적었다.

## 동시 요청 수 줄여보기

하지만 여기서 한가지 간과한 것이 있었다. 1000VU 가 같은 재고를 두고 계속 충돌하는 상황이 얼마나 자주 있을까? 물론 트래픽이 정말 많다면 이런 상황이 자주 생길 수도 있겠지만, 평소에도 계속 이럴지는 생각해볼 필요가 있었다.

생각해보자 인터넷에서 옷을 살때 모든 사람이 특정 옷을 구매하기 위해 몰리겠는가? 아니면 어떤 이벤트가 발생했을때 몰리겠는가?

그렇다면 충돌이 적을 때는 낙관적 락이 더 잘 맞을 수도 있겠다는 생각이 들었다. 그래서 이번에는 동시 요청 수를 줄여서 테스트해봤다.

| 방식 | 동시 진입 추가 제한 | 예약 성공/초 | 충돌률 | MySQL 평균 CPU |
| --- | --- | ---: | ---: | ---: |
| 비관적 | 없음 | 385.1건 | 0% | 45.0% |
| 낙관적 | 없음 | 44.4건 | 96.5% | 230.4% |
| 비관적 | 8개 | 394.4건 | 0% | 36.6% |
| 낙관적 | 8개 | 171.7건 | 86.8% | 124.1% |
| 비관적 | 1개 | 392.4건 | 0% | 26.0% |
| 낙관적 | 1개 | 348.0건 | 0% | 35.3% |

![동시 진입 제한에 따른 예약 성공 처리량과 MySQL 평균 CPU](/images/posts/locking-comparison/admission.svg)

낙관적 락도 동시 진입을 줄이자 충돌과 CPU 사용량이 줄고 성공량이 늘었다. 동시 1개에서는 같은 Event의 수정이 하나씩 진행되면서 충돌이 0%가 됐다. 그래서 충돌이 적을 때 낙관적 락을 많이 사용한다는 얘기도 조금 더 이해됐다.

같은 실험에서 MySQL 컨테이너의 자원 사용량도 함께 확인해봤다.

| 방식·동시 진입 제한 | MySQL 평균 / 최대 CPU | 최대 메모리 | 읽기 / 쓰기 증가량 |
| --- | ---: | ---: | ---: |
| 비관적 제한 없음 | 45.0% / 73.4% | 586.4MiB | 0.0 / 4026.4MiB |
| 낙관적 제한 없음 | 230.4% / 266.8% | 586.6MiB | 1.0 / 2122.9MiB |
| 비관적 8개 | 36.6% / 48.5% | 475.7MiB | 1.2 / 4054.1MiB |
| 낙관적 8개 | 124.1% / 144.1% | 511.2MiB | 1.0 / 3481.9MiB |
| 비관적 1개 | 26.0% / 39.0% | 516.3MiB | 1.0 / 4074.1MiB |
| 낙관적 1개 | 35.3% / 52.9% | 532.6MiB | 0.0 / 3704.1MiB |

![동시 진입 제한별 MySQL 평균 CPU와 최대 메모리](/images/posts/locking-comparison/db-resources.svg)

추가 제한이 없을 때 MySQL 평균 CPU는 비관적 45.0%, 낙관적 230.4%였다. 낙관적은 동시 진입을 8개로 줄이자 124.1%, 1개에서는 35.3%까지 내려갔다. 충돌이 줄어들면서 DB CPU도 함께 줄어드는 모습을 볼 수 있었다.

최대 메모리는 약 476~587MiB 범위였다. 추가 제한이 없을 때는 두 방식이 거의 비슷했고, 제한을 걸었을 때의 차이는 조건마다 달랐다.

쓰기 증가량은 모든 조건에서 비관적이 더 컸다. 비관적에서 예약 성공량도 더 많았으니, DB CPU와 함께 실제로 저장한 예약 수와 쓰기량도 같이 보는 게 좋겠다는 생각이 들었다.

CPU 100%는 대략 코어 1개 사용량이다. 메모리는 Docker stats 기준이며, 읽기·쓰기는 측정 구간의 Block I/O 누적 증가량이다.


## 테스트 결과 정리

이번처럼 같은 재고에 요청이 몰리는 상황에서는 비관적 락이 더 많은 예약을 성공시켰다. 낙관적 락은 성공한 요청의 응답시간은 짧았지만, 충돌과 롤백이 많아 앱과 DB의 CPU 사용량도 컸다.

동시 요청 수를 줄이자 낙관적 락의 충돌과 CPU 사용량도 줄었다. 결국 같은 재고에 요청이 얼마나 겹치는지가 락을 선택할 때 중요한 기준이 된다.

성공한 요청의 p95 응답시간은 비관적 락이 더 길었다. 낙관적 락은 이번 테스트에서 더 빠르게 응답했다. 예약 성공량과 함께 사용자가 응답을 기다리는 시간 역시 락을 선택하는 중요한 기준이 될 것 같다.

## 실무에서 상상해보기

실제 서비스에서는 대기열로 진입 인원을 조절하거나, 여러 대의 앱이 같은 재고를 수정할 수 있다. 그래서 앱 전체의 동시 요청을 어떻게 조절할지, 분산 락이 필요한 상황인지도 함께 생각해볼 필요가 있다.

동시에 들어오는 요청 수와 허용 가능한 대기시간, 재시도 횟수와 간격 등을 고려해서 처리 방식을 정해야 할 것 같다.

다음에는 충돌한 요청을 재시도했을 때 예약 성공까지 얼마나 걸리는지도 한번 확인해보면 좋을 듯하다.

## 측정 조건

- 예약 생성: 이벤트 1개, 재고 100만 개, 요청마다 다른 사용자
- 부하: k6 최대 1,000 VU, 60초, 방식별 2회 비교
- 동시 진입: 추가 제한 없음·8개·1개, 조건별 1회 비교
- 환경: Spring·JPA·MySQL Testcontainers, 단일 머신에서 앱 CPU·DB 잠금 대기·CPU·메모리·I/O 측정
