# InnoDB 인덱스·B+Tree·페이지 I/O

## 현재의 한 문장 설명

InnoDB의 B+Tree 인덱스는 큰 fan-out으로 Root에서 Leaf까지의 페이지 방문 수를 줄이고 정렬·연결된 Leaf로 범위를 이어 읽으며, 세컨더리 인덱스가 쿼리를 커버하지 못하면 Leaf의 PK로 클러스터드 인덱스를 다시 탐색한다.

## 이해 지도

### 알고 있는 것

- InnoDB 클러스터드 인덱스의 Leaf에는 PK 순서의 실제 행 레코드가 저장된다.
- 세컨더리 인덱스의 Leaf에는 세컨더리 키와 PK 값이 저장된다.
- 필요한 컬럼이 세컨더리 인덱스에 모두 있으면 커버링 조회가 되어 클러스터드 인덱스 재탐색을 피할 수 있다.
- B+Tree 내부 페이지에는 여러 경계 키와 자식 페이지 포인터가 있으며, fan-out이 크면 트리 높이가 낮아진다.
- 범위 조회는 첫 Leaf까지 내려간 뒤 정렬된 Leaf와 sibling Leaf를 이어 읽는다.
- HDD의 랜덤 I/O 벌점이 SSD보다 크지만, SSD에서도 개별 랜덤 I/O를 줄이고 연속 접근·read-ahead·캐시 지역성을 활용하는 것이 유리하다.
- 세컨더리 범위 스캔이 논리적으로 연속적이어도, 비커버링 조회의 PK별 클러스터드 재탐색은 랜덤 페이지 접근으로 흩어질 수 있다.

### 헷갈리는 것

- 논리적으로 이웃한 sibling Leaf와 저장 장치에서 물리적으로 연속된 블록의 차이
- 버퍼 풀에 Root·Branch·Leaf가 각각 얼마나 남는지에 따라 실제 저장 장치 I/O가 어떻게 달라지는지
- 많은 행을 반환할 때 옵티마이저가 인덱스보다 테이블 풀 스캔을 선택하는 비용 판단

### 오늘 다뤘지만 아직 약한 것

- fan-out이 커지면 트리 높이가 낮아지고, InnoDB의 B+Tree 노드가 페이지 단위로 구현되므로 노드 접근 감소가 페이지 접근 및 잠재적인 저장장치 I/O 감소로 이어진다고 설명할 수 있다.
- 세컨더리 인덱스는 `세컨더리 컬럼들 → 동일한 값 안에서는 PK` 순서로 정렬되며, PK 전체가 전역적으로 정렬된 것은 아니라는 세부사항
- 긴 PK와 무작위 PK가 각각 fan-out·인덱스 크기와 삽입 지역성·페이지 분할에 미치는 영향을 분리해서 설명하기
- 비커버링 세컨더리 범위 스캔에서 순차 접근과 랜덤 접근이 한 실행 안에 함께 존재한다는 설명

## 의사결정 모델

- 해결하려는 문제: 자주 실행되는 동등·범위·정렬 쿼리가 읽는 행과 페이지 수를 줄인다.
- 먼저 확인할 조건: 실제 조건·정렬·반환 컬럼, 선택도와 데이터 분포, 반환 행 수, 쓰기 빈도, 실행 계획과 버퍼 풀 적중률.
- 기본 선택: 쿼리의 선두 동등 조건과 범위·정렬을 고려해 최소한의 복합 B+Tree 인덱스를 만들고, 가치가 큰 읽기 경로에서만 커버링을 검토한다.
- 선택하지 않을 조건: 결과가 테이블의 큰 비율이거나 쓰기 비용·저장 공간이 더 크고 기존 인덱스와 중복된다면 추가 인덱스를 피한다.
- 주요 trade-off: 읽는 페이지와 double lookup을 줄이는 대신 인덱스 저장 공간, 버퍼 풀 점유, INSERT·UPDATE·DELETE 비용이 증가한다.

## 내가 처음에 잘못 알았던 것

- fan-out이 커지면 노드 접근도 많아진다고 생각했지만, fan-out이 크다는 것은 내부 페이지 하나가 더 많은 자식 범위를 구분하므로 일반적으로 트리 높이와 방문 페이지 수가 줄어든다는 뜻이다.
- 무작위 UUID 삽입 때 전체 인덱스가 다시 정렬된다고 생각했지만, 실제로는 알맞은 Leaf의 정렬 위치에 삽입하며 공간이 부족할 때 페이지가 분할된다.
- 연결된 Leaf는 저장 장치에서도 반드시 물리적으로 연속한다고 생각했지만, sibling 링크는 논리적 키 순서이고 물리적 연속성은 배치와 조각화에 따라 달라진다.

## 2026-09-18 추가 — 복합 인덱스의 순서와 조회 비용

출처: 사용자가 GPT와 함께 정리한 10개 항목을 이 대화에 제공하고 복습 편입을 요청했다. 공동 정리 자료이며 자료 없이 독립 회상에 성공한 기록은 아니다. 아래는 그 내용과 예시를 주제별로 옮긴 것이다. 기존 복습 수준·횟수는 올리지 않는다.

### 1. 복합 인덱스는 튜플 전체가 정렬된다

`INDEX (A, B, C)`는 열마다 별도 인덱스3개를 만드는 것이 아니다. 하나의 키를 A 순서로, A가 같으면 B 순서로, A와 B가 같으면 C 순서로 정렬한다. 아래는 모두 기본 오름차순인 경우다.

```java
Comparator.comparing(Row::getA)
    .thenComparing(Row::getB)
    .thenComparing(Row::getC);
```

### 2. Leftmost Prefix가 중요한 이유

`INDEX (A, B, C)`에서 `WHERE A = ? AND B = ?`는 왼쪽부터 값이 정해져 검색 범위를 좁히기 좋다. `WHERE B = ?`만 있으면 B가 같은 값들이 여러 A 구간에 흩어져 있어 하나의 좁은 연속 범위로 찾기 어렵다. 이를 모든 상황에서 ‘인덱스를 전혀 사용할 수 없다’는 뜻으로 외우지는 않는다.

### 3. B+Tree의 Range Scan

```text
[leaf] <-> [leaf] <-> [leaf]
```

트리를 따라 범위의 시작점을 찾은 뒤, 정렬된 엔트리와 이웃 Leaf를 이어 읽는다.

```sql
-- INDEX (user_id, created_at)
WHERE user_id = 10 AND created_at >= '2026-09-01'
```

개념적으로 `(10, 09-01)`부터 읽고 user_id=10 구간이 끝나면 멈춘다. Leaf의 논리적 연결과 디스크 블록의 물리적 연속성은 구분한다.

### 4. Cardinality가 높은 열을 무조건 앞에 두지는 않는다

```sql
WHERE status = 'PAID' AND created_at >= ?
```

`(status, created_at)`이면 PAID 구간 안에서 날짜 범위를 읽을 수 있다. `(created_at, status)`이면 날짜 범위 안에 여러 상태가 섞일 수 있다. status의 서로 다른 값이 적더라도 선두에 놓는 것이 유리할 수 있다.

실제 쿼리 패턴, 동등 조건, 범위 조건, ORDER BY, 선택도·카디널리티를 함께 본다. 이 목록 자체를 모든 쿼리에 적용할 고정 우선순위로 외우지는 않는다.

### 5. Equality 조건 뒤에 Range 조건을 두는 패턴

```sql
WHERE tenant_id = ? AND status = ? AND created_at >= ?
-- 후보: INDEX (tenant_id, status, created_at)
```

tenant와 status가 같은 구간을 고른 뒤 날짜 범위를 읽는다. 동등 조건으로 범위를 좁힌 다음 범위 스캔을 시작하는 패턴이다.

### 6. Range 조건 뒤의 열은 범위를 좁히기 어렵다

```sql
-- INDEX (A, B, C)
WHERE A = 1 AND B > 10 AND C = 5
```

```text
B=11 → C=1,5,9
B=12 → C=2,5
B=13 → C=5,8
```

`C=5`는 여러 B 구간에 흩어져 있다. `(A=1, B>10)`에서 읽는 범위를 C 조건만으로 하나의 더 좁은 연속 구간으로 만들기 어렵다. 그렇다고 C 조건 자체가 쓸모없는 것은 아니다.

### 7. Index Condition Pushdown (ICP)

```sql
-- INDEX (A, B, C)
WHERE A = 1 AND C = 10
```

비커버링 보조 인덱스 조회에서 ICP가 적용된다면, A=1 구간의 인덱스를 읽으며 C=10을 먼저 검사하고 통과한 항목만 PK로 본문 행을 찾는다.

```text
A=1 구간 읽기 → 인덱스에서 C 검사 → 통과한 항목의 본문 행 조회
```

‘인덱스 탐색 범위를 좁히는 조건’과 ‘읽은 인덱스 항목을 거르는 조건’을 구분한다. 모든 인덱스 필터링을 무조건 ICP라고 부르지 않으며 실제 적용 여부는 실행계획에서 확인한다.

### 8. InnoDB 보조 인덱스에는 PK가 포함된다

```sql
PRIMARY KEY (id)
INDEX (user_id, status)
```

보조 인덱스 엔트리는 개념적으로 `(user_id, status, id)`를 가진다. 필요한 열이 여기에 없으면 보조 인덱스에서 얻은 PK로 클러스터드 인덱스를 탐색해 본문 행을 읽는다. 필요한 열이 모두 있으면 커버링 조회가 가능하다.

오늘 대화에서 구분한 예시:

| 선언한 인덱스 | PK까지 포함한 키 순서 | 시각·ID 정렬과 금액 조회 |
| --- | --- | --- |
| `(created_at)` | `(created_at, id)` | 시각·ID는 커버링 가능. 금액은 본문 행 조회 필요 |
| `(created_at, amount)` | `(created_at, amount, id)` | 세 열이 있어도 같은 시각 안에서 금액이 ID보다 먼저 정렬됨 |
| `(created_at, id, amount)` | 그대로 | 시각·ID 정렬을 유지하면서 금액도 보관 |

가정은 id 단일 PK, 기본 오름차순 인덱스다. 포함된 열과 열의 정렬 순서는 별개의 문제다.

### 9. filesort는 반드시 디스크 정렬이라는 뜻이 아니다

`Using filesort`는 ORDER BY를 처리하는 별도 정렬 작업이 있다는 뜻이다. 메모리에서 끝날 수도 있다.

```sql
-- INDEX (user_id), created_at은 PK나 인덱스 열이 아니라고 가정
WHERE user_id = 10 ORDER BY created_at
```

user_id로 대상을 찾더라도 created_at 순서가 보장되지 않으면 별도로 정렬해야 한다.

### 10. 복합 인덱스와 ORDER BY

`INDEX (A, B, C)`에서:

| 쿼리 | 인덱스 순서 활용 |
| --- | --- |
| `WHERE A=1 ORDER BY B,C` | A가 고정되므로 B,C 순서를 활용 가능 |
| `WHERE A=1 ORDER BY C` | B 구간마다 C가 다시 정렬되므로 보통 그대로 활용 불가 |
| `WHERE A=1 AND B=2 ORDER BY C` | A,B가 고정되므로 C 순서를 활용 가능 |

예를 들어 B=1의 C가1,3이고 B=2의 C가2,4라면 전체 C는1,3,2,4다. 앞선 열들이 하나의 값으로 고정돼야 뒤쪽 정렬을 그대로 활용하기 쉬운 이유다.

### 정리한 핵심

실제 쿼리가 B+Tree에서 얼마나 좁고 연속된 범위를 읽게 되는지를 기준으로 열 순서를 생각한다. 검색 범위뿐 아니라 정렬, 커버링 여부, 본문 행 접근, 인덱스 유지 비용도 함께 고려한다.

### 다음 통합 복습에서 순환할 질문

아래5개는 질문 후보이며 하루에 모두 추가 출제하지 않는다. 기존 통합 복습3~5문항·15분 안에서 일부를 선택하고, 오늘은 다시 묻지 않는다.

1. `(A,B,C)`에서 A=1 구간에 `(B=1,C=1)`, `(B=1,C=3)`, `(B=2,C=2)`, `(B=2,C=4)`가 있다. `ORDER BY C`를 위해 별도 정렬이 필요한 이유와 B=1까지 고정했을 때의 차이를 설명해 보자.
2. 주문에서 `status='PAID' AND created_at>=특정시각`을 찾는다. 상태 종류가3개뿐이라는 이유만으로 status를 인덱스 첫 열에서 제외해야 할까? 두 열의 순서를 바꿨을 때 읽는 구간을 비교해 보자.
3. `(A,B,C)`에서 A=1, B>10, C=5를 찾는다. C가 읽는 범위를 좁히는 데 한계가 있어도, 본문 행 조회 횟수는 어떻게 줄일 수 있을까? 필요한 열 중 일부는 인덱스에 없다고 가정한다.
4. id가 단일 PK인 InnoDB에서 시각·ID·금액을 반환하고 시각·ID 순으로 정렬한다. `(created_at, amount)`와 `(created_at, id, amount)`는 필요한 열을 모두 갖는데도 왜 정렬 처리에 차이가 날까?
5. 실행계획에 `Using filesort`가 나왔다. 이것만으로 디스크 I/O가 발생했다고 말할 수 있을까? 또 인덱스가 커버링이라는 사실만으로 읽는 행 수가 적다고 말할 수 있을까?
