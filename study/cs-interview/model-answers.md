# 1. 운영체제

## 1.1 프로그램 실행 흐름

### OS-01. 프로그램이 실행되는 과정

**면접 답변:** 실행 파일을 실행하면 운영체제가 파일의 코드와 데이터를 가상 주소 공간에 배치하고, 스택과 힙을 준비한 뒤 PCB를 만들어 프로세스로 등록합니다. 프로세스가 준비 큐에 들어가고 스케줄러가 CPU를 배정하면, CPU가 명령어를 가져와 해석하고 실행합니다. 실행 중 파일·네트워크 같은 보호 자원이 필요하면 시스템 콜로 커널의 도움을 받고, 종료 시 운영체제가 메모리와 파일 디스크립터 같은 자원을 회수합니다.

**쉽게 말하면:** 프로그램 파일은 요리책이고 프로세스는 실제로 요리 중인 주방입니다. 운영체제는 주방 자리와 도구를 마련하고, CPU라는 요리사에게 차례로 일을 맡깁니다.

### OS-02. 프로세스 상태와 전이

**면접 답변:** 대표 상태는 생성(New), 준비(Ready), 실행(Running), 대기 또는 봉쇄(Waiting/Blocked), 종료(Terminated)입니다. 준비 상태에서 스케줄링되면 실행으로, 타임 슬라이스가 끝나거나 선점되면 다시 준비로 갑니다. 실행 중 I/O를 요청하면 대기로 이동하고, I/O가 끝나면 준비로 돌아옵니다.

**쉽게 말하면:** Ready는 계산대 줄에 선 상태, Running은 계산 중인 상태, Waiting은 카드 승인을 기다리는 상태입니다. 기다림이 끝났다고 바로 계산하는 것이 아니라 다시 CPU 줄인 Ready로 갑니다.

### OS-03. 프로세스 메모리 공간

**면접 답변:** 일반적으로 낮은 주소부터 코드(Text), 초기화된 데이터와 BSS, Heap, Stack 영역으로 나눕니다. 코드는 실행 명령, 데이터/BSS는 전역·정적 변수, Heap은 런타임 동적 할당, Stack은 함수 호출 정보와 지역 변수를 저장합니다. Heap은 보통 높은 주소 쪽으로, Stack은 낮은 주소 쪽으로 자라며 실제 배치는 운영체제와 실행 형식에 따라 달라질 수 있습니다.

**쉽게 말하면:** 코드는 레시피, 데이터는 공용 재료함, Heap은 필요할 때 빌리는 창고, Stack은 현재 처리 중인 주문표 더미입니다.

### OS-04. PCB

**면접 답변:** PCB(Process Control Block)는 운영체제가 프로세스를 관리하기 위한 커널 자료 구조입니다. PID, 현재 상태, 프로그램 카운터, CPU 레지스터, 스케줄링 정보, 메모리 관리 정보, 열린 파일과 I/O 상태, 계정 정보 등을 담습니다. 컨텍스트 스위칭 때 현재 실행 문맥을 PCB에 저장하고 다음 프로세스의 문맥을 복원합니다.

**쉽게 말하면:** CPU가 일을 잠시 멈출 때 어디까지 했는지 적어 두는 저장 카드입니다.

### OS-05. 시스템 콜과 인터럽트

**면접 답변:** 시스템 콜은 사용자 프로그램이 파일 읽기나 소켓 통신처럼 권한이 필요한 서비스를 커널에 요청하는 통제된 진입점입니다. 하드웨어 인터럽트는 타이머나 I/O 장치가 CPU에 사건 발생을 비동기적으로 알리는 신호입니다. 둘 다 커널 코드로 제어가 넘어갈 수 있지만, 시스템 콜은 현재 프로그램이 의도적으로 요청하고 하드웨어 인터럽트는 외부 사건이 끼어든다는 차이가 있습니다.

**주의:** 0으로 나누기나 페이지 폴트처럼 현재 명령 실행 중 발생하는 동기적 사건은 보통 예외(Exception/Trap)로 구분합니다.

## 1.2 스레드

### OS-06. 스레드와 필요성

**면접 답변:** 스레드는 프로세스 안의 실행 흐름 단위입니다. 같은 프로세스의 스레드는 코드·Heap·열린 파일을 공유하지만 각자 프로그램 카운터, 레지스터, Stack을 가집니다. 자원을 공유해 통신 비용이 낮고, I/O를 기다리는 동안 다른 작업을 실행하거나 여러 코어를 활용하기 위해 사용합니다.

### OS-07. 프로세스와 스레드

**면접 답변:** 프로세스는 독립된 주소 공간과 자원을 가진 실행 단위이고, 스레드는 그 프로세스 내부의 실행 단위입니다. 프로세스끼리는 격리가 강해 한쪽 장애가 덜 전파되지만 IPC 비용이 큽니다. 스레드는 공유 메모리로 빠르게 협력할 수 있지만 동기화가 필요하고 한 스레드의 치명적 오류가 프로세스 전체에 영향을 줄 수 있습니다.

### OS-08. 사용자 수준 스레드와 커널 수준 스레드

**면접 답변:** 사용자 수준 스레드는 사용자 라이브러리나 런타임이 스케줄링해서 생성·전환이 가볍지만, 커널이 개별 스레드를 모르면 하나의 블로킹 호출이 전체를 막거나 여러 코어 사용이 제한될 수 있습니다. 커널 수준 스레드는 운영체제가 직접 스케줄링해 병렬 실행과 블로킹 처리가 좋지만 생성과 전환 비용이 더 큽니다. 실제 런타임은 여러 사용자 스레드를 여러 커널 스레드에 매핑하기도 합니다.

### OS-09. 멀티 프로세스보다 멀티 스레드를 쓰는 이유

**면접 답변:** 같은 주소 공간을 공유하므로 데이터 전달이 빠르고, 생성과 컨텍스트 스위칭 비용도 보통 더 작기 때문입니다. 예를 들어 웹 서버의 여러 요청이 공통 캐시를 사용하기 쉽습니다. 다만 공유 상태 때문에 Race Condition이 생길 수 있으므로, 격리와 안정성이 더 중요하면 멀티 프로세스가 나을 수 있습니다.

## 1.3 CPU 스케줄링

### OS-10. 컨텍스트 스위칭

**면접 답변:** 컨텍스트 스위칭은 CPU가 실행 대상을 바꾸면서 현재 작업의 레지스터, 프로그램 카운터, 스택 포인터 같은 문맥을 저장하고 다음 작업의 문맥을 복원하는 과정입니다. 타이머 선점, I/O 대기, 우선순위가 높은 작업의 등장 등으로 발생합니다. 프로세스 전환은 주소 공간 변경까지 동반할 수 있어 같은 프로세스 내 스레드 전환보다 대체로 무겁습니다.

### OS-11. 컨텍스트 스위칭 비용

**면접 답변:** 문맥을 저장·복원하는 동안 실제 사용자 작업을 하지 못하고, 주소 공간이 바뀌면 TLB와 CPU 캐시의 유용한 내용이 줄어 다시 메모리에서 가져와야 하기 때문입니다. 스케줄러 실행과 커널 모드 전환 비용도 생깁니다. 따라서 스레드를 무작정 늘리면 병렬성이 좋아지기보다 전환 비용 때문에 처리량이 떨어질 수 있습니다.

### OS-12. CPU 스케줄링

**면접 답변:** CPU 스케줄링은 준비 상태의 작업 중 다음에 CPU를 사용할 작업을 고르는 정책입니다. CPU 이용률과 처리량을 높이고, 평균 대기·응답·반환 시간을 줄이며, 우선순위와 공정성을 만족시키기 위해 필요합니다. 대화형 시스템은 빠른 응답, 배치 시스템은 처리량처럼 목표가 다를 수 있습니다.

### OS-13. 대표 스케줄링 알고리즘

**면접 답변:** FCFS는 먼저 온 순서라 단순하지만 긴 작업이 앞을 막는 Convoy Effect가 있습니다. SJF/SRTF는 짧은 작업을 우선해 평균 대기 시간을 줄이지만 실행 시간을 미리 알아야 하고 긴 작업이 굶을 수 있습니다. Round Robin은 시간 할당량을 순환해 응답성이 좋지만 할당량이 너무 작으면 전환 비용이 커집니다. Priority는 중요 작업을 먼저 처리하지만 Starvation 방지가 필요하고, 실제 OS는 다단계 피드백 큐처럼 여러 정책을 조합합니다.

### OS-14. Starvation

**면접 답변:** Starvation은 실행 가능한 작업이 계속 다른 작업에 밀려 CPU나 락을 사실상 영원히 얻지 못하는 현상입니다. 우선순위 스케줄링에서는 오래 기다린 작업의 우선순위를 점차 올리는 Aging으로 완화할 수 있습니다. 공정한 큐, 대기 시간 상한, 락의 공정성 정책도 해결책입니다.

## 1.4 메모리 관리

### OS-15. 운영체제의 메모리 관리

**면접 답변:** 운영체제는 각 프로세스에 독립적인 가상 주소 공간을 제공하고, 페이지 테이블을 이용해 가상 페이지를 물리 프레임에 매핑합니다. 필요한 페이지만 메모리에 올리는 Demand Paging, 페이지 교체, 보호 비트와 권한 검사, 공유 페이지 등을 관리합니다. 목적은 제한된 RAM을 효율적으로 쓰면서 프로세스를 서로 격리하는 것입니다.

### OS-16. 내부 단편화와 외부 단편화

**면접 답변:** 내부 단편화는 고정 크기 블록을 할당했는데 요청보다 커서 블록 내부가 남는 현상입니다. 외부 단편화는 가용 공간의 총합은 충분하지만 작은 조각으로 흩어져 큰 연속 공간을 만들지 못하는 현상입니다. 페이징은 외부 단편화를 크게 줄이지만 마지막 페이지 등에서 내부 단편화가 생길 수 있고, 세그멘테이션은 외부 단편화가 생길 수 있습니다.

### OS-17. 가상 메모리

**면접 답변:** 가상 메모리는 프로세스가 실제 RAM과 독립된 연속 주소 공간을 사용하는 것처럼 보이게 하는 추상화입니다. 페이지 단위 매핑으로 프로세스를 격리하고, 필요한 페이지만 RAM에 올려 물리 메모리보다 큰 프로그램도 실행할 수 있게 합니다. 또한 공유 라이브러리, Copy-on-Write, 메모리 매핑 파일 같은 기능의 기반이 됩니다.

### OS-18. 가상 주소를 물리 주소로 바꾸는 과정

**면접 답변:** CPU가 만든 가상 주소는 가상 페이지 번호와 페이지 내부 오프셋으로 나뉩니다. MMU가 먼저 TLB에서 페이지 번호의 매핑을 찾고, 없으면 메모리의 페이지 테이블을 조회합니다. 유효한 물리 프레임 번호를 찾으면 같은 오프셋을 붙여 물리 주소를 만들고, 매핑이 없거나 권한이 맞지 않으면 페이지 폴트 예외가 발생합니다.

### OS-19. 페이지 폴트 처리

**면접 답변:** CPU가 접근한 페이지가 RAM에 없으면 커널로 제어가 넘어갑니다. 운영체제는 주소가 유효한지 확인하고, 빈 프레임을 찾거나 희생 페이지를 고른 뒤 필요한 페이지를 디스크에서 읽습니다. 페이지 테이블과 TLB를 갱신하고 중단된 명령을 다시 실행합니다. 주소가 유효하지 않으면 프로세스에 오류를 전달하거나 종료합니다.

### OS-20. 페이지 교체 알고리즘

**면접 답변:** RAM이 가득 찼을 때 어떤 페이지를 내보낼지 고르는 정책입니다. FIFO는 오래 들어온 페이지, LRU는 가장 오래 사용되지 않은 페이지, LFU는 사용 빈도가 낮은 페이지를 선택합니다. 이론적 OPT는 앞으로 가장 늦게 쓸 페이지를 골라 기준점이 되지만 미래를 알 수 없어 구현할 수 없습니다. 실제 OS는 참조 비트를 이용한 Clock 같은 근사 알고리즘과 Dirty 여부를 함께 고려합니다.

### OS-21. 스와핑과 성능 저하

**면접 답변:** 디스크나 SSD는 RAM보다 훨씬 느려 페이지를 내리고 올리는 동안 긴 I/O 대기가 발생합니다. 작업 집합보다 RAM이 부족해 페이지 폴트가 연속으로 나면 CPU는 실제 계산보다 페이지 교체에 시간을 쓰는 Thrashing 상태가 됩니다. 페이지 폴트율, 스왑 입출력, 메모리 압박을 함께 봐야 합니다.

## 1.5 동시성

### OS-22. Race Condition

**면접 답변:** 여러 실행 흐름이 공유 데이터를 동시에 읽고 수정할 때, 실행 순서에 따라 결과가 달라지는 문제입니다. `count++`처럼 한 줄로 보여도 읽기·증가·쓰기 여러 단계라 두 스레드의 연산이 섞이면 업데이트가 사라질 수 있습니다. 공유된 변경 가능 상태와 비원자적 연산, 적절한 동기화 부재가 원인입니다.

### OS-23. Race Condition 방지

**면접 답변:** 임계 구역을 Mutex/Lock이나 `synchronized`로 직렬화하거나, 원자적 연산을 사용합니다. 불변 객체, Thread Confinement, 메시지 전달처럼 공유 변경 상태 자체를 줄이는 방법이 더 근본적일 수 있습니다. 락을 쓸 때는 범위를 작게 하고 획득 순서를 정해 데드락과 성능 저하를 함께 관리합니다.

### OS-24. 이진 세마포어와 뮤텍스

**면접 답변:** 둘 다 값이 0 또는 1이라 상호 배제에 쓸 수 있지만 의미가 다릅니다. Mutex는 소유권이 있어 락을 획득한 실행 흐름이 해제해야 하며, 임계 구역 보호가 주목적입니다. 이진 세마포어는 소유권이 없어 다른 실행 흐름이 신호를 줄 수 있으므로 작업 간 알림에도 쓸 수 있습니다. 구현에 따라 Mutex는 우선순위 상속 같은 기능을 제공하기도 합니다.

### OS-25. 가시성과 원자성

**면접 답변:** 가시성 문제는 한 스레드의 변경이 다른 스레드에 언제 보이는지의 문제입니다. 원자성 문제는 하나처럼 보여야 하는 연산이 중간에 끼어들 수 있는 여러 단계로 실행되는 문제입니다. 가시성만 보장하는 `volatile`로 `count++`의 원자성까지 보장할 수는 없으며, 원자 타입이나 락이 필요합니다.

### OS-26. 데드락과 네 가지 조건

**면접 답변:** 데드락은 여러 작업이 서로가 가진 자원을 기다리며 아무도 진행하지 못하는 상태입니다. 네 조건은 하나만 사용할 수 있는 상호 배제, 자원을 가진 채 다른 자원을 기다리는 점유와 대기, 자원을 강제로 빼앗을 수 없는 비선점, 원형으로 기다리는 순환 대기입니다. 네 조건이 동시에 성립해야 하므로 하나라도 깨면 예방할 수 있습니다.

### OS-27. 데드락 예방과 회복

**면접 답변:** 예방은 모든 락을 정해진 순서로 획득해 순환 대기를 없애거나, 필요한 자원을 한 번에 요청해 점유와 대기를 깨는 방식입니다. 회피는 Banker 알고리즘처럼 안전 상태를 유지하지만 실제 범용 시스템에서는 비용과 사전 정보 문제로 제한적입니다. 감지 후에는 대기 그래프를 찾아 작업 하나를 중단하거나 롤백하고, 실무에서는 락 타임아웃과 재시도도 사용합니다.

## 1.6 I/O 모델

### OS-28. 동기와 비동기

**면접 답변:** 동기/비동기는 작업 완료를 누가 언제 알려주고 후속 흐름을 어떻게 이어가는지에 관한 구분입니다. 동기는 호출 측이 완료를 확인한 뒤 다음 일을 진행하고, 비동기는 작업을 맡긴 뒤 다른 일을 하다가 콜백·Future·이벤트로 완료 통지를 받습니다. 비동기라고 반드시 논블로킹인 것은 아니며 구현 조합을 따로 봐야 합니다.

### OS-29. 블로킹과 논블로킹

**면접 답변:** 블로킹/논블로킹은 호출한 순간 제어권이 언제 반환되는지에 관한 구분입니다. 블로킹 호출은 결과가 준비될 때까지 호출 스레드가 기다리고, 논블로킹 호출은 즉시 가능한 결과나 “아직 준비되지 않음”을 반환합니다. 논블로킹만 사용해도 계속 확인하는 Busy Waiting이 생길 수 있어 이벤트 통지나 I/O Multiplexing과 함께 사용합니다.

### OS-30. 스레드 기반 I/O와 이벤트 루프 기반 I/O

**면접 답변:** 스레드 기반 모델은 보통 요청마다 스레드를 배정하고 블로킹 I/O를 사용해 코드 흐름이 단순합니다. 이벤트 루프 모델은 소수 스레드가 많은 논블로킹 연결의 준비 이벤트를 받아 짧은 작업을 처리하므로 동시 연결이 많을 때 메모리와 전환 비용이 적습니다. 반면 이벤트 루프에서 CPU 작업이나 블로킹 호출을 하면 전체 처리가 밀리므로 별도 작업 풀로 보내야 합니다.

## 1.7 파일 시스템

### OS-31. 파일 시스템과 읽기/쓰기

**면접 답변:** 파일 시스템은 저장 장치의 바이트를 파일과 디렉터리라는 이름 있는 구조로 관리하며, 권한·크기·블록 위치 같은 메타데이터도 저장합니다. 읽을 때 경로를 따라 메타데이터와 데이터 블록을 찾고, 페이지 캐시에 있으면 메모리에서 반환하며 없으면 장치에서 읽습니다. 쓰기는 보통 페이지 캐시에 먼저 반영된 뒤 지연 기록되고, `fsync`는 필요한 내용을 안정적인 저장 장치에 반영하도록 요청합니다.

### OS-32. 파일과 디렉터리 관리

**면접 답변:** Unix 계열에서 파일의 메타데이터와 데이터 블록 위치는 inode 같은 구조에 저장되고, 디렉터리는 이름을 inode 번호에 연결하는 특수한 파일입니다. 경로 탐색은 루트나 현재 디렉터리부터 각 이름을 차례로 조회하는 과정입니다. 하드 링크는 같은 inode를, 심볼릭 링크는 다른 경로 문자열을 가리킵니다.

### OS-33. 디스크 I/O가 메모리보다 느린 이유

**면접 답변:** RAM은 CPU와 가까운 전자 회로에서 임의 위치에 빠르게 접근하지만 저장 장치는 더 느린 인터페이스와 컨트롤러를 거칩니다. HDD는 헤드 이동과 회전이라는 기계 지연까지 있고, SSD도 플래시 변환 계층·페이지 읽기·블록 단위 삭제 비용이 있습니다. 그래서 운영체제는 페이지 캐시, 버퍼링, 순차 I/O, 비동기 I/O로 차이를 숨깁니다.

# 2. Java

## 2.1 JVM과 실행 원리

### JAVA-01. JVM의 장단점

**면접 답변:** JVM은 Java 바이트코드를 운영체제별 JVM에서 실행해 플랫폼 독립성을 제공하고, GC·메모리 안전성·런타임 최적화·모니터링 같은 공통 기능을 제공합니다. 반면 VM과 런타임 메타데이터만큼 메모리를 더 쓰고, 시작 초기에 클래스 로딩과 JIT 워밍업 비용이 있으며, GC 일시 정지가 생길 수 있습니다. 장시간 동작한 서버에서는 JIT가 실제 실행 패턴에 맞춰 최적화해 네이티브 코드와의 차이를 많이 줄입니다.

### JAVA-02. Java가 C/C++보다 느릴 수 있는 이유

**면접 답변:** 시작 시 바이트코드 해석, 클래스 로딩, JIT 컴파일이 필요하고 객체 배치와 GC에 추가 비용이 있기 때문입니다. 배열 경계 검사나 동적 디스패치 같은 안전 장치도 있습니다. 다만 JIT는 실제 런타임 정보를 이용해 인라이닝과 탈출 분석을 하므로 “Java는 항상 느리다”는 표현은 부정확하고, 워크로드·구현·워밍업 상태로 비교해야 합니다.

### JAVA-03. Java 실행 과정

**면접 답변:** `javac`가 소스 코드를 JVM 명령인 바이트코드가 든 `.class`로 컴파일합니다. 실행 시 Class Loader가 클래스를 로딩·링크·초기화하고, JVM이 바이트코드를 검증합니다. Execution Engine은 처음에는 인터프리터로 실행하면서 프로파일을 수집하고, 자주 실행되는 코드를 JIT가 네이티브 코드로 컴파일합니다. 객체 메모리는 런타임 영역에 배치되고 GC가 회수합니다.

### JAVA-04. 인터프리터와 JIT

**면접 답변:** 인터프리터는 바이트코드를 한 명령씩 바로 실행해 시작이 빠르지만 반복 코드도 매번 해석합니다. JIT(Just-In-Time) 컴파일러는 자주 실행되는 메서드와 루프를 네이티브 코드로 바꿔 이후 실행을 빠르게 합니다. JVM은 인터프리터로 빠르게 시작하고 프로파일을 얻은 뒤 JIT 최적화를 적용하는 혼합 방식을 사용합니다.

### JAVA-05. Hot Code 판단

**면접 답변:** JVM은 메서드 호출 횟수와 루프의 Back Edge 횟수 같은 실행 프로파일을 카운터로 수집합니다. 임계값을 넘은 메서드나 루프를 Hot Spot으로 보고 컴파일 큐에 넣습니다. 계층형 컴파일에서는 빠른 저수준 컴파일로 시작하고, 충분한 프로파일이 모이면 더 공격적인 고수준 최적화를 적용합니다.

### JAVA-06. Code Cache가 가득 찼을 때

**면접 답변:** Code Cache는 JIT가 만든 네이티브 코드를 저장하는 공간입니다. 공간이 부족하면 오래되거나 사용되지 않는 컴파일 코드를 정리할 수 있지만, 끝내 공간을 확보하지 못하면 추가 JIT 컴파일이 제한되거나 중지되어 새 Hot Code가 인터프리터 또는 낮은 최적화 수준으로 실행될 수 있습니다. 컴파일 로그와 Code Cache 사용량을 확인하고, 원인 분석 뒤 크기 옵션을 조정합니다.

### JAVA-07. 배포 직후 초기 요청이 느린 이유

**면접 답변:** 클래스 로딩·검증·초기화, DI 컨테이너 초기화, 커넥션 생성, 캐시 미스와 함께 JIT가 아직 충분히 최적화하지 않은 Cold 상태이기 때문입니다. 운영 트래픽을 받기 전에 Health Check와 Warm-up 요청을 보내고, 필요한 캐시와 풀을 준비하면 완화할 수 있습니다. 단, 의미 없는 전체 코드 워밍업보다 실제 주요 경로를 대상으로 해야 합니다.

## 2.2 Garbage Collection

### JAVA-08. GC 알고리즘과 Java의 방식

**면접 답변:** 기본 알고리즘은 살아 있는 객체를 표시하는 Mark, 죽은 객체 공간을 회수하는 Sweep, 살아 있는 객체를 모으는 Compact, 다른 영역으로 복사하는 Copy입니다. Java GC는 하나만 쓰지 않고 세대 가설에 따라 Young 영역에는 복사 중심, Old 영역에는 Mark-Sweep-Compact 계열을 조합합니다. Parallel, G1, ZGC처럼 수집기가 달라지면 병렬성·동시성·일시 정지 목표가 달라집니다.

### JAVA-09. Java 8 Heap 구조와 GC 시점

**면접 답변:** Heap은 크게 Young과 Old로 나뉘고, Young은 Eden과 두 Survivor 영역으로 구성됩니다. 새 객체는 주로 Eden에 생기며 공간이 부족하면 Minor GC가 살아남은 객체를 Survivor로 복사하고, 여러 번 살아남거나 공간이 부족한 객체는 Old로 승격합니다. Old 수집은 수집기 정책과 메모리 압박에 따라 발생합니다. Java 8부터 클래스 메타데이터는 Heap의 PermGen이 아니라 네이티브 메모리의 Metaspace에 저장됩니다.

### JAVA-10. GC Root와 Root Space

**면접 답변:** 정확한 핵심 용어는 GC Root입니다. 현재 실행 중인 스레드 Stack의 참조, 로드된 클래스의 정적 참조, JNI 참조처럼 객체 그래프 탐색의 출발점이 되는 참조들입니다. GC는 Root에서 도달 가능한 객체를 살아 있다고 판단하고, 도달할 수 없는 객체를 회수합니다. “Root Space”는 보통 이 Root 집합이나 Root가 존재하는 영역을 느슨하게 부르는 표현입니다.

### JAVA-11. Young과 Old를 나눈 이유

**면접 답변:** 대부분의 객체는 생성 후 금방 죽고 일부만 오래 산다는 세대 가설을 이용하기 위해서입니다. 새 객체가 모인 Young을 자주 작게 수집하면 전체 Heap을 매번 훑지 않아도 되고, 오래 살아남은 객체만 Old로 보내 덜 자주 수집할 수 있습니다. 세대 간 참조는 Remembered Set이나 Card Table 같은 보조 구조로 추적합니다.

### JAVA-12. Stop-The-World

**면접 답변:** Stop-The-World는 GC나 일부 JVM 작업을 위해 애플리케이션 스레드를 안전 지점에서 모두 멈추는 구간입니다. 객체 그래프나 참조를 일관되게 관찰하고 이동된 참조를 안전하게 갱신하기 위해 필요합니다. 동시 수집기도 모든 단계를 완전히 없애지는 못하지만, 긴 작업의 상당 부분을 애플리케이션과 동시에 수행해 멈춤을 줄입니다.

### JAVA-13. 주요 Garbage Collector

**면접 답변:** Serial GC는 단일 스레드로 단순해 작은 Heap에 적합합니다. Parallel GC는 여러 스레드로 수집해 처리량을 중시합니다. CMS는 Old 수집을 애플리케이션과 동시에 수행해 멈춤을 줄였지만 단편화와 복잡성 때문에 제거됐습니다. G1은 Heap을 Region으로 나누고 회수 효율이 높은 Region을 우선 수집해 예측 가능한 멈춤을 목표로 합니다. ZGC와 Shenandoah는 매우 큰 Heap에서도 짧은 멈춤을 목표로 대부분의 작업을 동시 수행합니다.

### JAVA-14. Java 8과 Java 11의 기본 GC

**면접 답변:** 일반적인 Server-Class 환경의 HotSpot 기준으로 Java 8의 기본은 Parallel GC, Java 11의 기본은 G1 GC입니다. 서버 Heap이 커지고 응답 지연의 중요성이 커지면서 처리량 중심의 Parallel보다 멈춤 시간을 예측·제어하기 쉬운 G1이 기본이 됐습니다. 다만 JVM 배포판과 실행 환경에 따라 기본 선택이 달라질 수 있으므로 운영에서는 실제 플래그를 확인해야 합니다.

### JAVA-15. G1 GC

**면접 답변:** G1은 Heap을 연속된 Young/Old 덩어리 대신 같은 크기의 여러 Region으로 나눕니다. Region별 살아 있는 객체 비율과 회수 비용을 추정해 이득이 큰 Region부터 수집하고, Young과 일부 Old를 함께 수집하는 Mixed GC를 수행합니다. Remembered Set으로 Region 간 참조를 추적하며, 목표 일시 정지 시간을 맞추려 하지만 그것이 절대 보장은 아닙니다.

### JAVA-16. GC 모니터링과 OOM 대응

**면접 답변:** GC가 잦거나 멈춤이 길면 처리량과 응답 지연이 나빠지고, 메모리 누수나 과도한 할당의 신호일 수 있어 모니터링이 필요합니다. Heap 사용량, 할당률, GC 횟수·시간, 승격률, Old 회수 후 바닥값을 봅니다. OOM 시에는 오류 종류를 먼저 구분하고 Heap Dump, GC 로그, 스레드 덤프, 네이티브 메모리 지표를 보존한 뒤 지배 객체와 참조 경로를 분석합니다. 원인 없이 Heap만 키우면 장애를 늦출 뿐입니다.

## 2.3 Java 동시성

### JAVA-17. Java의 동시성 문제

**면접 답변:** 대표적으로 공유 값을 잃어버리는 원자성 문제, 한 스레드의 변경을 다른 스레드가 못 보는 가시성 문제, 컴파일러·CPU 재배치 때문에 기대한 순서가 깨지는 순서성 문제가 있습니다. Java Memory Model은 Happens-Before 관계로 언제 변경이 보장되는지 정의합니다. 락, `volatile`, 원자 클래스, 동시성 컬렉션을 문제의 성격에 맞게 사용해야 합니다.

### JAVA-18. 가시성 문제 발생 시점

**면접 답변:** 여러 스레드가 동기화 없이 같은 변경 가능 데이터를 접근하고, 한 스레드가 쓴 값이 다른 코어의 캐시나 컴파일러 최적화 때문에 즉시 관찰되지 않을 때 발생합니다. 예를 들어 종료 플래그를 일반 `boolean`으로 두면 반복문이 변경을 못 볼 수 있습니다. `volatile` 읽기/쓰기, 락 해제/획득, 스레드 시작/종료 같은 Happens-Before 관계가 가시성을 보장합니다.

### JAVA-19. 원자성 문제 예시

**면접 답변:** 두 스레드가 동시에 `count++`를 실행하면 각각 같은 기존 값을 읽고 1을 더해 같은 값을 쓸 수 있어 한 번의 증가가 사라집니다. `count++`는 읽기·계산·쓰기의 복합 연산이기 때문입니다. `AtomicInteger.incrementAndGet()`이나 락으로 전체 연산을 하나의 임계 구역으로 만들어 해결합니다.

### JAVA-20. Java 동시성 문제 해결법

**면접 답변:** 단순 가시성이나 상태 플래그는 `volatile`, 단일 값의 원자적 갱신은 `Atomic*`, 복합 불변식은 `synchronized`나 `Lock`으로 보호합니다. 공유 컬렉션은 `ConcurrentHashMap` 같은 동시성 컬렉션을 사용합니다. 가능하면 불변 객체, 작업별 소유권, 메시지 큐로 공유 자체를 줄이고, 스레드 안전성 규칙을 클래스 경계 안에 감춥니다.

### JAVA-21. synchronized의 문제점

**면접 답변:** 경쟁이 심하면 스레드가 대기하고 깨어나는 비용과 컨텍스트 스위칭이 늘며, 임계 구역이 길면 병렬성이 크게 줄어듭니다. 여러 락의 획득 순서가 엇갈리면 데드락이 생길 수 있습니다. `synchronized`는 타임아웃·인터럽트 가능한 획득·여러 Condition 같은 세밀한 제어가 부족하므로 필요하면 `ReentrantLock`을 고려합니다. 다만 경쟁이 적을 때는 JVM 최적화 덕분에 무조건 느리다고 볼 수 없습니다.

### JAVA-22. synchronized 구현

**면접 답변:** 인스턴스 동기화는 객체의 모니터를, 정적 동기화는 `Class` 객체의 모니터를 사용합니다. 바이트코드에서는 블록에 `monitorenter/monitorexit`, 동기화 메서드에 `ACC_SYNCHRONIZED` 플래그가 사용됩니다. JVM은 경쟁 상태에 따라 가벼운 경로에서 CAS와 스핀을 활용하고, 경쟁이 커지면 스레드를 대기시키는 모니터 경로로 전환할 수 있습니다. 락 해제와 다음 락 획득 사이에는 Happens-Before가 성립합니다.

### JAVA-23. 스레드 풀

**면접 답변:** 스레드 풀은 미리 만들거나 제한된 수의 스레드를 재사용해 작업 큐의 일을 처리하는 구조입니다. 작업마다 스레드를 만드는 비용을 줄이고, 동시에 실행할 작업 수를 제한해 CPU·메모리·외부 자원을 보호합니다. 크기는 CPU 작업이면 코어 수 근처, I/O 작업이면 대기 비율을 고려하되, 큐 길이·거부 정책·응답 시간과 함께 부하 테스트로 정해야 합니다.

### JAVA-24. Spring MVC가 많은 스레드를 운영하는 이유

**면접 답변:** 전통적인 Spring MVC의 요청-스레드 모델은 DB나 외부 API를 기다리는 블로킹 시간이 길어 한 스레드가 CPU를 계속 쓰지 않습니다. 여러 스레드를 두면 일부가 기다리는 동안 다른 요청이 CPU를 사용해 처리량을 높이고, 순차 코드라 개발과 디버깅도 단순합니다. 다만 스레드와 DB 커넥션을 무작정 늘리면 전환 비용과 병목이 커지므로 풀 크기와 타임아웃으로 제한합니다.

## 2.4 객체지향 프로그래밍

### JAVA-25. 캡슐화

**면접 답변:** 캡슐화는 객체가 데이터와 그 데이터를 지키는 동작을 함께 소유하고, 외부에는 필요한 의도만 공개하는 것입니다. 단순히 필드를 `private`로 만드는 것이 아니라 유효성 규칙과 상태 전이를 객체 내부에 모읍니다. 그러면 변경 영향 범위가 줄고, 잘못된 상태를 만들기 어려우며, 호출자는 내부 표현을 몰라도 됩니다.

### JAVA-26. 무분별한 getter/setter의 문제

**면접 답변:** 모든 상태를 읽고 쓰게 하면 외부 코드가 객체의 불변식을 우회하고, 객체가 로직 없는 데이터 주머니가 됩니다. 예를 들어 잔액에 `setBalance(-100)`을 허용하기보다 `withdraw(amount)`가 잔액 검증과 기록을 함께 수행해야 합니다. 필요한 조회는 제공하되, 변경은 업무 의미가 드러나는 메서드로 제한합니다.

### JAVA-27. 상속과 사용 시점

**면접 답변:** 상속은 하위 타입이 상위 타입의 계약과 구현 일부를 물려받아 “is-a” 관계를 표현하는 방식입니다. 하위 타입이 상위 타입을 완전히 대체할 수 있고 공통 불변식과 구현을 안정적으로 공유할 때 적합합니다. 단순 코드 재사용만을 위해 쓰기보다 진짜 타입 계층인지, 리스코프 치환 원칙을 지키는지 확인해야 합니다.

### JAVA-28. 상속의 단점

**면접 답변:** 하위 클래스가 상위 클래스의 구현 세부사항과 생명주기에 강하게 결합되고, 상위 변경이 예상치 못하게 전파됩니다. 깊은 계층은 동작을 추적하기 어렵고, 한 부모만 상속할 수 있어 조합 유연성도 떨어집니다. 잘못된 오버라이드는 상위 타입의 계약을 깨뜨릴 수 있습니다.

### JAVA-29. 상속과 조합

**면접 답변:** 상속은 “A는 B다”라는 타입 관계로 부모의 계약과 구현을 물려받습니다. 조합은 “A가 B를 가진다”는 관계로 필요한 기능을 다른 객체에 위임합니다. 조합은 구현을 인터페이스 뒤에 숨기고 런타임 교체가 쉬워 결합도가 낮으므로, 명확한 타입 계층이 아니라면 보통 조합을 우선합니다.

### JAVA-30. 다형성

**면접 답변:** 다형성은 같은 인터페이스 호출이 실제 객체 타입에 따라 다른 동작을 수행하는 성질입니다. 호출자는 구체 클래스 대신 추상 타입에 의존하므로 새로운 구현을 추가해도 기존 조건문과 호출 코드를 덜 바꿉니다. 예를 들어 `PaymentProcessor` 인터페이스 뒤에 카드·계좌 결제 구현을 교체할 수 있습니다.

### JAVA-31. 반복적인 instanceof의 문제

**면접 답변:** 타입마다 `instanceof` 분기를 반복하면 새 타입이 추가될 때 여러 조건문을 수정해야 해 개방-폐쇄 원칙을 어기기 쉽습니다. 해당 타입이 알아야 할 동작을 외부가 대신 결정한다는 신호이기도 합니다. 가능한 경우 공통 인터페이스의 다형적 메서드로 옮기되, 직렬화 경계나 제한된 패턴 매칭처럼 타입 분기가 자연스러운 곳은 예외입니다.

### JAVA-32. 인터페이스와 추상 클래스

**면접 답변:** 인터페이스는 구현체가 지켜야 할 역할과 계약을 표현하며 여러 개를 구현할 수 있습니다. 추상 클래스는 공통 상태, 생성 규칙, 보호된 메서드와 일부 구현을 공유하는 가까운 타입 계층에 적합하고 하나만 상속할 수 있습니다. 인터페이스도 `default` 메서드를 가질 수 있지만 인스턴스 상태와 생성자를 가질 수 없다는 차이가 핵심입니다.

### JAVA-33. 인터페이스와 추상 클래스 선택

**면접 답변:** 서로 다른 계층의 객체가 같은 역할을 수행하거나 구현 교체·테스트 대역이 중요하면 인터페이스를 선택합니다. 공통 상태와 불변식, 템플릿 실행 흐름을 강하게 공유하는 진짜 가족 관계라면 추상 클래스를 고려합니다. 보통 외부 계약은 인터페이스로 두고, 구현 재사용은 조합으로 해결한 뒤 필요한 경우에만 추상 클래스를 씁니다.

## 2.5 람다, 스트림, 함수형 프로그래밍

### JAVA-34. 람다와 스트림

**면접 답변:** 람다는 함수를 값처럼 전달할 수 있게 하는 익명 함수 표현이며 Java에서는 함수형 인터페이스의 인스턴스로 사용됩니다. 스트림은 컬렉션 등의 데이터를 `filter`, `map`, `reduce` 같은 선언적 파이프라인으로 처리하는 추상화입니다. 스트림은 데이터를 저장하지 않고, 한 번 소비되며, 내부 반복과 지연 연산을 사용합니다.

### JAVA-35. Java 8이 람다와 스트림을 도입한 이유

**면접 답변:** 가독성 외에도 동작을 값으로 전달하고, 데이터 처리의 “무엇”을 순회 방식인 “어떻게”와 분리하기 위해서입니다. 외부 반복을 내부 반복으로 바꾸면 라이브러리가 지연 실행, 연산 결합, 병렬 분할을 최적화할 수 있습니다. 다만 `parallelStream`은 공유 상태와 공용 풀, 작업 크기를 고려하지 않으면 더 느리거나 위험할 수 있습니다.

### JAVA-36. 함수형 프로그래밍

**면접 답변:** 함수형 프로그래밍은 계산을 함수의 조합으로 표현하고, 불변 데이터와 부수 효과가 적은 순수 함수를 선호하는 방식입니다. 같은 입력에 같은 결과를 내는 함수는 추론과 테스트가 쉽고 병렬 처리에도 유리합니다. Java는 순수 함수형 언어가 아니므로, 핵심 계산은 순수하게 만들고 I/O와 상태 변경은 경계에 모으는 식으로 장점을 활용합니다.

### JAVA-37. 스트림의 지연 연산

**면접 답변:** `filter`와 `map` 같은 중간 연산은 호출 즉시 전체 데이터를 처리하지 않고 파이프라인만 구성합니다. `collect`, `reduce`, `findFirst` 같은 최종 연산이 호출될 때 실제 처리가 시작됩니다. 덕분에 연산을 한 번의 순회로 합치고, `findFirst`처럼 답을 찾으면 남은 데이터를 처리하지 않는 Short-Circuit 최적화가 가능합니다.

# 3. 데이터베이스

## 3.1 트랜잭션

### DB-01. 트랜잭션과 ACID

**면접 답변:** 트랜잭션은 여러 DB 작업을 하나의 논리적 작업 단위로 묶는 것입니다. Atomicity는 전부 성공하거나 전부 취소, Consistency는 정의된 제약과 규칙을 만족하는 상태로 전이, Isolation은 동시에 실행된 트랜잭션의 중간 결과를 적절히 숨김, Durability는 커밋된 결과가 장애 후에도 남음을 뜻합니다. DB는 로그, 락/MVCC, 복구 절차로 이를 지원하지만 업무 일관성 규칙은 애플리케이션도 함께 지켜야 합니다.

### DB-02. 트랜잭션 사용 시 주의점

**면접 답변:** 트랜잭션이 길면 락과 버전이 오래 유지돼 대기, 데드락, Undo 증가가 커지므로 범위를 짧게 해야 합니다. 트랜잭션 안에서 느린 외부 API나 사용자 입력을 기다리지 않고, 같은 레코드를 수정할 때는 접근 순서를 통일합니다. 실패 시 재시도 가능성을 고려해 멱등성을 설계하고, 격리 수준과 읽기/쓰기 방식이 실제 DB에서 어떻게 동작하는지 확인해야 합니다.

### DB-03. 트랜잭션 격리 수준

**면접 답변:** 표준 격리 수준은 READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE 순으로 강해집니다. 수준이 높아질수록 다른 트랜잭션 변화로 인한 이상 현상을 더 막지만 대기와 충돌이 늘 수 있습니다. 실제 동작은 DB의 MVCC와 락 구현에 따라 다르므로, 이름만으로 판단하지 않고 사용 DB 문서를 확인해야 합니다.

### DB-04. Dirty, Non-Repeatable, Phantom Read

**면접 답변:** Dirty Read는 아직 커밋되지 않은 값을 읽는 현상입니다. Non-Repeatable Read는 같은 행을 두 번 읽었는데 다른 트랜잭션의 수정·삭제 때문에 값이 달라지는 현상입니다. Phantom Read는 같은 조건 범위를 다시 조회했을 때 다른 트랜잭션의 삽입·삭제로 행 집합이 달라지는 현상입니다. “한 행 값이 바뀜”과 “조건에 맞는 행 집합이 바뀜”을 구분하는 것이 핵심입니다.

### DB-05. 격리 문제 해결

**면접 답변:** 요구되는 일관성에 맞춰 격리 수준을 높이는 것이 기본이지만, 모든 트랜잭션을 SERIALIZABLE로 만들면 동시성이 크게 줄 수 있습니다. 특정 갱신에는 `SELECT ... FOR UPDATE`, 낙관적 버전 컬럼, 원자적 조건부 UPDATE를 사용하고, 범위 삽입까지 막아야 하면 범위 락이나 DB의 Serializable 동작을 활용합니다. 충돌이 정상적으로 발생할 수 있는 설계라면 짧은 재시도도 포함합니다.

### DB-06. MVCC

**면접 답변:** MVCC(Multi-Version Concurrency Control)는 한 행의 여러 버전을 관리해 읽기가 자신의 스냅샷에 맞는 버전을 선택하게 하는 방식입니다. 읽기가 쓰기를, 쓰기가 읽기를 불필요하게 막지 않아 동시성을 높입니다. 대신 오래 열린 트랜잭션은 과거 버전 정리를 막아 저장 공간과 성능에 영향을 주므로 장기 트랜잭션을 관리해야 합니다.

### DB-07. InnoDB REPEATABLE READ와 Phantom Read

**면접 답변:** InnoDB의 일반 Consistent Read는 트랜잭션의 Read View를 사용해 같은 스냅샷을 보므로 반복 조회에서 새 행이 보이지 않습니다. `SELECT ... FOR UPDATE` 같은 Locking Read와 변경 작업에서는 인덱스 레코드 사이까지 잠그는 Next-Key Lock, 즉 레코드 락과 Gap Lock의 조합으로 범위 삽입을 막습니다. 다만 조회 방식과 인덱스 조건에 따라 동작이 다르므로 “REPEATABLE READ면 모든 상황의 Phantom이 무조건 사라진다”라고 단정하면 안 됩니다.

## 3.2 Lock과 동시성 제어

### DB-08. DB Lock의 종류

**면접 답변:** Lock은 동시에 접근하는 트랜잭션의 충돌을 제어해 일관성을 지키는 장치입니다. 읽기를 공유하는 Shared Lock과 변경을 독점하는 Exclusive Lock이 기본이며, 범위에 따라 Row·Page·Table Lock이 있습니다. InnoDB에는 상위 수준 잠금 의도를 나타내는 Intention Lock과 범위 삽입을 제어하는 Gap/Next-Key Lock도 있습니다.

### DB-09. 낙관적 락과 비관적 락

**면접 답변:** 낙관적 락은 충돌이 드물다고 보고 잠그지 않은 채 작업한 뒤 버전 번호나 조건부 UPDATE로 충돌을 검출합니다. 비관적 락은 충돌 가능성이 높다고 보고 읽는 시점부터 `FOR UPDATE` 등으로 다른 변경을 막습니다. 낙관적 락은 대기가 적지만 충돌 시 재시도가 필요하고, 비관적 락은 즉시 일관성을 지키기 쉽지만 대기와 데드락 위험이 있습니다.

### DB-10. 낙관적/비관적 락 선택

**면접 답변:** 읽기가 많고 충돌이 드물며 재시도 비용이 작은 편집·설정 변경에는 낙관적 락이 적합합니다. 재고 차감처럼 충돌 가능성이 높고 실패 후 작업을 되돌리기 어렵거나, 갱신 전 값을 반드시 잠가야 하면 비관적 락을 고려합니다. 트래픽 패턴, 임계 구역 길이, 재시도 비용을 측정해 선택하며 핵심 갱신을 원자적 SQL로 끝낼 수 있는지도 먼저 봅니다.

### DB-11. 분산 락

**면접 답변:** 분산 락은 여러 프로세스나 서버가 공유 자원에 대한 임계 구역을 하나만 실행하도록 조정하는 장치입니다. 단일 JVM 락으로 보호할 수 없는 스케줄 작업, 외부 자원 갱신 등에 사용합니다. 임대 만료, 네트워크 분할, 정지된 소유자가 뒤늦게 작업하는 문제를 고려해야 하며, TTL만 믿지 말고 Fencing Token이나 DB의 조건부 쓰기로 오래된 소유자의 쓰기를 거부하는 설계가 필요합니다.

### DB-12. Lost Update와 격리 수준의 한계

**면접 답변:** Lost Update는 두 트랜잭션이 같은 기존 값을 읽고 각각 계산한 결과를 덮어써 한쪽 변경이 사라지는 현상입니다. READ COMMITTED나 스냅샷 기반 REPEATABLE READ에서 애플리케이션이 읽고 계산한 뒤 단순 UPDATE하면 발생할 수 있습니다. 격리 수준 이름만으로 애플리케이션의 Read-Modify-Write 전체가 하나의 원자 연산이 되지는 않기 때문입니다.

### DB-13. Lost Update 해결

**면접 답변:** `UPDATE stock SET quantity = quantity - 1 WHERE ...`처럼 계산을 원자적 SQL로 수행하거나, `WHERE version = ?` 조건과 버전 증가를 이용한 낙관적 락을 씁니다. 충돌이 많으면 `SELECT ... FOR UPDATE`로 행을 잠그고 갱신할 수 있습니다. 영향받은 행 수를 확인하고, 낙관적 충돌이나 데드락은 제한된 횟수로 재시도합니다.

## 3.3 인덱스

### DB-14. 인덱스의 장단점

**면접 답변:** 인덱스는 검색 키와 행 위치를 정렬된 별도 구조에 저장해 전체 테이블을 읽지 않고 원하는 행을 찾게 합니다. 조회, 정렬, 조인을 빠르게 할 수 있지만 추가 저장 공간이 필요하고 INSERT/UPDATE/DELETE 때 인덱스도 갱신해야 합니다. 선택도가 낮거나 많은 행을 읽는 쿼리는 인덱스 탐색보다 순차 스캔이 더 나을 수 있습니다.

### DB-15. Hash보다 B-Tree 계열을 쓰는 이유

**면접 답변:** Hash는 동등 비교에는 빠르지만 키 순서를 보존하지 않아 범위 검색, 정렬, 접두 조건에 약합니다. B+Tree는 균형 트리라 탐색 높이가 낮고, 한 노드에 많은 키를 담아 디스크 페이지 I/O를 줄입니다. Leaf가 정렬되고 서로 연결되어 범위 스캔도 효율적이어서 범용 DB 인덱스에 적합합니다.

### DB-16. 인덱스 동작

**면접 답변:** 쿼리 조건의 키를 루트 페이지부터 비교해 알맞은 자식 페이지로 내려가 Leaf에서 후보를 찾습니다. 이후 커버링 인덱스면 인덱스만으로 결과를 반환하고, 아니면 행을 저장한 페이지를 추가로 읽습니다. 옵티마이저는 통계로 예상 행 수와 비용을 계산해 인덱스 스캔, 테이블 스캔, 조인 순서를 선택합니다.

### DB-17. 클러스터링과 비클러스터링 인덱스

**면접 답변:** 클러스터링 인덱스는 Leaf에 실제 행 데이터가 저장되거나 행의 물리적 배치를 결정하므로 테이블당 보통 하나입니다. 비클러스터링, 즉 보조 인덱스는 별도 정렬 구조에 키와 행을 찾기 위한 포인터를 저장해 여러 개 만들 수 있습니다. 클러스터 키 범위 조회는 유리하지만, 클러스터 키가 크거나 자주 바뀌면 모든 보조 인덱스와 페이지 배치에 부담이 됩니다.

### DB-18. InnoDB 보조 인덱스

**면접 답변:** InnoDB의 보조 인덱스 Leaf는 실제 행 주소 대신 보조 키와 Primary Key 값을 저장합니다. 필요한 컬럼이 보조 인덱스에 모두 있으면 바로 반환하지만, 아니면 얻은 Primary Key로 클러스터링 인덱스를 다시 탐색합니다. 이를 흔히 Double Lookup이라고 하며, Primary Key가 크면 모든 보조 인덱스도 커집니다.

### DB-19. 복합 인덱스 주의점

**면접 답변:** `(a, b, c)` 인덱스는 정렬 순서 때문에 보통 왼쪽부터 이어지는 조건이 중요합니다. 선행 컬럼을 빼거나 범위 조건 이후 컬럼을 쓰면 탐색 범위 축소에 충분히 활용하지 못할 수 있습니다. 실제 쿼리의 동등 조건, 범위, 정렬, 선택도와 커버링 가능성을 보고 순서를 정하고, 중복 인덱스로 쓰기 비용을 늘리지 않아야 합니다.

### DB-20. Boolean 컬럼 인덱스

**면접 답변:** Boolean은 값 종류가 두 개라 단독 선택도가 낮아 많은 행을 읽는 쿼리에서는 인덱스 이점이 작을 가능성이 큽니다. 하지만 한 값이 매우 희소하거나, 다른 컬럼과 결합한 복합 인덱스·부분 인덱스로 자주 쓰는 소수 행만 찾는다면 효과적일 수 있습니다. 분포, 쿼리 빈도, 반환 행 수를 확인하고 실행 계획과 부하 테스트로 결정합니다.

### DB-21. LIKE와 인덱스

**면접 답변:** B+Tree는 문자열이 앞에서부터 정렬돼 있어 `LIKE 'abc%'`는 `abc` 이상 특정 상한 미만의 연속 범위로 바꿔 탐색할 수 있습니다. `LIKE '%abc%'`는 시작 문자가 무엇이든 될 수 있어 일치 값이 트리 전체에 흩어집니다. 중간 문자열 검색이 핵심이면 Full-Text, N-gram, 검색 엔진 같은 별도 구조를 고려합니다.

## 3.4 RDBMS와 NoSQL

### DB-22. RDBMS와 NoSQL

**면접 답변:** RDBMS는 정해진 스키마, 관계, 조인, 트랜잭션과 SQL이 강점이라 데이터 정합성과 복합 조회가 중요한 업무에 적합합니다. NoSQL은 Key-Value, Document, Wide-Column, Graph처럼 목적별 모델을 사용하고, 비정형 데이터와 특정 접근 패턴, 수평 확장에 최적화하기 쉽습니다. “NoSQL이 더 빠르다”가 아니라 일관성 요구, 조회 패턴, 확장 방식, 운영 역량을 기준으로 선택합니다.

### DB-23. 모델링 방식의 차이

**면접 답변:** RDBMS는 중복을 줄이는 정규화와 관계를 중심으로 모델링하고, 필요한 시점에 조인합니다. Document 계열 NoSQL은 주요 조회를 한 번에 처리하도록 관련 데이터를 함께 넣고 의도적인 중복을 허용하는 경우가 많습니다. 따라서 NoSQL은 데이터 자체보다 먼저 접근 패턴과 파티션 키를 설계하고, 중복 데이터 갱신의 일관성 비용을 감수합니다.

### DB-24. RDBMS의 Scale-Out

**면접 답변:** 가능합니다. 읽기는 Read Replica로 분산하고, 데이터는 Sharding으로 여러 노드에 나눌 수 있으며, 분산 SQL DB를 선택할 수도 있습니다. 다만 노드 간 조인, 전역 유일성, 분산 트랜잭션, 리샤딩과 장애 조치가 복잡해집니다. 먼저 인덱스·쿼리·캐시·수직 확장을 최적화하고 병목과 성장 규모가 정당할 때 수평 확장을 도입합니다.

### DB-25. NoSQL이 Scale-Out에 유리한 이유

**면접 답변:** 많은 NoSQL은 처음부터 파티션 키를 기준으로 데이터를 독립 배치하고, 제한된 조인과 완화 가능한 일관성 모델을 채택해 노드 간 조정을 줄입니다. 복제와 파티션 이동도 제품에 내장된 경우가 많습니다. 하지만 잘못된 파티션 키는 Hot Partition을 만들고, 강한 트랜잭션이나 전역 조회를 요구하면 장점이 줄어듭니다.

### DB-26. MySQL과 PostgreSQL

**면접 답변:** 둘 다 성숙한 오픈소스 RDBMS지만 PostgreSQL은 풍부한 SQL 기능, 확장 타입·인덱스, 엄격한 표준 준수와 복잡한 질의에 강한 편입니다. MySQL, 특히 InnoDB는 넓은 생태계와 단순 읽기 중심 웹 서비스 운영 경험이 풍부합니다. MVCC, 복제, 인덱스, JSON 구현과 운영 도구가 다르므로 팀 역량과 실제 워크로드로 선택해야 하며 단순 우열로 답하지 않습니다.

### DB-27. CAP 이론

**면접 답변:** 분산 시스템에 네트워크 파티션이 발생했을 때 선형화 가능한 일관성(Consistency)과 모든 정상 노드 요청에 응답하는 가용성(Availability)을 동시에 완전히 보장할 수 없다는 이론입니다. Partition Tolerance는 분산 환경에서 선택 옵션이라기보다 견뎌야 하는 조건입니다. 따라서 파티션 동안 일부 요청을 거부해 C를 지킬지, 오래된 값 가능성을 감수하고 A를 지킬지 결정합니다.

### DB-28. C와 A의 선택 기준

**면접 답변:** 잔액·재고 확정·권한처럼 잘못된 값으로 진행하는 피해가 크면 일관성을 우선하고 실패나 대기를 허용합니다. 피드·추천·일부 조회처럼 잠시 오래된 값이 보여도 서비스 지속이 중요하면 가용성을 우선할 수 있습니다. 시스템 전체를 하나로 고르기보다 업무 연산별 허용 가능한 오류, 복구 방식, RPO/RTO를 기준으로 결정합니다.

## 3.5 커넥션과 커넥션 풀

### DB-29. DB 커넥션과 생성 비용

**면접 답변:** DB 커넥션은 애플리케이션과 DB 서버 사이의 상태 있는 통신 세션입니다. TCP 연결, 필요하면 TLS handshake, 인증, 세션 상태 초기화와 서버 측 메모리·스레드/프로세스 자원 할당이 필요해 매 쿼리마다 만들기 비쌉니다. 네트워크 왕복과 DB의 최대 연결 수도 비용에 포함됩니다.

### DB-30. Connection Pool

**면접 답변:** Connection Pool은 일정 수의 DB 커넥션을 미리 만들고 요청이 빌렸다가 반환하도록 재사용하는 구조입니다. 연결 생성 지연을 줄이고 동시에 DB에 들어가는 작업 수를 제한해 DB를 보호합니다. 유휴·최대 크기, 획득 타임아웃, 최대 수명, 유효성 검사를 설정하고 반드시 닫기 구문으로 반환해야 합니다.

### DB-31. Pool 크기는 클수록 좋은가

**면접 답변:** 아닙니다. DB가 동시에 효율적으로 처리할 수 있는 수를 넘으면 CPU 경합, 메모리 사용, 락 대기와 컨텍스트 스위칭이 늘어 오히려 느려집니다. 애플리케이션 인스턴스 수까지 곱한 총 연결 수가 DB 한도 안에 있어야 합니다. DB 처리 시간, 요청 동시성, 대기 시간, CPU·I/O 병목을 측정해 작은 값부터 조정하고 대기 큐로 Backpressure를 줍니다.

### DB-32. Connection Timeout과 Read Timeout

**면접 답변:** Connection Timeout은 DB나 서버와 연결을 맺는 데 허용하는 시간이고, Read Timeout은 연결 후 요청을 보낸 뒤 응답 데이터를 기다리는 시간입니다. 무한 대기는 스레드·커넥션 풀을 소진해 작은 장애를 전체 장애로 키우므로 타임아웃이 필요합니다. 작업의 정상 지연 분포와 사용자 시간 예산에 맞추고, 재시도는 멱등성·지수 백오프·전체 마감 시간을 함께 설계합니다.

### DB-33. Connection Pool 모니터링

**면접 답변:** 활성·유휴·대기 커넥션 수, Pool 획득 대기 시간과 타임아웃, 생성·폐기율, 커넥션 사용 시간을 봅니다. 활성 수가 최대에 붙고 대기가 늘면 누수, Slow Query, 긴 트랜잭션, DB 지연을 구분해야 합니다. 애플리케이션 스레드 덤프, 쿼리 로그, DB 세션/락 대기와 같은 시각의 지표를 연관 분석합니다.

## 3.6 운영과 장애 대응

### DB-34. Slow Query 대응

**면접 답변:** 먼저 사용자 영향과 최근 변경을 확인하고, 해당 쿼리의 빈도·지연·대기 원인을 식별합니다. 실행 계획, 실제 반환 행 수, 스캔 행 수, 인덱스, 통계, 락 대기, I/O와 버퍼 캐시를 확인합니다. 긴급 시 문제 트래픽 제한이나 안전한 쿼리 중단으로 확산을 막고, 이후 쿼리/인덱스/모델을 개선해 실제 데이터 규모로 검증하며 재발 모니터링을 추가합니다.

### DB-35. EXPLAIN에서 볼 것

**면접 답변:** 접근 방식이 전체 스캔인지 인덱스 탐색인지, 사용·후보 인덱스, 조인 순서와 방식, 예상 행 수, 필터 비율, 정렬·임시 테이블 여부를 봅니다. 가능하면 `EXPLAIN ANALYZE`로 예상과 실제 행 수·시간 차이를 확인해 통계 오류나 데이터 편향을 찾습니다. “인덱스를 탔다”만 보지 말고 실제로 읽은 행과 반복 횟수, 최종 지연을 확인합니다.

### DB-36. 데이터 증가에 따른 성능 저하 해결

**면접 답변:** 먼저 쿼리와 실행 계획을 측정해 불필요한 컬럼·행 조회, N+1, 잘못된 인덱스와 정렬을 개선합니다. 그다음 캐시, 요약/비정규화, 오래된 데이터 아카이빙, 파티셔닝, 읽기 복제를 검토합니다. 단일 노드의 한계를 실제로 확인한 뒤 Sharding을 고려하며, 각 단계에서 쓰기 비용과 일관성·운영 복잡성의 대가를 평가합니다.

### DB-37. Clustering, Replication, Sharding

**면접 답변:** Clustering은 여러 노드를 하나의 DB 서비스처럼 묶어 가용성이나 처리 능력을 제공하는 넓은 개념입니다. Replication은 같은 데이터를 여러 노드에 복사해 읽기 확장과 장애 대비를 얻습니다. Sharding은 서로 다른 데이터 부분을 여러 노드에 나눠 저장 용량과 쓰기 부하를 분산합니다. 복제는 동일 데이터의 사본, 샤딩은 데이터의 분할이라는 차이가 핵심입니다.

### DB-38. Replication 동작

**면접 답변:** Primary가 변경 사항을 WAL이나 Binlog 같은 순서 있는 로그에 기록하고, Replica가 이를 전송받아 같은 순서로 적용합니다. 동기 복제는 커밋 전에 Replica 확인을 기다려 데이터 유실 가능성을 줄이지만 지연과 가용성 비용이 있고, 비동기 복제는 빠르지만 지연과 장애 시 유실 가능성이 있습니다. Replica Lag과 읽기 후 쓰기 일관성 문제를 고려해야 합니다.

### DB-39. DB 데드락

**면접 답변:** 두 트랜잭션이 서로 상대가 가진 락을 기다리는 순환 대기 상태입니다. 예를 들어 A가 주문 1 후 주문 2를, B가 주문 2 후 주문 1을 잠그면 생깁니다. DB는 보통 대기 그래프를 감지해 비용이 작은 트랜잭션 하나를 희생시켜 롤백합니다.

### DB-40. 데드락 감지와 대처

**면접 답변:** DB의 Deadlock Log와 희생된 트랜잭션 오류, Lock Wait 지표로 감지합니다. 애플리케이션은 해당 오류를 구분해 짧은 지수 백오프로 전체 트랜잭션을 재시도할 수 있어야 합니다. 근본적으로는 행 접근 순서를 통일하고, 인덱스로 잠금 범위와 트랜잭션 시간을 줄이며, 불필요한 사용자 상호작용을 트랜잭션 밖으로 뺍니다.

### DB-41. DB 장애 접근 순서

**면접 답변:** 먼저 영향 범위와 시작 시각, 오류율·지연을 확인하고 변경 작업을 멈춰 상황을 안정화합니다. 애플리케이션 문제인지 DB 자체인지, 연결 고갈·Slow Query·락·CPU·I/O·복제 지연 중 어디가 병목인지 지표와 로그로 좁힙니다. 읽기 전용 전환, 트래픽 제한, Failover 같은 가장 안전한 완화책을 적용하고 데이터 정합성을 확인한 뒤 원인을 수정하고 재발 방지 조치를 남깁니다.

### DB-42. 주요 DB 모니터링 메트릭

**면접 답변:** 사용자 관점의 쿼리 지연 백분위, 처리량, 오류와 타임아웃을 먼저 봅니다. 자원은 CPU, 메모리, 디스크 IOPS·지연, 버퍼 캐시 적중률, 연결·대기 큐를 보고, DB 내부는 Slow Query, Lock Wait/Deadlock, 긴 트랜잭션, 로그 증가를 봅니다. 복제 환경은 Replica Lag과 적용 상태, 저장 용량과 증가율도 중요합니다.

# 4. 네트워크 & 웹

## 4.1 브라우저 요청 흐름

### NET-01. 브라우저에서 URL에 접속하는 전체 흐름

**면접 답변:** 브라우저는 URL을 해석하고 캐시와 보안 정책을 확인한 뒤 DNS로 도메인의 IP를 찾습니다. 대상과 TCP 연결을 맺고 HTTPS라면 TLS handshake로 서버 인증과 세션 키 합의를 합니다. HTTP 요청을 보내면 CDN·로드 밸런서·웹 서버·애플리케이션이 처리해 응답하고, 브라우저는 HTML을 파싱해 DOM을 만들며 CSS와 JavaScript 등 추가 자원을 요청해 화면을 렌더링합니다. HTTP/3라면 TCP 대신 QUIC을 사용한다는 차이가 있습니다.

### NET-02. 패킷 관점의 요청 흐름

**면접 답변:** 로컬 DNS 캐시에 없으면 DNS 질의 패킷으로 IP를 얻습니다. 목적지가 다른 네트워크라면 ARP/Neighbor Discovery로 기본 게이트웨이의 링크 계층 주소를 찾고, IP 패킷을 라우터들로 전달합니다. TCP라면 SYN, SYN-ACK, ACK로 연결하고 TLS 메시지 뒤 암호화된 HTTP 데이터를 세그먼트로 나눠 보냅니다. 각 구간의 링크 계층 프레임 주소는 바뀔 수 있지만 종단 IP와 포트로 연결을 식별하며, NAT가 있으면 경계에서 주소와 포트가 변환됩니다.

## 4.2 TCP / UDP

### NET-03. TCP의 장단점

**면접 답변:** TCP는 연결 지향 바이트 스트림 프로토콜로 순서 보장, 오류 검출, 재전송, 흐름 제어와 혼잡 제어를 제공합니다. 애플리케이션이 신뢰성 로직을 직접 만들 필요가 적지만 연결 설정과 상태 관리, 헤더·재전송 비용이 있고 메시지 경계를 보존하지 않습니다. 웹, DB처럼 정확하고 순서 있는 전달이 중요한 통신에 적합합니다.

### NET-04. UDP와 TCP의 차이

**면접 답변:** UDP는 연결 설정 없이 독립된 Datagram을 보내며 전달·순서·중복 제거를 보장하지 않습니다. 헤더와 상태가 작고 애플리케이션이 필요한 신뢰성만 선택할 수 있어 DNS, 실시간 미디어, 게임 등에 적합합니다. TCP는 신뢰성과 혼잡 제어를 기본 제공하지만 지연과 Head-of-Line Blocking 비용이 있습니다. QUIC처럼 UDP 위에서 신뢰성과 암호화를 구현한 프로토콜도 있습니다.

### NET-05. 3-way / 4-way handshake

**면접 답변:** 연결 시 클라이언트가 초기 순서 번호를 담은 SYN, 서버가 자신의 SYN과 클라이언트 번호 확인 ACK, 클라이언트가 서버 번호 확인 ACK를 보내 양쪽 송수신 준비를 확인합니다. 종료는 한쪽의 FIN과 상대 ACK, 반대쪽 FIN과 마지막 ACK로 각 방향을 독립적으로 닫아 일반적으로 네 단계입니다. 마지막 ACK를 보낸 쪽은 지연 패킷이 새 연결을 방해하지 않고 ACK 유실 시 재전송에 답할 수 있도록 TIME_WAIT에 머뭅니다.

### NET-06. TCP 신뢰성과 혼잡 제어

**면접 답변:** TCP는 Sequence Number와 Checksum으로 순서와 손상을 확인하고, ACK·타이머·중복 ACK를 이용해 유실 데이터를 재전송합니다. 수신 측의 Receive Window로 처리 가능한 양을 맞추는 것이 흐름 제어입니다. 혼잡 제어는 네트워크가 감당할 양을 추정해 Congestion Window를 조절하며 Slow Start, Congestion Avoidance, Fast Retransmit/Recovery 같은 알고리즘을 사용합니다.

### NET-07. TCP/IP와 OSI 7계층

**면접 답변:** OSI 7계층은 통신 기능을 물리, 데이터 링크, 네트워크, 전송, 세션, 표현, 응용으로 설명하는 개념 모델입니다. 실무 TCP/IP 모델은 보통 링크, 인터넷, 전송, 응용의 4계층으로 묶습니다. HTTP는 응용, TCP/UDP는 전송, IP는 인터넷, Ethernet/Wi-Fi는 링크 계층에 대응하며 실제 프로토콜 경계가 OSI와 항상 정확히 일치하는 것은 아닙니다.

## 4.3 DNS

### NET-08. DNS와 도메인 접속

**면접 답변:** DNS는 사람이 읽는 도메인을 IP 주소 등 리소스 레코드로 바꾸는 분산 계층형 시스템입니다. 브라우저·OS·로컬 Resolver 캐시에 없으면 재귀 Resolver가 Root, TLD, Authoritative Name Server를 차례로 조회해 답을 얻고 TTL 동안 캐시합니다. 브라우저는 반환된 주소 중 하나로 연결을 시도합니다.

### NET-09. DNS가 UDP를 주로 쓰는 이유

**면접 답변:** 일반 DNS 질의/응답은 작고 한 번의 요청-응답으로 끝나는 경우가 많아 연결 설정 없는 UDP가 지연과 서버 상태 비용이 적습니다. 응답이 잘리면 TCP로 재시도할 수 있고, Zone Transfer는 TCP를 사용합니다. 오늘날에는 보안과 프라이버시를 위해 TCP/TLS 기반 DoT나 HTTPS 기반 DoH도 사용하므로 “DNS는 항상 UDP”는 아닙니다.

### NET-10. DNS 서버와 레코드

**면접 답변:** 재귀 Resolver는 클라이언트를 대신해 답을 찾고, Root와 TLD 서버는 다음 권한 서버 위치를 알려주며, Authoritative 서버가 도메인의 최종 레코드를 제공합니다. A는 이름을 IPv4 주소에, AAAA는 IPv6 주소에, CNAME은 다른 정식 이름에 연결합니다. TXT는 소유권 검증, SPF 같은 임의 텍스트 정책에 사용합니다. 역할별 레코드로 나누면 주소·별칭·메일·검증 정보를 독립 관리할 수 있습니다.

## 4.4 HTTP

### NET-11. HTTP와 동작 방식

**면접 답변:** HTTP는 클라이언트와 서버가 자원의 표현과 명령을 요청·응답 메시지로 주고받는 응용 계층 프로토콜입니다. 요청은 Method, Target, Header, 선택적 Body로, 응답은 Status, Header, Body로 구성됩니다. 전송에는 버전에 따라 TCP 또는 QUIC을 사용하며, 캐시·프록시·콘텐츠 협상 같은 웹 중간 계층을 지원합니다.

### NET-12. 비연결성과 무상태

**면접 답변:** HTTP의 무상태성은 각 요청이 처리에 필요한 정보를 담고 서버가 이전 요청 문맥에 의존하지 않는다는 의미입니다. 덕분에 서버 확장과 장애 복구가 쉬워집니다. 비연결성은 요청 사이에 애플리케이션 수준 연결을 영구 점유하지 않는 성격을 말하지만, 실제 HTTP/1.1 이후에는 성능을 위해 TCP 연결을 재사용합니다. 로그인 같은 상태는 쿠키나 토큰으로 요청마다 식별자를 전달해 별도 저장소와 연결합니다.

### NET-13. HTTP 버전 비교

**면접 답변:** HTTP/1.0은 보통 요청마다 연결했고, 1.1은 Persistent Connection과 Pipelining, Host 헤더를 표준화했습니다. HTTP/2는 하나의 TCP 연결에서 여러 Stream을 Multiplexing하고 헤더를 HPACK으로 압축하지만 TCP 패킷 손실 시 모든 Stream이 전송 계층에서 기다릴 수 있습니다. HTTP/3는 UDP 기반 QUIC을 사용해 Stream별 손실 처리를 분리하고 연결 설정을 줄이며 TLS 1.3을 통합합니다.

### NET-14. GET, POST, PUT, PATCH

**면접 답변:** GET은 자원 조회이며 Safe하고 멱등이어야 합니다. POST는 서버가 정한 의미로 처리하거나 하위 자원을 생성하며 기본적으로 멱등을 보장하지 않습니다. PUT은 지정한 URI의 자원 표현 전체를 생성 또는 교체하는 의미라 멱등이고, PATCH는 자원의 일부 변경을 표현하며 문서 설계에 따라 멱등일 수도 아닐 수도 있습니다. 차이는 Body 유무가 아니라 의미와 계약입니다.

### NET-15. 멱등성

**면접 답변:** 같은 요청을 한 번 보내든 여러 번 보내든 서버의 의도된 최종 상태가 같다면 멱등입니다. GET, PUT, DELETE는 의미상 멱등이고 POST는 일반적으로 아닙니다. 네트워크 타임아웃 후 클라이언트나 프록시가 안전하게 재시도할 수 있는지 판단하는 기준이라 중요하며, 결제 같은 POST는 Idempotency Key로 중복 처리를 막기도 합니다.

## 4.5 HTTPS

### NET-16. HTTPS와 HTTP의 차이

**면접 답변:** HTTPS는 HTTP를 TLS로 보호해 전송 내용의 기밀성, 변조 탐지, 서버 신원 인증을 제공합니다. HTTP 메시지 의미는 같지만 네트워크에서 Header와 Body가 암호화됩니다. 다만 접속 IP, 일부 연결 메타데이터까지 모두 숨기는 것은 아니며, HTTPS 자체가 애플리케이션의 인증·권한 검사나 안전한 입력 검증을 대신하지 않습니다.

### NET-17. TLS Handshake

**면접 답변:** 현대적인 TLS 1.3 기준으로 클라이언트는 지원 버전·암호군과 임시 공개키를 보내고, 서버는 선택 결과·임시 공개키·인증서와 인증서 개인키로 만든 서명을 보냅니다. 클라이언트는 CA 신뢰 사슬, 도메인, 유효 기간과 서명을 검증합니다. 양쪽은 Ephemeral Diffie-Hellman 결과에서 같은 세션 키를 만들고 Finished 메시지로 handshake 무결성을 확인한 뒤 대칭 키로 HTTP 데이터를 암호화합니다. 인증서의 공개키로 대용량 데이터를 직접 암호화하는 것이 아닙니다.

### NET-18. 대칭 키와 비대칭 키

**면접 답변:** 대칭 키 암호화는 같은 비밀키로 암복호화해 빠르지만 키를 안전하게 공유하기 어렵습니다. 비대칭 키는 공개키와 개인키 쌍을 사용해 키 합의·서명·신원 증명에 유리하지만 계산 비용이 큽니다. TLS는 비대칭 기술로 상대를 인증하고 공유 비밀을 합의한 뒤, 실제 데이터는 빠른 대칭 키로 암호화하는 혼합 방식을 씁니다.

### NET-19. CA 인증서와 Let's Encrypt

**면접 답변:** CA 인증서는 신뢰받는 인증 기관이 특정 공개키와 도메인의 연결을 서명한 전자 문서입니다. 브라우저는 운영체제나 브라우저의 Root CA 목록부터 인증서 체인을 검증합니다. Let's Encrypt는 무료이고 자동화된 DV 인증서를 발급하는 공개 CA이므로 개념적으로 별도 방식이 아니라 CA의 한 종류입니다. 유료 여부가 암호화 강도를 결정하지는 않습니다.

## 4.6 REST API & CORS

### NET-20. RESTful API

**면접 답변:** REST는 자원을 URI로 식별하고, 표준 HTTP 메서드와 표현을 통해 상태를 전이하며, 요청을 무상태로 처리하는 아키텍처 스타일입니다. RESTful한 API는 동사형 URL보다 자원 중심 URI를 쓰고, 메서드 의미·상태 코드·캐시 가능성을 일관되게 지킵니다. 엄밀한 REST에는 계층화, 캐시, Uniform Interface와 HATEOAS 제약도 있지만 실무에서는 HTTP 자원 API를 넓게 REST API라 부르기도 합니다.

### NET-21. REST와 gRPC

**면접 답변:** 일반적인 REST API는 HTTP와 JSON을 사용해 사람이 읽기 쉽고 브라우저·외부 공개 API 생태계가 넓습니다. gRPC는 Protocol Buffers로 계약과 코드를 생성하고 HTTP/2 위에서 효율적인 바이너리 직렬화와 양방향 Streaming을 제공합니다. 내부 마이크로서비스 간 낮은 지연, 강한 스키마, 다중 언어 코드 생성이 중요하면 gRPC가 유리하고, 브라우저 공개성과 디버깅 편의가 중요하면 REST가 단순합니다.

### NET-22. SOP와 CORS

**면접 답변:** SOP(Same-Origin Policy)는 브라우저가 출처가 다른 응답을 스크립트에서 함부로 읽지 못하게 하는 보안 정책입니다. 출처는 Scheme, Host, Port 조합입니다. CORS는 서버가 `Access-Control-Allow-*` 응답 헤더로 허용할 출처·메서드·헤더를 브라우저에 알려 SOP의 예외를 안전하게 여는 규약입니다. 서버 간 요청을 막는 방화벽이나 인증 기능은 아닙니다.

### NET-23. Simple Request와 Preflight

**면접 답변:** 제한된 Method, Header, Content-Type 조건을 만족하는 Cross-Origin 요청은 브라우저가 본 요청을 바로 보내고 응답의 CORS 헤더를 검사합니다. 그 밖의 요청은 먼저 OPTIONS Preflight로 실제 Method와 Header가 허용되는지 확인한 뒤 본 요청을 보냅니다. Simple Request도 전송 자체는 될 수 있으므로 서버는 CSRF와 권한 검사를 별도로 해야 합니다.

## 4.7 인증과 인가

### NET-24. 무상태 HTTP에서 로그인 유지

**면접 답변:** 로그인 성공 후 서버가 세션 ID나 서명된 토큰 같은 자격 정보를 발급하고, 브라우저는 보통 Cookie 또는 Authorization Header로 매 요청에 전달합니다. 세션 방식은 서버 저장소에서 상태를 조회하고, 토큰 방식은 서명과 만료·클레임을 검증합니다. 즉 HTTP 자체를 상태 있게 바꾸는 것이 아니라 각 요청이 상태를 찾거나 검증할 열쇠를 들고 오는 방식입니다.

### NET-25. 인증과 인가

**면접 답변:** 인증(Authentication)은 “누구인가”를 증명하는 과정이고, 인가(Authorization)는 인증된 주체가 “이 행동을 해도 되는가”를 판단하는 과정입니다. 로그인과 토큰 검증이 인증의 예이고, 관리자만 사용자 삭제를 허용하는 것이 인가입니다. 인증에 성공했다고 모든 자원에 접근할 수 있는 것은 아니며, 인가는 서버에서 매 요청의 자원과 행위 기준으로 확인해야 합니다.

### NET-26. 쿠키와 세션

**면접 답변:** Cookie는 브라우저가 도메인 규칙에 따라 저장하고 요청에 자동 첨부하는 작은 데이터 전달 수단이고, Session은 보통 서버가 로그인 상태를 저장하고 Cookie에는 예측 불가능한 Session ID만 두는 방식입니다. `HttpOnly`, `Secure`, `SameSite`, 짧은 만료와 ID 회전으로 위험을 줄입니다. 세션은 서버에서 즉시 폐기하기 쉽지만 저장소와 확장 설계가 필요하고, Cookie 자동 전송 때문에 CSRF 방어가 필요합니다.

### NET-27. JWT와 Access/Refresh Token

**면접 답변:** JWT는 Base64URL로 인코딩한 Header, Payload, Signature 세 부분으로 구성됩니다. 서명은 변조를 검출하지만 Payload를 암호화하지 않으므로 민감 정보를 넣지 않습니다. 짧은 Access Token은 API 접근에 쓰고, 긴 Refresh Token은 새 Access Token 발급에만 사용해 Access Token 탈취 피해 시간을 줄입니다. Refresh Token은 더 안전하게 저장하고 회전·폐기할 수 있어야 합니다.

### NET-28. JWT 탈취 대응과 탐지

**면접 답변:** Access Token은 짧게 만료시키고 HTTPS와 안전한 저장소를 사용하며, Refresh Token Rotation과 재사용 탐지를 적용합니다. 탈취가 의심되면 해당 Token Family나 사용자 세션을 폐기하고 재인증시키며 키 유출이면 Signing Key도 교체합니다. 탐지는 이미 사용된 Refresh Token 재사용, 비정상 지역·기기·속도, 동시 세션 패턴 같은 위험 신호를 조합하되 IP만으로 확정하지 않습니다.

### NET-29. 서버 저장 Refresh Token과 Session의 차이

**면접 답변:** 둘 다 서버 상태를 조회한다는 점에서는 비슷합니다. 차이는 Session ID가 매 요청의 인증 상태를 가리키는 경우가 많고, Refresh Token은 드물게 Access Token을 재발급하는 용도라 일반 API 요청은 자체 검증 가능한 Access Token으로 처리한다는 점입니다. 따라서 즉시 폐기와 확장성의 균형이 다르지만, 서버 저장소를 쓰는 순간 “완전한 무상태”라는 주장은 할 수 없습니다.

### NET-30. OAuth 2.0

**면접 답변:** OAuth 2.0은 사용자가 비밀번호를 애플리케이션에 주지 않고도 특정 자원 접근 권한을 위임하는 프레임워크입니다. Authorization Code Flow에서는 클라이언트가 사용자를 Authorization Server로 보내 동의를 받고 Code를 받은 뒤, 백채널에서 Code와 PKCE 검증값으로 Access Token을 교환합니다. 그 토큰으로 Resource Server를 호출합니다. OAuth는 본래 인가이며 로그인 신원 정보는 OpenID Connect가 보완합니다.

### NET-31. SSO와 OAuth 2.0의 관계

**면접 답변:** SSO는 한 번 인증한 사용자가 여러 애플리케이션에 다시 로그인하지 않고 접근하는 사용자 경험과 구조입니다. 중앙 Identity Provider가 인증 상태를 가지고 각 서비스에 신뢰 가능한 증명을 전달합니다. OAuth 2.0 자체는 권한 위임 규약이며, SSO 로그인에는 보통 OAuth 위에 신원 계층을 추가한 OpenID Connect나 SAML을 사용합니다.

## 4.8 실시간 통신

### NET-32. WebSocket

**면접 답변:** WebSocket은 하나의 연결에서 클라이언트와 서버가 서로 독립적으로 메시지를 보낼 수 있는 전이중 통신 프로토콜입니다. HTTP/1.1에서는 Upgrade handshake로 시작해 서버가 `101 Switching Protocols`로 수락하면 WebSocket Frame을 주고받습니다. 반복 HTTP 요청보다 양방향 실시간 통신 오버헤드가 작지만, 오래 열린 연결의 상태·인증 갱신·Backpressure·수평 확장을 관리해야 합니다.

### NET-33. Ping/Pong과 STOMP

**면접 답변:** WebSocket Ping/Pong Control Frame은 연결이 살아 있는지 확인하고 중간 장비의 유휴 타임아웃을 감지하는 데 사용합니다. STOMP는 WebSocket 위에서 Destination, Subscribe, Send, Ack 같은 메시징 의미를 제공하는 상위 프로토콜입니다. WebSocket 자체는 전송 Frame만 정의하므로 채팅방·구독 같은 애플리케이션 규칙은 직접 만들거나 STOMP 같은 규약을 사용해야 합니다.

### NET-34. SSE와 WebSocket

**면접 답변:** SSE(Server-Sent Events)는 서버가 하나의 HTTP 연결로 `text/event-stream` 형식의 이벤트를 클라이언트에 계속 보내는 단방향 방식입니다. 브라우저의 `EventSource`는 재연결과 Last-Event-ID를 지원하고 일반 HTTP 인프라와 잘 맞습니다. 서버→클라이언트 알림만 필요하면 단순하지만, 양방향·바이너리·낮은 지연의 빈번한 상호 통신에는 WebSocket이 적합합니다.

### NET-35. Polling, Long Polling, SSE

**면접 답변:** Polling은 일정 주기로 새 데이터 여부를 물어 단순하지만 빈 응답과 지연이 생깁니다. Long Polling은 서버가 데이터가 생길 때까지 응답을 보류하고 응답 후 다시 연결해 요청 수를 줄이지만 연결 재설정 비용이 있습니다. SSE는 한 HTTP 응답을 유지하며 이벤트를 연속 전송하고, 끊기면 `retry`와 Last-Event-ID를 이용해 재연결합니다. 연결 종료 감지, Heartbeat, 이벤트 유실·중복 처리와 프록시 버퍼링을 함께 설계해야 합니다.

# 5. Redis

## 5.1 구조와 실행 원리

### REDIS-01. Redis와 사용 상황

**면접 답변:** Redis는 메모리를 중심으로 동작하는 Key-Value 데이터 구조 서버입니다. 매우 빠른 읽기·쓰기와 TTL, 원자적 명령을 제공해 캐시, 세션, Rate Limit, 순위, 분산 조정, 가벼운 메시징에 사용합니다. 다만 메모리 비용, 제한된 쿼리 모델, 비동기 복제 중 유실 가능성이 있으므로 모든 데이터의 원본 DB로 무조건 선택하지는 않습니다.

### REDIS-02. 주요 자료 구조

**면접 답변:** String은 캐시·카운터, Hash는 객체 필드, List는 양끝 큐, Set은 중복 없는 집합, Sorted Set은 점수 기반 순위에 적합합니다. Bitmap은 많은 Boolean 상태, HyperLogLog는 오차를 허용한 고유 개수 추정, Stream은 저장되는 이벤트 로그와 Consumer Group에 사용합니다. 구조 이름보다 필요한 연산과 시간복잡도를 기준으로 고릅니다.

### REDIS-03. 단일 스레드인데 빠른 이유

**면접 답변:** 핵심 명령 실행이 주로 한 스레드라 공유 자료 구조를 위한 락과 컨텍스트 스위칭이 적고, 데이터가 메모리에 있어 디스크 대기보다 훨씬 짧기 때문입니다. 이벤트 루프와 I/O Multiplexing으로 많은 연결을 처리하고 자료 구조 구현도 효율적입니다. 다만 큰 Key 연산이나 오래 걸리는 명령 하나가 다른 요청을 막을 수 있으며, 최근 버전은 네트워크 I/O 등의 일부 작업에 별도 스레드를 사용합니다.

### REDIS-04. 이벤트 루프와 I/O Multiplexing

**면접 답변:** Redis는 `epoll`이나 `kqueue` 같은 OS 기능으로 많은 소켓 중 읽고 쓸 준비가 된 연결만 이벤트로 받습니다. 한 연결을 기다리며 스레드를 막지 않고, 준비된 요청을 짧게 처리한 뒤 다음 이벤트로 넘어갑니다. 연결 수만큼 스레드를 만들 필요가 없지만 명령 실행이 오래 걸리면 이벤트 루프 전체가 지연됩니다.

### REDIS-05. RDB와 AOF

**면접 답변:** RDB는 특정 시점의 전체 메모리 상태를 Snapshot 파일로 저장해 파일이 작고 복구가 빠르지만 마지막 Snapshot 이후 변경을 잃을 수 있습니다. AOF는 쓰기 명령을 로그로 남겨 `fsync` 정책에 따라 유실 구간을 줄이지만 파일과 쓰기 비용이 더 크고 Rewrite가 필요합니다. 운영 목표에 따라 둘을 함께 쓰거나, Redis를 재생성 가능한 캐시로 보고 영속화를 최소화할 수도 있습니다.

## 5.2 고가용성과 확장

### REDIS-06. Replication, Sentinel, Cluster

**면접 답변:** Replication은 Primary의 데이터를 Replica에 복사해 읽기 분산과 장애 대비를 제공합니다. Sentinel은 Sharding 없이 Primary/Replica 구성을 감시하고 장애 시 새 Primary 선출과 클라이언트 안내를 담당합니다. Cluster는 16,384 Hash Slot으로 데이터를 여러 Primary에 나눠 용량과 처리량을 수평 확장하고 각 Shard의 Failover도 처리합니다.

### REDIS-07. Hash Slot과 데이터 분산

**면접 답변:** Redis Cluster는 Key의 CRC16 결과를 16,384개 Slot 중 하나에 매핑하고, 각 노드가 Slot 범위를 소유합니다. Slot을 노드 사이로 이동해 Resharding할 수 있고, 클라이언트는 `MOVED`나 `ASK` 응답을 따라 올바른 노드로 요청합니다. 여러 Key를 한 원자 연산에 써야 하면 `{user:1}` 같은 Hash Tag로 같은 Slot에 배치해야 합니다.

### REDIS-08. Failover 중 데이터 유실

**면접 답변:** Redis 복제는 기본적으로 비동기라 Primary가 쓰기 성공을 응답한 뒤 Replica에 전달하기 전에 죽을 수 있습니다. 이 Replica가 새 Primary가 되면 아직 복제되지 않은 쓰기가 사라집니다. `WAIT`, 충분한 Replica, 장애 허용 설정으로 위험을 줄일 수 있지만 강한 합의 저장소와 같은 보장은 아니므로 업무가 허용하는 RPO를 먼저 정해야 합니다.

### REDIS-09. Scale-Out, Hot Key, 재분배

**면접 답변:** Cluster로 Key를 Slot에 분산해도 특정 Key에 요청이 몰리면 그 Key를 가진 한 Shard가 병목이 됩니다. 읽기 Hot Key는 로컬 캐시, Replica 읽기, Key 분할을 검토하고 쓰기 Hot Key는 버킷 분산 후 합산이나 업무 모델 변경이 필요합니다. Resharding은 점진적으로 수행하고 네트워크, 메모리 여유, Redirect 증가와 P99 지연을 관찰합니다.

## 5.3 캐시 설계와 장애

### REDIS-10. 캐시 패턴 비교

**면접 답변:** Cache-Aside는 애플리케이션이 캐시 Miss 때 DB를 읽어 채워 단순하고 흔하지만 첫 요청 Miss와 정합성 처리가 필요합니다. Read-Through는 캐시 계층이 원본 조회까지 감추고, Write-Through는 캐시와 원본을 동기 갱신해 읽기 일관성이 좋지만 쓰기 지연이 큽니다. Write-Behind는 캐시에 먼저 쓰고 원본을 비동기 반영해 빠르지만 장애 시 유실과 순서·재처리 설계가 필요합니다.

### REDIS-11. DB와 캐시 정합성

**면접 답변:** 일반적인 Cache-Aside에서는 DB를 먼저 커밋한 뒤 캐시를 삭제해 다음 읽기가 새 값을 채우게 합니다. 삭제 실패를 재시도할 Outbox나 이벤트를 두고 TTL을 최종 안전장치로 사용합니다. 매우 강한 일관성이 필요한 값은 캐시 사용을 피하거나 버전 번호를 함께 저장해 오래된 이벤트가 새 값을 덮지 못하게 합니다. 캐시와 DB를 별도 트랜잭션으로 완벽히 원자화할 수 있다고 가정하면 안 됩니다.

### REDIS-12. Cache Stampede

**면접 답변:** 인기 Key가 만료되는 순간 많은 요청이 동시에 DB를 조회해 원본을 과부하시키는 현상입니다. Key별 Lock이나 Single Flight로 한 요청만 갱신하게 하고 나머지는 기존 값이나 결과를 기다리게 합니다. TTL Jitter, 논리적 만료와 Background Refresh, 만료 전 확률적 갱신도 함께 사용합니다.

### REDIS-13. Penetration과 Avalanche

**면접 답변:** Cache Penetration은 존재하지 않는 Key 요청이 계속 DB까지 통과하는 현상으로 짧은 Negative Cache, 입력 검증, Bloom Filter로 완화합니다. Cache Avalanche는 많은 Key가 동시에 만료되거나 Redis 전체가 장애 나 DB로 부하가 쏠리는 현상입니다. TTL 분산, 다계층 캐시, 요청 제한, Circuit Breaker, Redis 고가용성과 원본 DB 보호 전략이 필요합니다.

### REDIS-14. Hot Key와 Big Key

**면접 답변:** Hot Key는 한 Key에 트래픽이 집중돼 단일 노드 CPU·네트워크를 병목으로 만들고, Big Key는 값이나 원소 수가 커 직렬화·전송·삭제 중 이벤트 루프를 오래 막습니다. 명령 통계, Latency Monitor, Slow Log, 샘플링 도구와 메모리 사용량으로 찾습니다. Key 분할, 로컬 캐시, 데이터 구조 재설계, 점진적 Scan과 `UNLINK` 같은 비동기 삭제로 완화합니다.

### REDIS-15. Redis 장애 시 우회 기준

**면접 답변:** 추천·조회 캐시처럼 오래된 값이나 DB 직접 조회가 허용되면 짧은 타임아웃 후 우회하되, DB가 감당할 수 있도록 Rate Limit과 Circuit Breaker를 둡니다. 분산 락·재고·보안 정책처럼 Redis 실패가 잘못된 쓰기를 만들면 Fail Closed가 안전할 수 있습니다. 기능별 정확성 요구와 DB 여유, 장애 확산 위험을 기준으로 결정하고 한 가지 전역 정책을 적용하지 않습니다.

## 5.4 메모리와 동시성

### REDIS-16. TTL과 Eviction

**면접 답변:** TTL은 Key의 업무상 만료 시점을 정하고 Redis는 접근 시 만료 확인과 주기적인 능동 만료를 함께 사용합니다. `maxmemory`에 도달하면 `noeviction`, `allkeys-lru/lfu/random`, `volatile-lru/lfu/ttl` 같은 정책으로 쓰기를 거절하거나 Key를 제거합니다. LRU/LFU는 근사 방식이며, 캐시 특성과 재생성 비용에 맞는 정책과 충분한 메모리 여유를 선택해야 합니다.

### REDIS-17. 안전한 분산 락

**면접 답변:** 단일 Redis에서는 `SET key token NX PX ttl`로 고유 Token과 만료 시간을 함께 설정하고, 해제는 Lua Script로 내가 가진 Token인지 확인한 뒤 삭제합니다. 작업 시간이 TTL을 넘을 수 있으면 안전한 연장이나 더 짧은 작업 단위가 필요합니다. 프로세스 정지와 네트워크 지연으로 오래된 소유자가 뒤늦게 쓰는 문제는 Fencing Token을 실제 자원 저장소에서 검증해야 막을 수 있습니다.

### REDIS-18. MULTI/EXEC, Lua, 명령 원자성

**면접 답변:** Redis의 개별 명령은 이벤트 루프에서 중간에 다른 명령이 끼지 않아 원자적입니다. `MULTI/EXEC`는 큐에 넣은 여러 명령을 연속 실행하지만 일반 DB처럼 실행 중 오류를 자동 Rollback하지 않으며, `WATCH`로 낙관적 충돌 검사를 할 수 있습니다. Lua Script는 읽기·판단·쓰기를 서버에서 하나의 원자 작업으로 실행해 왕복과 Race를 줄이지만 오래 실행되면 전체 요청을 막습니다.

### REDIS-19. 분산 Rate Limiter

**면접 답변:** 고정 Window는 `INCR`와 TTL로 단순하지만 경계 순간 Burst가 큽니다. Sliding Log는 Sorted Set에 요청 시각을 기록해 정확하지만 메모리 비용이 크고, Token Bucket은 일정 속도로 Token을 보충해 평균 속도와 Burst를 함께 제어합니다. 여러 명령의 시간 계산과 갱신은 Lua로 원자화하고 Redis 서버 시간, Key TTL, 장애 시 허용/차단 정책을 정합니다.

### REDIS-20. Redlock과 논쟁점

**면접 답변:** Redlock은 독립된 여러 Redis 노드 중 과반에서 제한 시간 안에 같은 Lock을 얻어 단일 노드 장애 위험을 줄이려는 알고리즘입니다. 그러나 네트워크 지연, 프로세스 정지, 시계와 임대 만료 뒤의 오래된 소유자 문제 때문에 강한 일관성 Lock으로 충분한지 논쟁이 있습니다. 중요한 자원은 합의 시스템이나 DB Lock을 고려하고, Redis Lock을 쓰더라도 Fencing Token과 멱등 쓰기를 함께 둡니다.

## 5.5 메시징과 운영

### REDIS-21. Pub/Sub과 Streams

**면접 답변:** Pub/Sub은 현재 구독 중인 Consumer에게 메시지를 즉시 Fan-Out하지만 저장·재전송·ACK가 없어 Consumer가 끊기면 놓칩니다. Streams는 메시지를 ID가 있는 로그로 저장하고 Consumer Group, Pending 목록, ACK, 재처리를 지원합니다. 휘발성 실시간 알림은 Pub/Sub, 추적과 재처리가 필요한 작업 흐름은 Streams가 적합합니다.

### REDIS-22. Streams Consumer Group

**면접 답변:** Consumer Group은 Stream의 메시지를 그룹 내 Consumer들이 나눠 처리하게 합니다. 전달했지만 `XACK`되지 않은 메시지는 PEL(Pending Entries List)에 남고, 장애 난 Consumer의 오래된 Pending 메시지는 다른 Consumer가 Claim해 재처리할 수 있습니다. 따라서 적어도 한 번 전달을 전제로 Consumer가 멱등해야 하며 PEL 크기와 Idle 시간을 모니터링합니다.

### REDIS-23. Redis 모니터링 메트릭

**면접 답변:** 명령 처리량과 P50/P99 지연, CPU, 사용 메모리와 단편화율, Eviction·Expired Key, Cache Hit Ratio를 봅니다. 연결 수·거부, Blocked Client, Network I/O, Slow Log도 중요합니다. 고가용성에서는 Replication Lag, Link 상태, Failover, Cluster Slot 상태와 노드별 Key·트래픽 불균형을 함께 봅니다.

### REDIS-24. Redis 지연 진단

**면접 답변:** 영향 시간과 느린 명령을 확인한 뒤 서버 CPU·메모리·Swap·네트워크와 Slow Log, Latency Monitor를 봅니다. Big Key, `KEYS` 같은 O(N) 명령, 대량 Lua, Fork 기반 RDB/AOF Rewrite, Replica 동기화, 클라이언트 연결 폭증을 구분합니다. 먼저 위험한 명령과 트래픽을 제한하고, 이후 Key 구조·명령·메모리·Persistence 설정을 실제 부하로 개선합니다.

# 6. Kafka

## 6.1 구조와 데이터 흐름

### KAFKA-01. Kafka와 전통적 메시지 큐의 차이

**면접 답변:** Kafka는 이벤트를 Partition별 순서 있는 Append-Only Log로 저장하는 분산 이벤트 스트리밍 플랫폼입니다. Consumer가 읽어도 메시지가 즉시 삭제되지 않고 보존 정책 동안 남아 여러 Consumer Group이 독립적으로 읽거나 Replay할 수 있습니다. 작업 분배와 삭제 중심의 Queue보다 이벤트 이력, 높은 처리량, 다수 구독자와 재처리에 강하지만 운영 복잡성과 Partition 설계가 필요합니다.

### KAFKA-02. Broker, Topic, Partition, Record

**면접 답변:** Broker는 Kafka 서버 한 대이고 Cluster는 여러 Broker로 구성됩니다. Topic은 이벤트의 논리적 이름이며, 실제 데이터는 여러 Partition에 나뉘어 각 Partition의 Offset 순서대로 저장됩니다. Record는 Key, Value, Timestamp, Header를 가지며 Partition은 Replica를 통해 여러 Broker에 복제됩니다.

### KAFKA-03. Producer 전송 과정

**면접 답변:** Producer가 Key와 Value를 직렬화하고 Partitioner가 대상 Partition을 고릅니다. Record Accumulator에서 같은 Partition 데이터를 Batch로 모아 해당 Partition Leader Broker에 전송합니다. Leader가 로그에 Append하고 `acks` 조건을 만족하면 성공을 응답하며, 재시도 가능한 오류면 Producer가 다시 보냅니다. Batch, 압축, In-Flight 요청 설정이 처리량·지연·순서에 영향을 줍니다.

### KAFKA-04. Partition Key와 순서 보장

**면접 답변:** 같은 Key는 일반적으로 같은 Partition으로 보내져 사용자나 주문 단위의 순서를 유지합니다. Kafka가 보장하는 총순서는 Topic 전체가 아니라 Partition 내부의 Offset 순서입니다. Key가 한 값에 몰리면 Hot Partition이 생기므로 순서가 필요한 업무 단위를 최소 Key로 잡고, 순서와 분산 사이의 Trade-Off를 결정합니다.

### KAFKA-05. Consumer Group

**면접 답변:** 같은 Group ID의 Consumer들은 Topic Partition을 나눠 읽어 하나의 논리적 구독자를 이룹니다. 한 Partition은 같은 Group 안에서 동시에 한 Consumer에만 할당되므로 순서를 유지합니다. 다른 Group은 같은 이벤트를 독립적으로 다시 읽을 수 있어 분석, 알림, 저장 파이프라인을 분리할 수 있습니다.

### KAFKA-06. Offset

**면접 답변:** Offset은 Partition 안에서 Record 위치를 나타내는 증가 번호입니다. Consumer는 어디까지 처리했는지 다음에 읽을 Offset을 Group별로 Kafka의 `__consumer_offsets` Topic에 Commit합니다. 자동 Commit은 단순하지만 실제 처리 완료와 시점이 어긋날 수 있어, 중요한 작업은 처리 성공 후 수동 Commit하고 실패·재시도 경계를 명확히 합니다.

## 6.2 전달 보장과 장애

### KAFKA-07. 전달 보장 비교

**면접 답변:** At-Most-Once는 처리 전에 Offset을 Commit해 중복은 적지만 장애 시 메시지를 잃을 수 있습니다. At-Least-Once는 처리 후 Commit해 유실을 줄이지만 장애 구간에서 중복이 발생하므로 Consumer가 멱등해야 합니다. Exactly-Once는 정의한 Kafka 처리 경계 안에서 결과와 Offset을 원자화하지만 외부 DB·API까지 자동으로 한 번 실행되게 하지는 않아 별도 Idempotency가 필요합니다.

### KAFKA-08. acks, ISR, min.insync.replicas

**면접 답변:** `acks=0`은 확인을 기다리지 않고, `acks=1`은 Leader 기록만, `acks=all`은 현재 ISR의 복제를 기다립니다. ISR은 Leader를 충분히 따라온 Replica 집합이고 `min.insync.replicas`는 `acks=all` 쓰기를 허용할 최소 ISR 수입니다. 예를 들어 Replication Factor 3, 최소 ISR 2면 한 노드 장애에도 안전한 쓰기를 계속하지만 두 노드가 빠지면 가용성보다 내구성을 택해 쓰기를 거부합니다.

### KAFKA-09. Idempotent Producer의 범위

**면접 답변:** Idempotent Producer는 Producer ID와 Partition별 Sequence Number로 재시도 중 같은 Record가 Broker 로그에 중복 Append되는 것을 막습니다. 하지만 애플리케이션이 같은 업무 이벤트를 두 번 생성하거나, Consumer가 외부 DB 반영을 두 번 하는 문제까지 막지는 않습니다. 업무 Event ID와 Consumer 측 Unique Constraint 또는 멱등 Upsert가 별도로 필요합니다.

### KAFKA-10. Kafka Transaction

**면접 답변:** Kafka Transaction은 한 Producer가 여러 Partition에 쓴 Record와 Consumer Offset Commit을 하나의 원자적 단위로 묶을 수 있습니다. `read_committed` Consumer는 Commit된 Transaction만 읽어 Kafka→처리→Kafka 파이프라인의 Exactly-Once Semantics를 구성합니다. 일반 RDB나 외부 API 호출은 이 Transaction에 포함되지 않습니다.

### KAFKA-11. DB 반영과 Offset Commit 장애

**면접 답변:** DB 반영 후 Offset Commit 전에 죽으면 같은 메시지를 다시 읽어 DB 작업이 중복될 수 있고, Commit 후 DB 반영 전에 죽으면 메시지를 잃습니다. 보통 처리 후 Commit하는 At-Least-Once와 Event ID Unique Constraint, Inbox 테이블, 멱등 Upsert를 조합합니다. DB 변경에서 Kafka 발행까지 원자성이 필요하면 Transactional Outbox에 함께 기록하고 별도 Publisher가 전송합니다.

### KAFKA-12. Retry Topic, DLQ, Poison Message

**면접 답변:** 일시 오류는 횟수 제한과 지수 Backoff를 둔 Retry Topic으로 보내고, 영구 오류나 한도를 넘은 메시지는 원본 Metadata와 실패 원인을 붙여 DLQ로 격리합니다. Poison Message를 같은 Partition에서 무한 재시도하면 뒤 이벤트까지 막으므로 격리하되, 순서가 절대 중요하면 해당 Key의 후속 처리 정책을 따로 정해야 합니다. DLQ는 묘지가 아니라 알람, 수정, 안전한 Replay 절차가 있는 운영 큐여야 합니다.

### KAFKA-13. Broker 장애와 Leader 복구

**면접 답변:** Partition Leader가 장애 나면 Controller가 ISR 중 하나를 새 Leader로 선출하고 Producer와 Consumer가 Metadata를 갱신해 연결합니다. ISR 밖 Replica를 Leader로 허용하는 Unclean Election은 가용성을 높일 수 있지만 복제되지 않은 데이터를 잃을 수 있습니다. Replica 분산, 충분한 ISR, Rack/AZ Awareness와 Leader Election 시간을 모니터링해야 합니다.

## 6.3 소비와 확장

### KAFKA-14. Consumer Rebalancing

**면접 답변:** Group의 Consumer 수나 Topic Partition이 바뀔 때 Partition 소유권을 다시 나누는 과정입니다. Rebalance 동안 소비가 멈추거나 처리 중인 작업이 중복될 수 있고 Cache도 다시 데워야 합니다. 처리 시간을 `max.poll.interval.ms` 안에 맞추고, Static Membership과 Cooperative Sticky Assignor, 적절한 종료 처리로 이동 범위와 중단을 줄입니다.

### KAFKA-15. Consumer Lag 진단

**면접 답변:** 먼저 전체가 느린지 특정 Partition만 느린지와 유입률 대비 처리율을 봅니다. Consumer 오류·GC·CPU, 외부 DB/API 지연, Batch 크기와 처리 시간, Rebalance, Network, Hot Partition을 확인합니다. 일시 폭증이면 처리량을 늘리거나 따라잡을 시간을 계산하고, 구조적 병목이면 Partition과 Consumer 확장 전에 Downstream이 감당할 수 있는지 확인합니다.

### KAFKA-16. Consumer가 Partition보다 많을 때

**면접 답변:** 같은 Consumer Group에서는 한 Partition을 동시에 한 Consumer만 담당하므로 초과 Consumer는 할당받지 못하고 유휴 상태가 됩니다. 소비 병렬성의 상한은 기본적으로 Partition 수입니다. 더 늘리려면 Partition을 추가할 수 있지만 Key 매핑과 운영 비용, 기존 순서 의미가 달라질 수 있습니다.

### KAFKA-17. Hot Partition

**면접 답변:** 특정 Key가 지나치게 많거나 Partition 전략이 불균등하면 한 Partition의 Producer 지연과 Consumer Lag만 커집니다. 업무상 순서가 꼭 필요한 범위를 다시 정의해 Key를 세분화하거나 Salt를 붙여 분산하고 Downstream에서 합칠 수 있습니다. 단순히 Partition을 늘려도 같은 Key는 한 곳에 가므로 Key 분포를 먼저 고쳐야 합니다.

### KAFKA-18. Kafka의 높은 처리량

**면접 답변:** 디스크에 무작위 갱신보다 순차 Append하고 OS Page Cache를 적극 활용합니다. Producer와 Consumer가 Record를 Batch로 묶고 압축해 네트워크 왕복을 줄이며, Zero-Copy 전송으로 불필요한 복사를 줄일 수 있습니다. Partition 단위 병렬 처리와 Pull 기반 Consumer도 처리량 조절에 유리합니다.

### KAFKA-19. Batch, Linger, Compression

**면접 답변:** `batch.size`와 `linger.ms`를 키우면 더 많은 Record를 한 번에 보내 압축률과 처리량이 좋아지지만 대기 지연과 메모리가 늘어납니다. Compression은 네트워크와 디스크를 절약하지만 Producer/Consumer CPU를 사용하며 같은 Batch의 유사 데이터가 많을수록 효과적입니다. 평균이 아니라 Peak에서의 P99 지연, 처리량, CPU, Request 크기를 함께 측정해 조정합니다.

## 6.4 데이터 수명과 시스템 설계

### KAFKA-20. Retention과 Log Compaction

**면접 답변:** Retention은 시간이나 크기 기준으로 오래된 Log Segment를 제거해 이벤트 이력을 일정 기간 보존합니다. Log Compaction은 Key별 가장 최신 Value를 남겨 상태를 복원할 수 있게 하며 Tombstone으로 삭제를 표현합니다. 둘은 함께 설정할 수 있고 Compaction도 즉시 실행되는 것이 아니므로 Consumer가 모든 중간 이벤트를 영구히 볼 수 있다고 가정하면 안 됩니다.

### KAFKA-21. 스키마 호환성

**면접 답변:** Event에 명시적 버전을 두고 Schema Registry와 Avro/Protobuf/JSON Schema로 호환 규칙을 검사합니다. 기존 Consumer가 모르는 선택 필드를 추가할 때는 기본값을 제공하고, 필드 삭제·타입 변경·의미 변경은 단계적으로 진행합니다. Producer를 먼저 바꿀지 Consumer를 먼저 바꿀지 Backward/Forward Compatibility 계약으로 정하고 실제 구버전 Contract Test를 둡니다.

### KAFKA-22. Transactional Outbox

**면접 답변:** 업무 DB 변경과 발행할 Event를 같은 로컬 DB Transaction에서 Outbox 테이블에 함께 기록하는 패턴입니다. 별도 Publisher나 CDC가 Outbox를 Kafka로 전송해 “DB는 커밋됐지만 Event 발행은 실패”하는 Dual Write 문제를 줄입니다. 전송은 중복될 수 있으므로 Event ID, 멱등 Consumer, Outbox 정리와 지연 모니터링이 필요합니다.

### KAFKA-23. Replay 주의점

**면접 답변:** 새 Consumer Group이나 Offset 재설정으로 과거 이벤트를 다시 읽을 수 있지만, 외부 알림·결제 같은 부수 효과가 다시 실행되지 않도록 Replay Mode와 멱등성을 준비해야 합니다. 당시 스키마와 참조 데이터, Event Time을 재현할 수 있어야 하고 실시간 트래픽을 압도하지 않도록 Quota와 별도 Consumer를 둡니다. 진행률, 결과 검증, 중단·재개 절차도 필요합니다.

### KAFKA-24. Kafka, Queue, Redis Streams 선택

**면접 답변:** 긴 보존, Replay, 다수 독립 구독자, 매우 높은 Stream 처리량이 필요하면 Kafka가 적합합니다. 작업을 한 번 분배하고 관리형 운영·Visibility Timeout·DLQ가 중요하면 SQS 같은 Queue가 단순합니다. 이미 Redis를 운영하고 규모가 제한적이며 짧은 Stream과 Consumer Group이 필요하면 Redis Streams를 고려할 수 있지만 메모리 비용과 내구성·확장 한계를 평가합니다.

### KAFKA-25. Kafka 모니터링

**면접 답변:** Producer 오류·재시도·Record 지연과 전송률, Broker CPU·디스크·네트워크·Request Queue를 봅니다. Under-Replicated/Offline Partition, ISR 축소, Controller와 Leader Election은 내구성과 가용성 신호입니다. Consumer는 Partition별 Lag, 처리율, Rebalance, Commit 실패를 보고 디스크 사용량과 Retention 여유도 알람으로 관리합니다.

# 7. 핵클 JD 예상 답안

## 7.1 SDK와 로컬 평가

### JD-01. SDK 로컬 평가를 쓰는 이유

**면접 답변:** 기능 플래그와 실험 분배를 SDK 로컬에서 평가하면 매 요청의 네트워크 왕복이 없어 지연과 비용이 작고, 중앙 서버가 잠시 장애여도 마지막 설정으로 서비스를 계속할 수 있습니다. 대신 설정 전파가 즉시가 아니고 SDK 구현·버전 호환·메모리와 스레드 관리가 복잡해집니다. 따라서 Control Plane은 버전 있는 설정을 배포하고 Data Plane인 SDK는 검증된 Snapshot으로 빠르게 평가하도록 분리합니다.

### JD-02. 설정 동기화의 최신성과 가용성

**면접 답변:** SDK는 시작 시 설정을 가져오고 일정 주기로 Version 또는 ETag를 확인해 변경분을 동기화합니다. 새 설정을 검증한 뒤에만 원자적으로 교체하고 실패하면 Last-Known-Good 설정을 유지하며 지수 Backoff와 Jitter로 재시도합니다. 긴급 Kill Switch에는 짧은 Polling이나 Push 경로를 제공하되, 동기화 장애가 고객 요청 경로를 막지 않게 합니다.

### JD-03. 설정 전체의 Thread-Safe 교체

**면접 답변:** 읽기마다 큰 Lock을 잡기보다 완성된 불변 설정 Snapshot을 별도 공간에서 만들고 검증한 뒤 `AtomicReference`나 `volatile` 참조를 한 번에 교체합니다. 요청은 시작할 때 참조 하나를 읽어 같은 Version의 설정만 사용하므로 중간 상태를 보지 않습니다. 부분 변경 가능한 Map을 여러 단계로 수정하는 방식은 혼합 Version과 Race를 만들기 쉽습니다.

### JD-04. 상태 있는 SDK Singleton Bean

**면접 답변:** Spring Singleton은 인스턴스가 하나라는 뜻이지 자동 Thread-Safe를 뜻하지 않습니다. 공유 설정·이벤트 큐·통계의 가시성과 원자성을 보장하고, 사용자 요청별 변경 상태를 필드에 두지 않아야 합니다. Executor와 HTTP Client를 중복 생성하지 않고 애플리케이션 종료 시 `@PreDestroy`로 전송을 마무리하고 스레드·커넥션을 닫아야 합니다.

### JD-05. SDK/서버 호환성

**면접 답변:** Protocol과 설정 Schema는 가능한 한 필드 추가 중심으로 진화시키고 새 필드는 기본값을 가져 구버전 SDK가 무시해도 안전하게 합니다. 서버는 지원 중인 SDK Version과 Capability를 알고 해당 버전이 이해할 수 있는 설정만 내려주며, 제거는 사용률 관찰과 충분한 Deprecation 기간 뒤에 합니다. 언어별 SDK에 같은 Golden Test Vector를 적용해 직렬화와 평가 결과도 Contract Test합니다.

## 7.2 이벤트 수집과 비동기 처리

### JD-06. Bounded Queue와 포화 정책

**면접 답변:** 무제한 Queue는 전송이 느려질 때 메모리를 계속 먹어 고객 애플리케이션까지 OOM으로 죽일 수 있어 SDK Queue는 한도를 둬야 합니다. 가득 찼을 때 Block은 Event를 보존하지만 고객 요청 지연을 만들고, Drop은 요청을 보호하지만 데이터가 빠지며, Caller-Runs는 자연스러운 Backpressure지만 역시 지연을 전파합니다. Event 중요도와 SDK 계약에 따라 정책을 선택 가능하게 하고 Drop 수·Queue 사용률을 노출합니다.

### JD-07. N건 또는 T초 Batch

**면접 답변:** N을 키우면 요청 횟수와 Header 비용이 줄고 압축률이 좋아지지만 낮은 트래픽에서 전송이 늦고 장애 시 메모리 내 유실량이 커집니다. T를 줄이면 Freshness와 종료 시 유실 구간은 줄지만 작은 Batch가 많아집니다. `size >= N OR elapsed >= T`로 두 조건을 함께 사용하고 Payload Byte 한도, 네트워크 지연, 서버 수용 Batch 크기를 부하 테스트로 정합니다.

### JD-08. SDK Graceful Shutdown

**면접 답변:** 종료 신호를 받으면 새 Event 접수를 중단하거나 명시된 정책으로 제한하고, Queue의 남은 Event를 제한 시간 안에 Flush한 뒤 Dispatcher와 HTTP 자원을 닫습니다. Shutdown Hook이나 프레임워크 Lifecycle에 연결하되 무한 대기하지 않고 Flush 성공·실패·남은 Event 수를 기록합니다. Crash와 강제 종료는 막을 수 없으므로 중요한 Event는 로컬 Disk Buffer나 서버 측 중복 허용 재전송을 고려합니다.

### JD-09. 재시도와 중복 방지

**면접 답변:** 각 Event에 전역 또는 Tenant 범위의 고유 Event ID를 부여하고 Producer는 동일 ID로 재시도합니다. 수집 서버나 Consumer는 Unique Constraint, Dedup Store, 멱등 Upsert로 같은 Event의 효과를 한 번만 반영합니다. Dedup TTL은 최대 재시도·Replay 기간보다 길게 잡고, 정확한 중복 제거 비용이 너무 크면 업무별로 중복 허용과 근사 제거 범위를 정합니다.

### JD-10. Multi-Tenant 이벤트 수집 설계

**면접 답변:** 인증·Tenant Quota가 있는 Stateless Ingestion API가 Event를 빠르게 검증해 Kafka 같은 Broker에 기록하고, Consumer가 정규화·중복 제거 후 Object Storage 원본과 분석 저장소에 적재하도록 분리합니다. Partition Key는 Tenant와 순서 요구 단위를 함께 고려하고 Schema Registry, DLQ, Replay 경로를 둡니다. SLO는 수집 성공률·P99 응답·Broker 기록 내구성·조회 Freshness로 나누고 Tenant별 비용과 Lag를 관찰합니다.

### JD-11. Tenant 격리

**면접 답변:** Tenant별 인증, Rate Limit, 동시성·Queue·저장량 Quota를 두고 공정한 Scheduling으로 한 고객이 Worker를 독점하지 못하게 합니다. Partition을 Tenant 하나에 고정하면 큰 고객이 Hot Partition을 만들 수 있어 크기에 따라 Key를 분할하고, 초대형 고객은 전용 Partition·Consumer Pool로 격리할 수 있습니다. 메트릭과 알람도 Tenant Label을 가져야 원인 고객을 빠르게 식별할 수 있습니다.

### JD-12. 늦거나 순서가 뒤바뀐 이벤트

**면접 답변:** 수집 시각과 실제 발생 시각을 분리하고 Event Time 기준 Window와 허용 지연 Watermark를 정의합니다. Window가 닫힌 뒤 늦게 온 Event는 보정 Update나 별도 Late Stream으로 처리하고, 고유 ID와 업무 Version으로 중복·오래된 변경을 거부합니다. 완전한 전역 순서를 만들기보다 사용자·세션처럼 필요한 범위만 순서 Key로 묶습니다.

### JD-13. 스키마 변경과 Replay

**면접 답변:** Event Schema를 Registry에서 호환성 검사하고 새 선택 필드는 기본값과 함께 추가합니다. 원본 Event는 변경 없이 보존하고 변환 로직과 파생 Dataset에 Version을 부여해 새 Consumer가 과거 원본을 다시 계산할 수 있게 합니다. Replay는 별도 Quota와 Consumer Group으로 실시간 파이프라인을 방해하지 않게 하며 부수 효과는 끄고 결과 수·Checksum을 검증합니다.

## 7.3 A/B 테스트와 기능 플래그

### JD-14. 모든 SDK에서 같은 그룹을 받는 조건

**면접 답변:** 동일한 Canonical User Identifier, Experiment Seed, Hash 알고리즘과 Byte Encoding, Slot 수와 구간 설정을 사용해야 합니다. Null·Unicode·숫자 문자열 처리까지 언어별로 같아야 하며 설정 Version도 일치해야 합니다. 서버가 제공하는 Golden Input/Output Vector를 모든 SDK의 Contract Test로 실행해 교차 언어 결정성을 검증합니다.

### JD-15. 결정적 버케팅

**면접 답변:** Experiment Seed와 User ID를 합쳐 균등 분포 특성이 좋은 Hash를 계산하고 고정 Slot 범위에 매핑합니다. 각 Variation이 소유한 Slot 구간으로 그룹을 결정하므로 같은 입력은 항상 같은 결과를 받아 Sticky Assignment가 됩니다. 암호학적 보안보다 빠른 계산, 안정된 결과, 충분한 분포가 중요하지만 식별자 조작이 보안 문제가 되면 별도 신뢰 경계가 필요합니다.

### JD-16. 비율 변경과 재배정 최소화

**면접 답변:** 고정된 10,000개 같은 Slot 공간에서 기존 Variation 구간을 유지하고, 비율 증가에 꼭 필요한 인접 Slot만 다른 그룹에서 이동합니다. 50:50에서 90:10이면 최소한 40%의 Slot은 B에서 A로 이동해야 하지만 나머지 사용자는 그대로 둘 수 있습니다. 장기 Sticky Assignment가 더 중요하면 최초 배정을 저장하되 저장 비용과 신규 비율 수렴 속도의 대가를 설명합니다.

### JD-17. 배정과 실제 노출의 차이

**면접 답변:** 그룹 배정만 됐어도 사용자가 해당 화면에 들어오지 않거나 기능을 실제로 보지 않을 수 있습니다. 배정 시점을 분모로 쓰면 실험 효과가 희석되거나 노출 조건에 따른 편향이 생길 수 있어 실제 평가 지점에서 Exposure Event를 기록합니다. 중복 Exposure, Bot, 내부 사용자, 사용자 식별 변경도 분석 전에 정리해야 합니다.

### JD-18. Sample Ratio Mismatch 조사

**면접 답변:** 먼저 기대 비율과 실제 분배 차이가 통계적으로 우연 범위를 넘는지, 특정 기간·SDK·플랫폼·Tenant에 집중되는지 확인합니다. 그다음 Hash/Slot 설정과 SDK Version, 식별자 Null·중복, Exposure 로깅 실패, 수집 Drop, 필터 조건과 Bot을 순서대로 봅니다. 분배 문제와 측정 파이프라인 문제를 분리하고 원본 Event부터 단계별 Count를 대조합니다.

### JD-19. 점진 출시와 Kill Switch

**면접 답변:** 내부 사용자와 작은 비율부터 시작해 오류율·P99·업무 Guardrail을 확인하며 단계적으로 확대하고, 각 단계의 자동 중단 기준을 정합니다. 설정은 Version과 감사 로그를 갖고 원자적으로 Publish하며 즉시 이전 Version으로 Rollback할 수 있어야 합니다. Kill Switch는 의존 서비스가 불안정할 때도 빠르게 평가돼야 하므로 마지막 안전 설정과 SDK 전파 지연을 고려합니다.

## 7.4 Reactive, Coroutine, 고가용성

### JD-20. Reactive Streams Backpressure

**면접 답변:** Backpressure는 Consumer가 처리할 수 있는 양만 `request(n)`으로 Producer에 요구해 무제한 Buffer와 OOM을 막는 흐름 제어입니다. 이벤트 수집에서는 Downstream DB가 느려질 때 수집 속도를 그대로 밀어 넣지 않고 Buffer, 제한, Drop, Retry 중 정책을 적용하게 합니다. 단순히 비동기라는 뜻이 아니며 전체 경로에 Blocking 구간이 있으면 별도 Scheduler와 용량 경계를 둬야 합니다.

### JD-21. Coroutine이 가볍다는 의미

**면접 답변:** Coroutine은 대기 중 실행 상태를 객체로 저장하고 소수 Thread 위에서 중단·재개할 수 있어 요청마다 OS Thread와 큰 Stack을 점유하는 것보다 비용이 작다는 뜻입니다. CPU 작업 자체가 공짜이거나 여러 Coroutine이 한 Thread에서 동시에 실행된다는 뜻은 아닙니다. Suspend 가능한 비동기 API를 사용할 때 특히 많은 I/O 동시성을 효율적으로 표현합니다.

### JD-22. Coroutine에서 Blocking I/O 호출

**면접 답변:** `Dispatchers.Default` 같은 제한된 CPU Thread Pool에서 Blocking I/O를 호출하면 Thread가 대기하는 동안 다른 Coroutine도 실행하지 못해 Pool Starvation과 지연이 발생합니다. Blocking 호출은 `Dispatchers.IO`나 별도 제한 Pool로 격리하고 가능하면 Suspend 기반 Client를 사용합니다. Timeout, Cancellation과 ThreadLocal Context 전파도 경계에서 확인합니다.

### JD-23. 핵클형 시스템의 SLO

**면접 답변:** SDK 평가는 고객 요청 경로이므로 매우 낮은 P99 지연과 높은 로컬 가용성을, 설정 배포는 Freshness와 성공률을, 이벤트 수집은 수락 성공률·내구성·최대 Lag를 따로 정의합니다. 모든 지표를 동시에 최대로 만들 수 없으므로 고객 기능을 막지 않는 평가 가용성을 우선하고, 분석 Event는 허용 가능한 유실률과 지연을 명시합니다. SLO에는 측정 지점과 Error Budget, 초과 시 중단할 출시 정책까지 연결합니다.

### JD-24. AZ, Broker, DB 장애 대응

**면접 답변:** Stateless API를 여러 AZ에 분산하고 Health 기반 Load Balancing을 사용합니다. Kafka와 DB는 AZ를 나눈 Replica와 자동 Failover를 구성하되 Replication Lag과 쓰기 일관성 대가를 정합니다. 중앙 Control Plane 장애 때도 SDK는 Last-Known-Good 설정으로 평가하고, 이벤트는 제한된 로컬/브로커 Buffer로 흡수해 핵심 기능과 분석 기능의 장애를 분리합니다.

### JD-25. Kubernetes Probe

**면접 답변:** Startup Probe는 초기화가 긴 애플리케이션이 시작하기 전 Liveness에 죽지 않게 합니다. Readiness는 현재 트래픽을 받을 준비가 됐는지를 판단해 실패하면 Service Endpoint에서 제외하고, Liveness는 프로세스가 복구 불가능하게 멈췄는지 판단해 재시작합니다. DB가 잠깐 느리다는 이유로 모든 Pod의 Liveness를 실패시키면 장애를 키울 수 있어 의존성별 의미를 분리합니다.

### JD-26. Rolling Update와 무손실 종료

**면접 답변:** 새 Pod가 Startup과 Readiness를 통과한 뒤에만 트래픽을 받고, 종료 Pod는 먼저 Readiness를 내려 새 요청 유입을 끊습니다. `preStop`과 충분한 `terminationGracePeriodSeconds` 동안 진행 중 요청을 완료하고 Consumer Partition을 반납하며 Buffer Event와 Offset을 안전하게 Flush합니다. Load Balancer 전파 지연, SIGTERM 처리, PodDisruptionBudget과 실제 종료 시간을 배포 테스트로 검증합니다.

## 7.5 JD·경험 연결형

### JD-27. 성능 또는 정합성 문제 해결 경험

**면접 답변:** 이 질문은 꾸며낸 기술 지식보다 실제 한 사례의 증거가 중요합니다. `사용자 영향과 수치 → 로그·프로파일·실행 계획으로 확인한 원인 → 검토한 대안 → 내가 선택한 변경 → 같은 조건의 전후 결과 → 남은 한계와 재발 방지` 순서로 답합니다. “쿼리를 튜닝했다”보다 스캔 행 수, 지연 백분위, Lock 범위처럼 판단 근거를 말해야 합니다.

**쉽게 말하면:** 무엇을 고쳤는지보다 어떻게 원인을 좁히고 선택이 맞았음을 증명했는지를 보여주는 질문입니다.

### JD-28. Redis·Kafka 선택 과정

**면접 답변:** 먼저 데이터의 원본 여부, 접근 패턴, 순서·재처리·일관성, 허용 지연, 장애 시 행동과 운영 역량을 정의합니다. 짧은 Key 조회와 TTL·원자 연산이면 Redis, 보존되는 이벤트 로그·Replay·다수 Consumer면 Kafka가 후보가 되며 단순한 RDB나 관리형 Queue로 충분한지도 비교합니다. 선택하지 않은 대안과 실패 모드, 측정할 지표까지 말해야 기술 이름 나열을 벗어납니다.

### JD-29. 고객 요구와 완벽한 설계의 충돌

**면접 답변:** 실제 사례를 `고객이 지금 겪는 손실 → 완벽한 안과 빠른 안의 비용·위험 → 되돌릴 수 있는 최소 해결책 → 성공/중단 지표 → 후속 개선` 순서로 답합니다. 빠른 안을 골랐다면 안전장치와 갚을 기술부채를, 긴 안을 골랐다면 지금 투자해야만 했던 비가역 위험을 설명합니다. 속도나 완성도 자체가 아니라 고객 Impact 대비 투자로 판단했음을 보여줍니다.

### JD-30. 강한 의견을 바꾼 경험

**면접 답변:** `처음 주장과 근거 → 상대가 제시한 반대 근거 → 논쟁 대신 합의한 검증 방법 → 결과를 보고 바꾼 결정 → 바뀐 실행에 내가 기여한 행동` 순서로 답합니다. 처음 의견이 틀렸다는 고백만으로 끝내지 않고, 불확실성을 데이터로 줄이고 결정 후에는 한 팀으로 실행했다는 점을 보여줍니다. 반대로 의견을 유지했다면 무엇이 반증되면 바꿀지도 말할 수 있어야 합니다.

## 7.6 Spring, ORM, NoSQL, 서비스 운영

### JD-31. @Transactional이 적용되지 않는 경우

**면접 답변:** 기본 Proxy 방식에서는 같은 객체 내부에서 `this`로 호출하는 Self-Invocation이 Proxy를 거치지 않아 Transaction Advice가 적용되지 않습니다. `private` 메서드처럼 Proxy가 가로챌 수 없는 호출, Spring이 관리하지 않는 객체, 잘못된 예외 Rollback 규칙도 대표 원인입니다. 비동기나 Coroutine으로 실행 경계가 다른 Thread·Context로 넘어가면 기존 Transaction이 자동 전파된다고 가정하면 안 됩니다.

### JD-32. JPA N+1 발견과 해결

**면접 답변:** 목록 한 번을 조회한 뒤 연관 Entity마다 추가 Query가 반복되는 현상으로 SQL 로그, Query Count Test, APM에서 발견합니다. 한 연관을 함께 가져오면 Fetch Join이나 Entity Graph를, 여러 컬렉션과 Pagination 제약이 있으면 Batch Fetch나 필요한 값만 조회하는 DTO Projection을 고려합니다. 무조건 Eager로 바꾸기보다 화면별 조회 모양을 명시하고 실제 Query 수와 결과 건수를 검증합니다.

### JD-33. 실험 상태 전이의 동시성

**면접 답변:** DRAFT에서 RUNNING으로 갈 수 있다는 상태 전이 규칙을 Domain 안에 두고 DB에서 한 번만 성공하도록 보장합니다. 충돌이 드물면 Version 컬럼의 낙관적 락이나 `UPDATE ... WHERE status='DRAFT'` 후 영향 행 수 확인이 적합하고, 여러 관련 행을 함께 잠가야 하면 비관적 락을 검토합니다. 중복 요청에는 Idempotency Key나 이미 완료된 결과 반환 정책을 둡니다.

### JD-34. 데이터 성격에 따른 저장소 선택

**면접 답변:** 실험 정의·권한·상태처럼 강한 정합성과 관계가 필요한 Control Data는 RDB에 둡니다. 매우 자주 읽는 배포 설정 Snapshot은 Redis나 SDK 로컬 캐시, 대량 Event 전달과 Replay는 Kafka, 변경하지 않는 원본 Event의 장기 보존은 Object Storage가 적합합니다. 분석 결과는 조회 패턴에 맞는 OLAP/검색 저장소에 두며, 각 저장소의 원본 여부와 재생성 경로를 명확히 합니다.

### JD-35. Elasticsearch를 원본 저장소로 조심하는 이유

**면접 답변:** Elasticsearch는 역색인과 분산 검색·집계에 강하지만 Refresh 전에는 새 문서가 검색에 보이지 않는 Near-Real-Time 시스템이고, Update·Delete와 강한 Transaction 제약이 RDB와 다릅니다. Mapping 변경, Segment Merge, Replica와 Cluster 복구도 운영 비용이 큽니다. 원본은 내구성과 정합성이 맞는 저장소에 두고 Elasticsearch는 Event나 CDC로 재구축 가능한 검색 Projection으로 사용하는 편이 안전합니다.

### JD-36. Microservice 경계와 데이터 일관성

**면접 답변:** 기술 계층보다 업무 Capability, 변경 주기, 데이터 소유권과 팀 책임을 기준으로 경계를 나눕니다. 각 서비스가 자기 DB를 소유하고 다른 서비스가 내부 Table을 직접 수정하지 않게 합니다. 서비스 간 원자 Transaction 대신 Saga, Outbox, 멱등 Event로 최종 일관성을 관리하며, 강한 일관성이 계속 필요한 데이터는 성급히 분리하지 않습니다.

### JD-37. 동기 API와 비동기 이벤트 선택

**면접 답변:** 호출 결과가 지금 바로 있어야 다음 결정을 할 수 있고 오류를 즉시 사용자에게 알려야 하면 동기 API가 단순합니다. 여러 Subscriber에게 사실을 전달하거나 호출자를 Downstream 지연과 장애에서 분리하고 Replay가 필요하면 비동기 Event가 유리합니다. 비동기는 지연·중복·순서와 관측 복잡성을, 동기는 시간 결합과 연쇄 장애를 대가로 가지므로 Timeout과 업무 완료 시점을 기준으로 선택합니다.

### JD-38. 로그, 메트릭, 트레이스 연결

**면접 답변:** 모든 요청과 Event에 Trace ID, Tenant ID, Event ID를 부여해 Ingestion부터 Broker, Consumer, 저장소까지 같은 문맥으로 연결합니다. 메트릭으로 오류율·P99·처리량·Lag의 이상을 발견하고 Trace로 느린 구간을 좁힌 뒤 구조화 로그로 입력과 결정 원인을 확인합니다. 고유 ID 같은 고카디널리티 값은 메트릭 Label에 넣지 않고 Trace나 Log에서 조회합니다.

## 7.7 제품·Fit 예상 질문

### JD-39. 왜 핵클인가

**면접 답변:** 회사 이름이나 A/B 테스트에 대한 막연한 흥미가 아니라 `행동 데이터 수집 → 분석 → 실험·기능 출시 → CRM → 성과 측정`의 닫힌 고리에서 어떤 고객 문제에 끌리는지 답합니다. 이어서 그 문제에 내 Java/Spring, 성능·정합성, 내부 플랫폼 경험 중 무엇을 바로 기여할지 연결합니다. 마지막에는 대용량 이벤트나 SDK처럼 입사 후 더 깊게 풀고 싶은 구체 영역을 한 가지 말합니다.

### JD-40. 중요한 목표를 위해 포기한 경험

**면접 답변:** 실제 사례를 `전체 목표와 마감 → 후보 작업별 Impact와 비용 → 포기한 기능과 감수한 위험 → 선택한 핵심 범위 → 결과와 후속 처리`로 답합니다. 단순히 시간이 없었다가 아니라 어떤 기준으로 고객 가치가 작은 일을 버렸는지 보여줍니다. 포기한 항목 때문에 생길 위험을 문서화하고 다시 판단할 시점도 정했다면 더 좋습니다.

### JD-41. 데이터로 판단을 바꾼 경험

**면접 답변:** 처음의 가설과 그 근거를 솔직히 말한 뒤, 어떤 지표나 실험이 예상과 달랐고 왜 믿을 만했는지 설명합니다. 그 데이터를 보고 결정·우선순위·설계를 어떻게 바꿨으며 결과가 어땠는지 연결합니다. 데이터가 완전하지 않았다면 한계와 추가로 확인한 Guardrail도 함께 말합니다.

### JD-42. 위험과 지연을 빠르게 공유한 경험

**면접 답변:** 위험을 처음 감지한 신호, 전체 일정과 고객에 미칠 영향, 아직 모르는 부분을 분리해 어떻게 공유했는지 답합니다. 문제만 던지기보다 가능한 선택지와 필요한 결정 시점, 다음 업데이트 시간을 함께 제시합니다. 조기 공유로 범위·일정·지원 인력이 어떻게 조정됐는지 결과까지 연결합니다.

### JD-43. 새 기술을 빠르게 학습한 경험

**면접 답변:** 기술 이름보다 `해결해야 했던 실제 문제 → 필요한 최소 학습 범위 → 공식 문서·작은 실험 → 안전한 적용 → 측정 결과 → 이후 보완한 이해` 순서로 답합니다. 모르는 부분을 숨기지 않고 위험이 큰 가정은 Spike나 Test로 먼저 검증했음을 보여줍니다. 학습 결과가 문서·테스트·공통 도구로 남아 팀에도 재사용됐으면 함께 말합니다.

## 7.8 JD 우대 스택 선택 기준

### JD-44. MongoDB와 RDBMS 선택

**면접 답변:** MongoDB는 한 Aggregate를 Document 하나로 읽고 쓰며 필드 구조가 자주 확장되는 데이터, 고정된 접근 패턴과 수평 분산에 적합합니다. RDBMS는 관계, Join, 제약 조건과 복잡한 Transaction이 중요한 데이터에 강합니다. MongoDB도 Transaction과 Index를 지원하지만 Embedding/Reference, Document 크기, Shard Key를 조회 패턴부터 설계해야 하며 “Schema가 없다”가 아니라 Schema를 애플리케이션이 관리한다고 보는 편이 정확합니다.

### JD-45. Kafka, SQS, Kinesis 선택

**면접 답변:** Kafka는 긴 보존·Replay·여러 독립 Consumer와 직접 운영/세밀한 제어가 필요할 때 적합합니다. SQS는 작업 Queue를 관리형으로 빠르게 운영하고 Visibility Timeout과 DLQ로 Consumer를 분리할 때 단순합니다. Kinesis는 AWS 안에서 Shard 기반 Event Stream과 관리형 연동이 중요할 때 후보가 됩니다. 순서 범위, 보존 기간, Replay, 처리량, 운영 인력, 다른 AWS 서비스와의 결합 비용으로 비교합니다.

### JD-46. 안전하고 재현 가능한 Docker Image

**면접 답변:** Base Image와 Dependency Version을 고정하고 Multi-Stage Build로 실행에 필요한 파일만 넣어 Image를 작게 만듭니다. Root가 아닌 사용자, 읽기 전용 파일 시스템, Secret 미포함, 취약점 Scan과 SBOM으로 공급망 위험을 줄입니다. 같은 Source와 Lockfile로 같은 결과를 만들고, Image는 환경별로 다시 Build하지 않고 설정만 주입해 한 Artifact를 승격합니다.

### JD-47. AWS Multi-AZ 이벤트 수집 설계

**면접 답변:** Multi-AZ Load Balancer 뒤에 Stateless Ingestion Service를 분산하고, Event는 MSK/Kinesis 같은 AZ 복제 Stream에 먼저 내구성 있게 기록합니다. 원본은 S3에 보존하고 DB는 Multi-AZ 구성과 명확한 Failover 정책을 사용하며 Consumer는 AZ별로 분산합니다. 한 AZ 장애 시 목표 처리량과 Buffer 시간을 계산하고 NAT, AZ 간 전송, IAM, Retry 폭주가 새로운 단일 장애점이 되지 않는지 확인합니다.

# 답변을 실제 말로 바꾸는 마지막 규칙

1. 첫 문장은 반드시 질문에 대한 직접 답으로 시작한다.
2. 나열만 하지 말고 “왜 그런가”를 한 문장 덧붙인다.
3. 절대 표현 대신 조건을 붙인다. 예: “항상 빠르다”가 아니라 “이 워크로드에서는 유리하다.”
4. 모르는 꼬리 질문은 추측하지 말고, 아는 경계와 확인 방법을 말한다.
5. 자신의 경험을 붙일 때는 `상황 → 선택 → 근거 → 결과/배운 점` 순서로 30초 안에 말한다.
