단순 서비스 로직 검증과 사용자가 실행해 볼 수 있는 작은 시스템 완성을 구분한다. Redis/Kafka 추가 자체를 목표로 삼지 않는다.

2026-09-14 사용자 정정 — 완성 가능한 HTTP 흐름과 조합 가능한 구현 계층:
다음 날로 넘어가는 요청을 현재 결제 실습을 버리고 새 도메인으로 교체하라는 뜻으로 해석하지 않는다. Day6 Order 과제는 철회하고 기존 Payment를 재사용한다. Controller에서 요청·응답을 실제 실행할 수 있게 제공하고 Service만 구현하는 빈칸 실습에 머무르지 않는다. Java는 줄바꿈·가독성을 갖춰 제공하며 현재 결제/Day6 범위의 Spotless 설정을 재사용한다. 과거 제외 요구는 과거 결함으로 소급하지 않고 오늘 추가 범위를 먼저 명시한다.


### 과제 문장 작성 원칙

중고등학생도 이해할 수 있는 말로 `실제 상황 → 직접 수정할 메서드 → 바꿀 값과 반환값 → 예시 표 → 오늘 제외한 범위` 순서로 쓴다. 용어를 먼저 나열하지 않는다. 예를 들어 “승인 이벤트를 멱등하게 반영” 대신 “같은 승인 연락이 두 번 와도 기존 결제 하나만 완료로 바꾸고 true를 반환”이라고 쓴다. 없는 경우의 false가 무엇을 뜻하는지도 설명한다. 사용자가 요구사항을 이해하지 못하면 자신의 설명부터 고치고, 이를 사용자의 설계 역량 부족으로 평가하지 않는다.
