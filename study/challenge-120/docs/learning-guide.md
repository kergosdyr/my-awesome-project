## 과제 이름과 설명

파일명과 첫 제목에 `C007`, `B007` 같은 식별자를 붙인다. 코딩·백엔드를 각각 한 문서로 나누고 [과제 목록](exercises/README.md)에 연결한다.

각 과제 앞에는 오늘 해결할 문제, 중요한 이유, 필요한 개념2~3개, 관찰 가능한 완료 기준2~4개를 적는다. 먼저 중고등학생도 이해할 상황·입력·기대 결과를 제시하고 용어로 설명을 대신하지 않는다. Java 주석에도 상황·입출력·제약·실행 명령·한계를 적는다.

- Coding: 입력·출력·설명 예제 최소3개. 작은 입력 수작업→느려도 정확한 구현→반복 작업 파악→최적화→이유·복잡도→자작 반례. 기본 정확성과 최적화를 따로 평가한다.
- Backend: **사용자가 먼저 예상하고 설계 선택을 한 뒤, 제공 실험으로 결과 차이를 확인**하게 한다. 구현할 메서드별 결과와 책임은 명확히 하되 핵심 처리 순서·답안을 미리 채우지 않는다.
- 9/16 정정: 조건문 몇 줄로 끝나고 선택할 것이 거의 없는 과제를 기본으로 반복하지 않는다. 재미는 기술 수가 아니라 실제 사건과 결과가 달라지는 판단에서 만든다. 이미 발행한 B007에 어려운 조건을 뒤늦게 붙이지 않는다.
- 제공 환경·직접 구현할 부분·입력 가정·제외 범위·완료 기준을 분리한다. 외부 장애·동시성을 요구한다면 재현 장치를 함께 제공한다.
- 테스트는 업무 결과를 검증한다. 특정 클래스 배치나 호출 순서·횟수로 동등한 해법을 탈락시키지 않는다. 관찰 실험 성공과 과제 해결 성공을 구분한다.

## 구현과 튜터링

사용자가 먼저 시도한다. 막히면 질문→작은 힌트→구체적 힌트→명시적 요청 시 해답 순으로 돕는다. 같은 추상 질문만 반복하지 않는다. 해답 요청은 허용하며 AI 해답 학습과 독립 도출을 구분한다. 평가용 업무 코드는 대신 수정하지 않는다. 컴파일을 막는 단순 문법 보완은 변경 사실을 밝히며 정책·알고리즘을 몰래 고치지 않는다.

기존 사용자 구현·반례·설계 선택을 보존한다. 이미 통과하는 기능을 다시 작성하도록 강요하거나 일부러 결함을 넣지 않는다. 새 과제는 실행 가능한 틀과 공개 테스트를 준비해 제공하며 사용자에게 테스트 도구 구현을 숙제로 넘기지 않는다.

## 커머스 경계

Spring Boot·JPA를 기본으로 한다. Controller는 API 요청/응답을 변환하고 서비스가 트랜잭션과 업무 흐름을 소유한다. Reader·Saver 등은 조합 가능한 객체이며 불필요한 interface/Impl을 만들지 않는다.

**JPA Entity는 유일한 infra 격리 예외다.** Service·Reader·Saver·Validator 등 업무 객체 전체와 API 응답 매퍼에서 공유한다. 순수 업무 복제 모델·왕복 변환을 만들지 않는다. JpaRepository·EntityManager·쿼리·DB 설정은 infra에 둔다. HTTP 응답은 별도 DTO다. 의미 있는 여러 객체 조합·계산 결과에만 Result를 둔다. Optional은 반환형으로만 사용하고 파라미터로 받지 않는다.

OSIV=false를 유지하며 응답에 필요한 데이터는 명시적으로 조회한다. 서비스에 검증용 flush/latch/callback/수동 트랜잭션을 넣지 않는다. 장애·동시성 장치는 테스트나 도구에 둔다. Palantir Java Format2.96.0을 유지한다.

## 평가와 기록

접근·정확성·선택의 비용·경계·장애·설명·독립성을 각0~5로 평가하되 관찰하지 않은 항목은 데이터 없음/N/A다. 미제출을 실패나0점으로 만들지 않는다. 독립성은 해답 그대로0, 해답 보고 재구성1, 구체 힌트2, 작은 힌트3, 유도 질문4, 도움 없이5이며 근거 없으면 추정하지 않는다. 초기 결과와 피드백 후 결과를 분리한다.
