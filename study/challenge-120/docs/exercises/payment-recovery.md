## Coding — C005 다음으로 더 높은 측정값

[NextHigher.java](../../src/main/java/challenge/coding/NextHigher.java)의 `findIndices(int[] values)`를 구현한다.
각 위치에서 오른쪽으로 처음 만나는 **엄격히 큰 값의 인덱스**를 반환한다. 없으면 -1.
입력은 null 아님, 길이 0..200,000, int 전체 범위. 입력 보존·새 반환 배열.
인덱스는 **0부터 시작**하며 값 자체가 아니라 위치를 반환한다.

**예제 1**

```text
입력: values = [2,1,2,4,3]
출력: [3,2,3,-1,-1]
```

위치 0의 2보다 큰 첫 값은 위치 3의 4다. 위치 2의 2는 같은 값이므로 제외한다.
위치 1의 1은 위치 2의 2를, 위치 2의 2는 위치 3의 4를 만난다.
위치 3과 4에는 오른쪽에 더 큰 값이 없다.

**예제 2**

```text
입력: values = [2,3,1,9]
출력: [1,3,3,-1]
```

위치 0의 답은 가장 큰 값 9의 위치 3이 아니라 처음 만나는 3의 위치 1이다.
위치 1과 2의 답은 모두 9의 위치 3이다. 마지막 위치의 답은 -1이다.

**예제 3**

```text
입력: values = [4,4,4]
출력: [-1,-1,-1]
```

같은 값은 엄격히 큰 값이 아니므로 모든 위치에 답이 없다. 빈 입력 `[]`의 출력은 `[]`다.

첫 시도는 `[3,1,3,2,5]`의 답을 손으로 적고 기본 구현부터 만든다. 기본 정확성과 O(n) 목표 달성은 따로 평가한다.
Minimum은 작은 입력 기본 구현까지. 공개 테스트10개 중7개를 실행한다. 최적화는 기본 풀이 이후 같은 시간 안에서 시도한다.

### 먼저 볼 문제 상황

예약1번을 1,000원에 결제한다. 아래 두 사건 중 하나가 발생한다.

| 시나리오 | PG에서 일어난 일 | 우리 서버에서 일어난 일 | 해결할 문제 |
| --- | --- | --- | --- |
| A. 응답 유실 | 승인1건 완료 | 제한 시간 안에 응답을 못 받음 | 실패라고 단정하지 않고 고객 재요청을 처리할 수 있는가? |
| B. 로컬 작업 중단 | 승인1건 완료 | 승인 직후 요청이 중단돼 로컬 DB 작업이 롤백됨 | 결제 행이 없거나 미확정이어도 같은 요청으로 복구할 수 있는가? |

B는 테스트 전용 Error로 요청을 중단해 외부 원장은 남고 로컬 쓰기는 롤백되는 조건을 만든다.
**실제 JVM을 종료·재시작하는 시험은 아니다.** 가짜 PG 원장이 프로세스 밖에서 영속되는지도 검증하지 않는다.
실제 서버 사망을 다룰 때도 이 두 상태가 갈라질 수 있다는 경계를 작은 환경에서 먼저 관찰한다.

### 용어와 PG 계약

- PG `APPROVED`: PG 승인 완료. `PROCESSING`: PG 접수 후 아직 승인 전(오늘 필수에서 제외).
- `ResponseLostException`: 응답을 못 받은 사건. 이 fake는 승인 후 예외를 던진다. 실제 모든 timeout의 PG 결과가 승인이라는 뜻은 아니다.
- 로컬 `PENDING`: 우리 서비스가 승인을 확정하지 못함. 타임아웃 자체나 승인 거절을 뜻하지 않는다.
- 로컬 `PAID`: 승인 결과를 확인하고 DB에도 완료를 기록함.
- 같은 PG key/예약/금액으로 `approve`를 호출하면 같은 결과이며 실제 승인은 늘지 않는다. 다른 payload는 충돌 예외다.
- `lookup(key)`는 기존 결과 조회이며 새 승인을 만들지 않는다. 없는 key는 empty다.

이는 이 가짜 PG의 명시적 계약이지 실제 PG 공통 규격이 아니다.
기존 타입의 PENDING/PAID 이름은 호환을 위해 유지한다. 어떤 상태를 언제 저장하고 어떻게 확인할지는 직접 결정한다.

### 구현할 범위

[PaymentService.java](../../legacy/main/java/challenge/payment/PaymentService.java)의 `pay`와 필요한
[PaymentRepository.java](../../legacy/main/java/challenge/payment/PaymentRepository.java) 조회를 작성한다.
기존 본문을 초기화하지 않는다. Spring/JPA·Entity·예약 ID fixture·가짜 PG·테스트는 제공한다.
필요하면 Entity/Repository와 트랜잭션 설정을 조정할 수 있으며 테스트를 우회하는 변경은 하지 않는다.

| 입력·사건 | 외부에서 확인할 완료 계약 |
| --- | --- |
| 없는 예약 | NOT_FOUND/null. PG 호출과 결제 행 생성 없음 |
| 정상 승인 | PAID/승인ID 반환, DB와 일치 |
| 응답 유실 | PENDING/null 또는 **실제로 결과를 재확인한** PAID/승인ID. DB와 반환이 일치 |
| 같은 예약·금액의 나중 재요청 | 기존 승인ID의 PAID, PG 승인1건·DB 결제1행 |
| PG 승인 직후 로컬 작업 중단 뒤 재요청 | 앞의 동일한 최종 계약. 중단 직후 DB 행의 존재 여부는 설계에 따라 달라도 됨 |
| 별개 예약2건 | 각각의 승인ID와 결제 행. 두 요청을 잘못 합치지 않음 |

오늘은 기존 예약·양수 금액·순차 요청만 다룬다. 같은 예약은 항상 같은 금액으로 재요청한다.
예약 생성·재고·인증은 구현하지 않는다. 승인 거절/환불/동시 요청/HTTP API/백그라운드 복구/브로커는 범위 밖이다.
`onNotification`, 다른 금액 충돌, PG PROCESSING은 후속 후보이며 오늘 완료 조건이 아니다.
기존 테스트와 사용자 확장 구현을 확인하는 PENDING 재요청 테스트는 `extension` 태그로 남겨 기본 실행에서 제외했다. 추가 숙제로 요구하지 않는다.

기존 **“첫 timeout에서 반드시 PENDING, 즉시 조회/재시도 금지”** 조건은 철회했다.
대신 자신의 응답 정책을 설명하고 두 정책 모두 중복 승인 없이 검증할 수 있어야 한다.
이번 구현은 작은 결제 복구 흐름이며 실제 결제 시스템 전체를 완성했다고 평가하지 않는다.
