# Challenge Day 7/120 · 2026-09-15 · 할인 종료 1초 뒤의 주문

1. **오늘 해결할 문제:** 29,000원으로 보고 주문한 티셔츠가 할인 종료 뒤 39,000원짜리 주문으로 만들어지는 일을 막는다.
2. **왜 중요한가:** 고객이 확인한 금액보다 비싼 주문이 생기고, 구매 의사가 없는 주문에 재고까지 잡힌다.
3. **오늘 배울 개념:** 화면 가격은 고객이 본 정보, 판매 가격은 서버가 현재 받는 금액이다. **주문 가격 스냅샷**은 주문할 때 정한 금액을 이후에도 보존하는 기록이다. **트랜잭션**은 주문을 거절했을 때 관련 재고 변경도 함께 남지 않게 하는 작업 묶음이다.
4. **완료 기준:** 가격 인상 시 안내와 함께 주문을 거절하고 주문·재고를 보존한다. 인하 정책을 선택하고 그 결과를 확인한다. 기존 주문의 결제 금액을 유지한다. 예상과 실제 결과의 차이·선택의 비용을 설명한다.

## 어제 결과와 오늘 새로 할 일

원래 IntelliJ 프로젝트에서 C006 9/9, B006 Payment 상태·알림 5/5를 확인했다. `Payment`와 `PaymentService`의 사용자 구현을 그대로 이어간다. 통과를 독립 설명·장기 기억 성공으로 평가하지 않는다.

Day5의 응답 유실·PG 승인 후 DB 롤백을 다시 출제하지 않는다. 오늘은 **정보를 본 시점과 구매를 확정한 시점이 다를 때, 무엇을 다시 확인해야 하는지**가 주제다. 기존 주문의 가격 보존은 이미 제공되는 동작이며 통과하면 재작성하지 않는다.

## 시작 전 3분: 실행하지 말고 먼저 예상하기

지금 코드를 고치기 전에 다음 상황의 예상만 짧게 말한다.

- 티셔츠가 29,000원일 때 A가 2장을 주문했다. 이후 가격이 39,000원이 됐다. A가 이제 결제하면 얼마가 승인될까?
- B는 29,000원 화면을 열어 둔 채 가격 변경 뒤 2장을 주문한다. **현재 코드**는 어떤 주문 금액과 재고를 남길까?
- 반대로 가격이 내려갔다면 바로 싼 가격으로 주문할까, 바뀐 금액을 다시 확인받을까? 고객 입장에서 이유를 하나 고른다.

두 번째 상황은 개선할 사건이며 첫 번째는 지켜야 할 기존 동작이다. 예상이 틀려도 감점하지 않는다. 실행 뒤 무엇을 새로 알았는지가 중요하다.

## B007 · Backend 작은 실험 · 45분

### 제공 환경과 직접 해결할 부분

| 제공됨 | 직접 결정·구현 |
| --- | --- |
| FORM 상품·옵션·주문·결제, Spring/JPA, 기존 트랜잭션 | 가격 인하 시 자동 적용 / 재확인 선택 |
| 화면에서 본 개당 가격을 `displayedUnitPrice`로 전달하는 FE·HTTP 입력 | 가격 확인 규칙과 안내 문구, 규칙을 둘 객체 |
| 양수 가격 필수 검증, 기존 주문 가격 기록 | 기존 주문·재고 흐름에 규칙을 연결하는 방법 |
| 실제 HTTP 서버·H2와 가격 변경·PG 관찰 테스트 | 결과와 이유를 설명하고 작은 변형 하나 예상 |

진입점은 [OrderService.java](../../src/main/java/challenge/commerce/domain/order/OrderService.java)의 기존 `create(CreateOrder)`다. `CreateOrder`에는 `optionId`, `quantity`, `displayedUnitPrice`가 있다. 메서드·처리 순서를 추가로 지정하지 않으며, 관련 domain 객체로 규칙을 옮겨도 된다. **주문 생성 본문은 이전 동작 그대로이며 가격 확인은 TODO다.**

HTTP 입력 예:

```json
{"optionId":201,"quantity":2,"displayedUnitPrice":29000}
```

`displayedUnitPrice`는 총액이 아니라 화면에서 본 **1장 가격**이다. 이를 서버 판매 가격이나 할인 쿠폰처럼 사용하면 안 된다. 누락·0·음수는 400이며, 기존 요청 도구와 FE에도 이 필드를 연결했다.

| 상황 | 기대 결과 |
| --- | --- |
| 본 가격 29,000 / 현재 39,000 | 409와 가격 재확인 안내. 주문·재고·결제 변화 없음 |
| 본 가격 29,000 / 현재 29,000 / 2장 | 201, 58,000원 주문. 재고 2 감소 |
| 본 가격 39,000 / 현재 29,000 | **선택:** 29,000원으로 주문 또는 409로 재확인. 과거 비싼 가격으로 주문하지 않음 |
| 거절 뒤 새 가격을 보고 다시 주문 | 새 판매 가격으로 주문 가능 |
| 요청 가격을 1원으로 바꿈 / 현재 39,000 | 409. 고객이 보낸 값을 판매 가격으로 사용하지 않음 |
| 58,000원 주문을 만든 뒤 상품 가격 변경·결제 | 주문 금액·PG 승인 금액은 58,000원 유지 |

409는 “현재 조건으로 그대로 주문할 수 없음”을 알리는 HTTP 응답이다. 기존 `BusinessException`의 오류 응답을 재사용할 수 있다. 정확한 메시지 문구·새 클래스 유무·내부 호출 순서는 채점하지 않는다. 안내가 가격을 다시 확인해야 한다는 뜻인지 사람이 확인한다.

구현 중 비교할 선택은 하나다: **인하 시 재확인은 구매 단계를 한 번 더 만들고, 바로 적용하면 고객이 마지막 화면과 다른 금액을 보게 된다.** 어느 쪽을 골랐는지 결과와 함께 설명한다.

### 가정·제외 범위

가격 변경은 주문 요청 **이전에 끝나며**, 요청은 순차 실행된다. 수량은1~5, 가격은 양수다. 오늘은 실제 FORM의 서버 판매 가격을 기준으로 한다. 이전 화면의 가격을 일정 시간 보장하는 견적 기능은 만들지 않는다.

주문 실행 도중의 동시 가격 변경, 쿠폰·배송비·세금·환불·회원·실제 PG·MySQL·JVM 재시작은 오늘 검증하지 않는다. 현재 테스트는 화면을 자동 조작하지 않고, 화면이 보내는 것과 같은 HTTP 요청을 보낸다. 개발자 가격 변경 버튼을 별도 숙제로 만들지 않는다.

완료 후 작은 변형: “수량을1장→3장으로 바꿔도 비교할 값과 기존 주문에 남을 금액을 설명할 수 있는가?” 추가 구현 없이 짧게 답한다.

## C007 · Coding · 30분

[SizeSearch.java](../../src/main/java/challenge/coding/SizeSearch.java)의 `firstAtLeast(int[] sizes, int target)`를 구현한다. 작은 값부터 정렬된 사이즈 중 `target` 이상인 첫 **인덱스**를 찾는다. 같은 값이면 가장 앞의 위치, 없으면 -1이다.

| 입력 | 출력 | 설명 |
| --- | --- | --- |
| `[90,95,95,100]`, 95 | `1` | 95 두 개 중 첫 위치 |
| `[90,95,95,100]`, 96 | `3` | 96은 없어도 100은 조건에 맞음 |
| `[90,95,95,100]`, 105 | `-1` | 조건을 만족하는 값 없음 |
| `[]`, 95 | `-1` | 빈 목록 |

배열은 null이 아니며 정렬되어 있다. 길이0~200,000, 원소와 target은 int 전체 범위, 중복 허용, 입력 변경 금지. 사이즈 이야기는 예시이며 음수·정수 경계도 포함한다. 잘못된 입력 검증은 제외한다.

손으로 예제 → 느려도 정확한 기본 풀이 → 반복해서 확인하는 일을 줄이는 순서로 시도한다. 목표 시간 O(log n), 추가 공간 O(1)이지만 기본 정확성과 최적화를 따로 평가한다. 공개9개 통과만으로 시간복잡도를 증명하지 않는다.

```sh
./gradlew test --tests '*SizeSearchTest'
```

[테스트](../../src/test/java/challenge/coding/SizeSearchTest.java)는 TODO로 인해9개 모두 실패하는 상태로 제공한다. 최초 제공 시 코드·패턴 해답은 채우지 않았다. 9/16 사용자의 명시적 해답 요청으로 설명을 제공했고, 이후 사용자 구현9/9 통과를 확인했다. 코딩은 마감하며 독립 해결로 평가하지 않는다.
