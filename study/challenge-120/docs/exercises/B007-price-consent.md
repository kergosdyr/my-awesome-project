# B007 — 할인 종료 1초 뒤의 주문

발행: Day7 · 2026-09-15. 코딩은 [C007](C007-SizeSearch.md)로 분리했다.

1. **오늘 해결할 문제:** 29,000원으로 보고 주문한 티셔츠가 할인 종료 뒤 39,000원짜리 주문으로 만들어지는 일을 막는다.
2. **왜 중요한가:** 고객이 확인한 금액보다 비싼 주문이 생기고, 구매 의사가 없는 주문에 재고까지 잡힌다.
3. **오늘 배울 개념:** 화면 가격은 고객이 본 정보, 판매 가격은 서버가 현재 받는 금액이다. **주문 가격 스냅샷**은 주문할 때 정한 금액을 이후에도 보존하는 기록이다. **트랜잭션**은 주문을 거절했을 때 관련 재고 변경도 함께 남지 않게 하는 작업 묶음이다.
4. **완료 기준:** 가격 인상 시 안내와 함께 주문을 거절하고 주문·재고를 보존한다. 인하 정책을 선택하고 그 결과를 확인한다. 기존 주문의 결제 금액을 유지한다. 예상과 실제 결과의 차이·선택의 비용을 설명한다.

원래 IntelliJ 프로젝트에서 C006 9/9, B006 Payment 상태·알림 5/5를 확인했다. `PaymentEntity`와 `PaymentService`의 사용자 구현을 그대로 이어간다. 통과를 독립 설명·장기 기억 성공으로 평가하지 않는다.

Day5의 응답 유실·PG 승인 후 DB 롤백을 다시 출제하지 않는다. 오늘은 **정보를 본 시점과 구매를 확정한 시점이 다를 때, 무엇을 다시 확인해야 하는지**가 주제다. 기존 주문의 가격 보존은 이미 제공되는 동작이며 통과하면 재작성하지 않는다.

## 시작 전 3분: 실행하지 말고 먼저 예상하기

지금 코드를 고치기 전에 다음 상황의 예상만 짧게 말한다.

- 티셔츠가 29,000원일 때 A가 2장을 주문했다. 이후 가격이 39,000원이 됐다. A가 이제 결제하면 얼마가 승인될까?
- B는 29,000원 화면을 열어 둔 채 가격 변경 뒤 2장을 주문한다. **현재 코드**는 어떤 주문 금액과 재고를 남길까?
- 반대로 가격이 내려갔다면 바로 싼 가격으로 주문할까, 바뀐 금액을 다시 확인받을까? 고객 입장에서 이유를 하나 고른다.

두 번째 상황은 개선할 사건이며 첫 번째는 지켜야 할 기존 동작이다. 예상이 틀려도 감점하지 않는다. 실행 뒤 무엇을 새로 알았는지가 중요하다.

## B007 · Backend 작은 실험 · 45분

### 제공 환경과 직접 해결할 부분

| 제공됨 | 직접 결정·구현 |
| --- | --- |
| FORM 상품·옵션·주문·결제, Spring/JPA, 기존 트랜잭션 | 가격 인하 시 자동 적용 / 재확인 선택 |
| 화면에서 본 개당 가격을 `displayedUnitPrice`로 전달하는 FE·HTTP 입력 | 가격 확인 규칙과 안내 문구, 규칙을 둘 객체 |
| 양수 가격 필수 검증, 기존 주문 가격 기록 | 기존 주문·재고 흐름에 규칙을 연결하는 방법 |
| 실제 HTTP 서버·H2와 가격 변경·PG 관찰 테스트 | 결과와 이유를 설명하고 작은 변형 하나 예상 |

진입점은 [OrderService.java](../../commerce/src/main/java/challenge/commerce/domain/order/OrderService.java)의 기존 `create(CreateOrderCommand)`다. `CreateOrderCommand.items`의 각 품목에는 `optionId`, `quantity`, `displayedUnitPrice`가 있다. 메서드·처리 순서를 추가로 지정하지 않으며, 관련 domain 객체로 규칙을 옮겨도 된다. 가격 확인은 사용자 구현으로 완료했으며, 아래의 다품목 확장은 사용자 요청으로 제공 환경에 반영했다.

HTTP 입력 예:

```json
{"items":[{"optionId":201,"quantity":2,"displayedUnitPrice":29000}]}
```

`displayedUnitPrice`는 총액이 아니라 화면에서 본 **1장 가격**이다. 이를 서버 판매 가격이나 할인 쿠폰처럼 사용하면 안 된다. 누락·0·음수는 400이며, 기존 요청 도구와 FE에도 이 필드를 연결했다.

| 상황 | 기대 결과 |
| --- | --- |
| 본 가격 29,000 / 현재 39,000 | 409와 가격 재확인 안내. 주문·재고·결제 변화 없음 |
| 본 가격 29,000 / 현재 29,000 / 2장 | 201, 58,000원 주문. 재고 2 감소 |
| 본 가격 39,000 / 현재 29,000 | **선택:** 29,000원으로 주문 또는 409로 재확인. 과거 비싼 가격으로 주문하지 않음 |
| 거절 뒤 새 가격을 보고 다시 주문 | 새 판매 가격으로 주문 가능 |
| 요청 가격을 1원으로 바꿈 / 현재 39,000 | 409. 고객이 보낸 값을 판매 가격으로 사용하지 않음 |
| 58,000원 주문을 만든 뒤 상품 가격 변경·결제 | 주문 금액·PG 승인 금액은 58,000원 유지 |

409는 “현재 조건으로 그대로 주문할 수 없음”을 알리는 HTTP 응답이다. 기존 `BusinessException`의 오류 응답을 재사용할 수 있다. 정확한 메시지 문구·새 클래스 유무·내부 호출 순서는 채점하지 않는다. 안내가 가격을 다시 확인해야 한다는 뜻인지 사람이 확인한다.

기존 IntelliJ 프로젝트의 터미널에서 실행한다. 별도 DB·서버 기동은 필요 없다.

### 가정·제외 범위

가격 변경은 주문 요청 **이전에 끝나며**, 요청은 순차 실행된다. 수량은1~5, 가격은 양수다. 오늘은 실제 FORM의 서버 판매 가격을 기준으로 한다. 이전 화면의 가격을 일정 시간 보장하는 견적 기능은 만들지 않는다.

주문 실행 도중의 동시 가격 변경, 쿠폰·배송비·세금·환불·회원·실제 PG·MySQL·JVM 재시작은 오늘 검증하지 않는다. 현재 테스트는 화면을 자동 조작하지 않고, 화면이 보내는 것과 같은 HTTP 요청을 보낸다. 개발자 가격 변경 버튼을 별도 숙제로 만들지 않는다.

완료 후 작은 변형: “수량을1장→3장으로 바꿔도 비교할 값과 기존 주문에 남을 금액을 설명할 수 있는가?” 추가 구현 없이 짧게 답한다.

## 제출 확인 · 2026-09-16

사용자는 ProductEntity.validatePrice에서 현재 가격과 요청 가격이 다르면 거절하도록 구현했고, OrderService는 재고 차감 전에 이를 호출한다. 이는 인상·인하 모두 다시 확인받는 허용된 선택이다. 누락된 세미콜론만 AI가 보완했으며 업무 조건·예외 선택은 그대로 두었다. 최초 확인은 HTTP400/409 차이로3/8 통과였다. 이후 사용자 요청으로 기존 `BusinessException.conflict`에 연결했고8/8 통과했다. 별도 예외 클래스는 추가하지 않았다. 별도 비어 있는 ProductValidator는 사용자 작성 중 파일로 보존했다.

### 이 과제의 가정과 한계

- displayedUnitPrice는 클라이언트가 보낸 비교값이며 “실제로 이 가격을 보았다”는 증거가 아니다. 서버 발급 견적·가격 보장 기능을 구현했다고 주장하지 않는다.
- 가격을 읽은 뒤 주문을 저장하기 전의 가격 변경은 실험하지 않았다. 조회값으로 만든 주문 금액을 보존하는 것과 항상 최신 가격으로 주문하는 것은 서로 다른 정책이다.
- 서버 상품 가격 하나만 있는 제공 환경이며, 쿠폰·고객별 가격·배송비가 있는 결제 총액 문제를 해결하지 않는다.
- 사용자는 과제가 너무 쉽고 선택할 부분이 적다고 평가했다. 동일 과제의 완료 기준에 새 조건을 덧붙이지 않는다. 다음 Backend는 업무 결과가 달라지는 선택과 관찰 가능한 실험부터 설계하며, 미리 처리 순서까지 제공하지 않는다.


### 다품목 주문으로 변경 · 2026-09-16

사용자 요청으로 단일 옵션 주문을 `OrderEntity`와 `OrderItemEntity`로 분리했다. 이는 B007 완료 조건을 추가한 것이 아니라 제공 환경의 설계 개선이다.

- 요청은 `items` 목록을 받는다. 한 주문은1~20개 품목, 옵션별 수량은 기존처럼1~5개다. 같은 옵션을 두 행에 나눠 보내면400이며, 화면에서는 같은 옵션을 합쳐 담는다.
- 각 품목의 가격을 확인한 뒤 재고를 차감한다. 하나라도 실패하면 주문·품목·모든 재고 변경을 함께 롤백한다. 재고 행은 옵션 ID 순으로 확보한다.
- 이름·옵션·이미지·단가·수량은 주문 품목에 기록한다. 주문 총액은 품목 금액의 합계이고 결제는 주문 전체에 한 번 요청한다.
- 응답은 `id`, `items`, `totalAmount`, `createdAt`이다. 기존 단일 품목 요청·응답 형식은 대체했고 FE·HTTP 도구·기존 테스트도 갱신했다.
- 주문 조회는 품목을 fetch join한 뒤 결제를 일괄 조회한다. OSIV=false에서도 API 변환 중 추가 SQL이 발생하지 않는다.

검토 포인트: 한 품목의 가격 인상과 다른 품목의 인하가 상쇄될 수 있으므로 합계만 비교하면 안 된다. 재고가 부족한 두 번째 품목에서 실패했을 때 첫 번째 품목의 차감도 되돌아가야 한다. `MultiItemOrderTest`가 이를 검사한다.

남은 범위: 가격 조회 이후 동시 가격 변경을 막는 잠금·견적 유효기간은 도입하지 않았다. 현재 H2는 실행마다 다시 만드는 제공 환경이며 기존 운영 DB의 스키마 마이그레이션은 포함하지 않는다. 주문 목록은 여전히 전체 조회이고, 장바구니는 브라우저 메모리에만 보관한다.
