# B008 — 쿠폰을 쓴 주문, 나눠 취소하면 얼마를 돌려줄까?

Day8 · Backend45분 / Minimum20분. [과제 목록](README.md)

## 먼저 사건부터

티셔츠1,000원짜리3개를 주문하면서100원 쿠폰을 썼다. 실제 낼 돈은2,900원이다.

- 하나씩 취소할 때 `2,900 / 3 = 966원`씩 돌려주면 전부 취소해도2,898원밖에 못 받는다.
- 매번967원씩 주면2,901원을 돌려준다.
- 마지막에 남은 상품에 전부 떠넘기면 취소 순서에 따라 고객별 환불 안내가 달라질 수 있다.

**구매할 때 개별 상품마다 돌려줄 금액을 미리 정해 두면 어떨까?** 예를 들어 고정된 상품 번호1,2,3에 `[967,967,966]`원을 붙인다. 같은 상품 번호를 취소한다면 한꺼번에 처리하든 나눠 처리하든 합계가 같다. 어떤 상품에1원을 더 배정할지는 네 정책이다.

1. **해결할 문제:** 가격·수량이 서로 다른 여러 품목에 쿠폰을 배분하고 개별 상품의 환불 금액표를 만든다.
2. **중요한 이유:** 전체 결제액은 맞아도 부분 취소에서 돈이 새거나 고객이 손해 볼 수 있다. ‘금액 비교 if’만으로 해결되지 않는다.
3. **핵심 개념:** 원 단위 정수 계산, 전체 금액 보존, 입력 순서와 무관한 고정 배분.
4. **완료 기준:** 아래 금액 조건을 지키는 계획을 만들고, 잔돈 우선순위·고정할 정보·다시 계산하면 안 되는 시점을 설명한다.

## 오늘 구현 범위

이번은 **실제 주문 데이터로 할인·환불 계획을 계산하는 읽기 전용 실험**이다. 실제 쿠폰을 적용하거나 취소·PG 환불을 실행하지 않는다. 기존 주문·재고·결제 금액은 그대로 유지한다. 실제 환불 기능을 구현한 것으로 평가하지 않는다.

제공 진입점은 [CouponRefundPlanner.plan](../../commerce/src/main/java/challenge/commerce/domain/pricing/CouponRefundPlanner.java)이다. 계산 방식·분해할 객체·중간 자료구조는 직접 정한다. 필요한 객체를 추가하거나 구조를 바꿔도 된다. 메서드 이름과 입출력은 공개 테스트의 진입점이므로 유지한다.

| 대상 | 찾아야 할 값 / 할 일 / 반환 |
| --- | --- |
| `plan(command)` — 직접 구현 | `lines`에서 옵션ID·단가·수량, `discountAmount`에서 전체 쿠폰 금액을 읽는다. 품목별 할인과 각 상품의 환불액을 결정한다. `CouponRefundPlanResult`를 반환한다. |
| `RefundLineResult` — 제공 결과 형식 | 옵션ID와 `unitRefundAmounts`를 담는다. 배열 길이는 해당 품목 수량. 배열 위치0부터 각각 상품 번호1,2,…에 대응한다. |
| `CouponRefundService.preview` — 제공 | 주문 당시 가격을 읽어 입력으로 만든다. 현재 상품 가격을 다시 쓰지 않는다. |
| `/dev/orders/{id}/coupon-refund-plan` — 제공 | 쿠폰 금액을 받아 계획을 JSON으로 보여준다. 금액 저장·PG 호출 없음. |

**네가 결정할 것**

- 나눠떨어지지 않는 할인액의 나머지를 어느 품목에 줄 것인가? 동률이면 무엇으로 순서를 정할 것인가?
- 한 품목 안의 여러 상품에 남는1원을 어떤 번호부터 배정할 것인가?
- 이 계획을 실제 주문에 적용한다면 어떤 값을 언제 저장해야 상품 가격 변경·취소 순서에 흔들리지 않을까? 이번에는 설명만 한다.

한 가지 알고리즘을 정답으로 강요하지 않는다. 아래 조건을 만족하고 같은 입력에 같은 결과를 내면 허용한다.

## 고정된 업무 조건

품목은 서로 다른 옵션1~20개, 수량은 각각1~5개, 단가는1~10^12원이다. 총액은 최대10^14원. 입력은 유효하며 배송비·세금·쿠폰 중복·쿠폰 제외 상품은 없다. 전체 쿠폰은0원부터 상품 합계까지이며 범위를 벗어나는 입력 검증은 제공한다.

1. **쿠폰은 품목의 원금 비율로 나눈다.** 품목 원금은 단가×수량. 예를 들어1,000원 품목과3,000원 품목에1,000원 쿠폰이면 할인은250원·750원이다.
2. 비율대로 나눈 값이 소수라면 **각 품목 할인은 정확한 몫의 내림 또는 올림**이어야 한다. 모든 품목 할인 합계는 쿠폰과 정확히 같아야 한다. 특정 품목에 쿠폰 전부를 몰아주는 방식은 안 된다.
3. 품목 안의 상품별 환불액 차이는 최대1원. 각 환불액은0원 이상 원래 단가 이하. 전체 환불액 합계는 **원금 합계−쿠폰**이다.
4. 옵션ID별 상품 번호에 붙은 금액은 고정이다. 요청의 품목 순서가 바뀌거나 같은 요청을 반복해도 같은 금액표를 반환한다. 결과의 품목 배열 순서 자체는 자유다.
5. 입력을 수정하지 않는다. 금액을 `float`·`double`로 근사하지 않는다. **결과가 long에 들어가도 중간 곱셈은 넘을 수 있다.**

| 입력·상황 | 기대 결과 |
| --- | --- |
| 1,000원×3 / 쿠폰100 | 한 가지 허용 결과 `[967,967,966]`. 합계2,900, 순서를 정하는 정책은 직접 선택 |
| 1,000원×1 + 3,000원×1 / 쿠폰1,000 | `[750]`, `[2250]` |
| 쿠폰0 | 각 상품 환불액은 원래 단가 |
| 쿠폰=원금 합계 | 모든 환불액0 |
| 같은 옵션들의 입력 순서를 뒤집음 | 옵션ID별 개별 상품 금액표 동일 |
| 먼저1번, 나중에2·3번을 취소한다고 계산 | 고정 금액표를 더하므로 한 번에1·2·3번을 취소한 금액과 동일 |
| 주문 생성 후 상품 가격 변경 | 기존 주문 가격을 기준으로 계산 |
| 실험을 반복 호출 | 원본 주문·재고·결제·PG 무변경 |

## 해답 구현 · 2026-09-17

사용자가 좋은 실제 구현을 요청해 AI가 `CouponRefundPlanner.plan`을 구현했다. 품목별 비례 몫을 BigInteger로 나눠 정수 할인과 나머지를 보관하고, 나머지 내림차순·동률은 optionId 오름차순으로 남은 할인1원을 배분한다. 확정된 품목 환불액을 수량으로 나누며 상품 번호가 작은 쪽부터 환불 잔돈1원을 준다. 핵심 계산은 한 메서드의 두 단계와 중간 결과 record 하나로 구성했다. 후속 사용자 요청으로 할인 몫 계산·Comparator 정렬·합계·순위별 배분·개별 환불액 생성을 Stream으로 변경했다. 배분 정책은 동일하다.

[사용자 작성 중 원본](../attempts/coupon-refund/B008-before-solution.java.txt)을 보존했다. 공개12/12·커머스 필수28/28·포맷 검사 통과. 실제 취소·PG 환불은 여전히 범위 밖이며 사용자 독립 해결로 평가하지 않는다.
