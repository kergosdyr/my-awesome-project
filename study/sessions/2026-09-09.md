# 2026-09-09 Kafka 전달·파티션·Spring Kafka 학습

## 오늘 다룬 것

- at-most-once, at-least-once, exactly-once의 차이
- Kafka topic, partition, message key와 partition 안의 순서
- consumer group별 offset과 같은 그룹 안의 partition 분담
- 한 worker 안에 여러 consumer group을 두는 구조
- Spring Kafka의 `KafkaTemplate`, `@KafkaListener`, `groupId`, `concurrency`

## 사용자가 자기 말로 연결한 내용

- consumer group ID가 다르면 offset도 별도로 관리된다고 설명했다.
- message는 topic 단위로 발행되고 partition은 한 topic을 나눈 단위라고 설명했다.
- partition을 샤딩과 비슷하게 보고 어떤 key를 기준으로 나누는지 질문했다.

## 질문으로 드러난 확인 대상

- exactly-once가 실제로 어디까지 보장되는지 질문했다.
- 카카오 알림처럼 여러 consumer가 있을 때 offset을 어떻게 관리하는지 질문했다.
- Spring에서 Kafka를 쓸 때 어떤 라이브러리와 코드로 partition·consumer group을 구성하는지 질문했다.
- 하나의 worker 안에서도 여러 consumer group을 분리할 수 있는지 질문했다.

## 오늘 새로 설명한 범위

- at-most-once는 offset을 업무 처리보다 먼저 확정하면 유실 가능성이 있고, at-least-once는 업무 처리 뒤 offset을 확정하므로 장애 경계에서 중복 가능성이 있다.
- exactly-once는 전달 횟수보다 최종 효과가 한 번 반영되는지를 봐야 한다. Kafka transaction은 Kafka에서 읽고 Kafka에 쓰는 결과와 input offset을 함께 commit할 수 있지만 MySQL이나 외부 API의 부작용까지 자동으로 묶지는 않는다.
- offset은 `consumer group + topic + partition` 단위로 저장된다. 같은 group의 consumer는 partition을 나눠 처리하고 다른 group은 같은 event를 각자 소비한다.
- message key는 partition 선택에 사용된다. 같은 `orderId`를 사용하면 관련 event를 같은 partition에 모아 partition 내부 순서를 유지할 수 있지만 편향된 key는 hot partition을 만들 수 있다.
- Spring에서는 보통 `spring-kafka`를 사용하고 `KafkaTemplate`로 발행하며 `@KafkaListener`로 소비한다. `groupId`는 논리적 구독자를, `concurrency`는 같은 JVM 안에서 같은 group의 consumer 수를 표현한다.
- 한 JVM 안에 서로 다른 `groupId`를 가진 listener 여러 개를 둘 수 있으며, 서로 다른 group은 같은 event를 각각 처리한다.

## 현재 판정

### 3. Coding C001 — 처리 예산 안의 가장 긴 연속 구간
longestBatch(int[] costs, long budget)를 Java로 구현한다.
costs는 원래 순서를 유지해야 하는 로그별 처리 비용이다. 비용 합이 budget 이하인 연속 구간 중 최대 길이를 반환한다. 해당하는 비어 있지 않은 구간이 없으면 0.
조건: costs는 null 아님, 길이 0~200,000, 각 값 0~1,000,000,000, budget 0~1,000,000,000,000,000. 입력 배열을 수정하지 않는다. 시간 복잡도 O(n), 추가 공간 O(1)을 목표로 한다. 충족하지 못하면 현재 풀이의 복잡도를 정확히 설명한다.
예시: [4,2,1,7,3], budget=8 → 3. [0,0,5], budget=0 → 2. [], budget=10 → 0.
제출: 초기 접근, Java 구현, 직접 고른 테스트와 결과, 시간·공간 복잡도.

### 4. Backend B001 — 마지막 예약 한 자리
Spring Boot 인스턴스 2개와 MySQL 8 한 대가 있다. event(event_id PK, remaining INT NOT NULL), reservation(reservation_id PK, event_id, user_id) 테이블을 사용한다. remaining은 예약 가능한 남은 자리 수다. 지금은 취소·결제·캐시·메시지 브로커가 없으며 모든 요청은 같은 DB에 접근한다.
요구사항: 같은 이벤트에 사용자는 최대 1건의 예약만 가진다. 성공은 예약 1건 생성과 remaining 1 감소를 함께 뜻한다. 실패한 요청은 둘 다 변경하지 않는다. remaining은 음수가 될 수 없다. 기존 예약의 재요청은 기존 예약을 반환하고 다시 차감하지 않는다.
Practical: POST /events/{eventId}/reservations의 핵심 Java 서비스 코드와 실행할 SQL, 필요한 스키마 변경을 작성한다. 인증된 userId가 주어진다고 가정한다. HTTP/ORM 보일러플레이트는 생략 가능하나 트랜잭션 범위, SQL 순서, 결과·예외 분기를 구체적으로 쓴다. 실제 DB 실행이 안 되면 검증 전이라고 표시하고 재현 가능한 테스트 절차를 제출한다.
Design: 이 서비스를 이벤트 1개에 초당 2,000건의 예약 시도와 10,000건의 잔여 좌석 조회가 들어오는 상황으로 확장한다. 조회는 최대 3초 지연 가능하나 확정 예약 수는 정원을 넘으면 안 된다. 구성도 또는 요청 흐름, 병목 후보, 대안 두 개와 선택 근거를 설명한다. 특정 제품 사용은 필수가 아니다.
Failure: 부하 테스트에서 remaining=1로 시작해 서로 다른 사용자 두 명에게 201이 반환됐고, reservation은 2행 늘었는데 remaining=0이다. 오류 로그는 없다. 가능한 실행 순서 하나, 가설을 판별할 증거, 재현 테스트, 가장 먼저 확인할 지점을 제시한다. 실제 원인은 미확정이며 제공한 관찰만으로 단정하지 않는다.
Project Deep Dive: 실제 본인 프로젝트 한 건에서 어려웠던 기술적 결정, 본인 기여, 대안, 결과 근거, 지금 다시 한다면 바꿀 점을 설명한다. 수치가 없으면 없다고 한다.
Technical explanation: 자료를 닫고 방금 작성한 예약 처리에서 트랜잭션이 보장하는 것과 별도로 확인해야 할 것을 동료에게 5~8문장으로 설명한다.

### B001 낙관적 락 시도 검증 및 Coding 지도 방식 승인

사용자가 느려도 맞는 풀이부터 최적화하는 진행 방식을 승인하여 자동화와 운영 문서에 반영했다. 같은 추상 질문을 반복하지 않고 막힌 사고 단계를 설명하되, 초기 Benchmark 조건과 독립/도움 후 평가를 구분한다.
사용자는 Event에 @Version int version을 추가했다. 첫 실행은 schema.sql 컬럼 누락으로 실패했다. AI가 선택된 엔티티 매핑을 실행 가능하게 맞추는 범위에서 version INT NOT NULL DEFAULT 0을 추가했다. 저장 실패 테스트가 스키마 오류도 DataAccessException으로 받아 거짓 통과했으므로 DataIntegrityViolationException으로 assertion을 좁혔다. 사용자 서비스 로직은 변경하지 않음.
재실행 결과 H2 Backend12개 중6개 통과(인프라1+순차5). 동시성2시나리오*3회는 모두 ObjectOptimisticLockingFailureException으로 실패. 이전 초과 성공/다중행 조회와 달리 버전 충돌을 감지하는 실행 근거가 생겼다. 단, 테스트가 예외로 중단되어 해당 동시 실행의 최종 DB 불변식까지 검증 완료라고 주장하지 않는다. MySQL은 미검증.
잠정 Backend: 접근3(명시적 충돌 검출 도입), correctness2(응답 계약 미완성), edge2, failure2(충돌 검출은 개선했으나 처리 미완성), trade-off·설명·독립성 데이터 없음. 초기 평가를 덮어쓰지 않는다. 스키마 준비 도움은 독립성 감점에서 제외한다.
다음은 새 과제가 아니라 B001의 충돌 이후 서비스 응답 완성이다. 먼저 마지막 자리에서 성공1/나머지SOLD_OUT/예약1/잔여0, 이후 동일사용자 동시재요청에서 CREATED1/나머지EXISTING/동일예약ID/차감1을 목표로 한다. Java 문제 주석에 추가했다. 질문: 모든 낙관적 락 충돌을 SOLD_OUT으로 처리하면 두 시나리오 모두 맞는가? 정답 구현이나 재시도 경계 코드는 제공하지 않았다.

### B001 비관적 락과 hot row 질문

사용자는 @Version을 제거하고 EventRepository에 PESSIMISTIC_READ를 적용했다. 기존 예약 조회는 이벤트 락 획득 전에 수행한다. 사용자 서비스/테스트는 수정하지 않았다.
H2 재검증: 정상/순차5개와 마지막자리3회 통과, 같은사용자 동시재요청3회 실패(단일조회에 2/4/6개 행). 인프라 검사가 findByIdWithLock을 트랜잭션 밖에서 호출하도록 바뀌어 TransactionRequiredException으로 별도 실패했다. 기능 결과는 인프라 제외8/11이며 종료 후 MySQL은 미검증.
현재 PESSIMISTIC_READ는 쓰기 배타 락과 동일한 요청이 아니다. JPA는 READ를 WRITE로 대체하는 구현을 허용하며 갱신 시 락 승격이 필요하므로 H2 성공을 MySQL 공유 락 동작의 증거로 삼지 않는다.
설명: 단일 event row 경합은 비관적 락에서 대기 비용, 낙관적 방식에서 충돌/롤백/재시도 비용으로 나타날 수 있다. 낙관적 방식도 DB 갱신 락을 없애지 않는다. 낙관적 락만으로 응답 계약은 완성되지 않지만 실패 트랜잭션 종료 후 새 트랜잭션/영속성 컨텍스트의 재판단과 적절한 재시도 및 사용자-이벤트 유일성 보장으로 구현 가능. 제한된 재시도가 모든 요청의 무조건 성공/정상응답을 보장하는 것은 아니며 소진/타임아웃 계약도 필요하다.
다음 질문: 같은 사용자의 두 요청이 락을 잡기 전에 둘 다 기존예약없음을 확인하면, 뒤늦게 event 락을 얻은 요청의 그 판단은 여전히 유효한가? 정답 코드 제공 없이 검사 순서와 보호 범위부터 점검한다. hot row 우려는 타당한 trade-off 문제 제기이며 실제 처리량·지연 측정은 아직 없음. 잠정 trade-off2(경합 비용을 짚었으나 낙관적 불가능 판단은 교정 필요); correctness는 동일 사용자 계약 잔존으로2 유지.
출처: https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html (3.5.4.2, 낙관적 충돌 후 새 트랜잭션 재시도), https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html .

### B001 쓰기 락·검사 순서 수정 검증과 락 설명

사용자가 PESSIMISTIC_WRITE로 변경하고 event 락 조회를 기존 예약 조회보다 앞에 배치했다. 서비스 구현은 AI가 수정하지 않음. H2 기능11개(순차5+동시성2종각3회) 모두 통과. 인프라 테스트는 트랜잭션 밖 findByIdWithLock 호출로 실패해 연결/매핑 검사 목적에 맞는 원래 일반 findById로 수정하고 그 테스트만 재실행해 통과. 기능 검사 완화는 없음.
확인된 개선: 이전 동일사용자 중복 재현이 현재 공개 테스트에서 해소, 마지막자리·재요청·저장실패 원복 유지. 전체12개는 두 실행을 합쳐 통과 확인; MySQL·성능·다른 실행 경로는 미검증. 설명 후 사용자 수정이므로 독립적인 새 문제 해결이나 락 개념 숙달로 평가하지 않는다. 사용자는 READ/WRITE 차이를 아직 잘 모르겠다고 명시했다.
설명 범위: READ는 공유(S), WRITE는 배타(X)라는 기본 모델; S-S 호환/S-X·X-X 충돌; READ로 읽은 뒤 쓰면 승격 필요, 둘이 S 보유 후 X 요구 시 교착 가능; WRITE는 조회 시점부터 수정 요청을 직렬화; 일반 SELECT는 InnoDB의 보통 RC/RR에서 MVCC 읽기로 진행 가능; 락은 조회 함수가 끝날 때가 아니라 트랜잭션 종료까지 유지; 이벤트 락 하나를 같은 이벤트 예약 흐름의 진입 순서에 이용한 것이지 예약 테이블 모든 행까지 자동으로 잠근 것은 아님. JPA READ→WRITE 대체 허용/DB별 차이와 실제 MySQL 검증 한계 명시.
잠정 Backend correctness3/edge3(공개 요구사항 통과), 접근3, failure3(현재 저장실패 및 동시성 검증), trade-off2(경합 질문했으나 측정·비교 미완료), 설명·독립성은 추가 검증 필요. 원래 초기점수는 보존한다. 다음 주제 추가 없이 설명 이해와 현재 구현의 트랜잭션 경계를 확인한다.
출처: Jakarta Persistence 3.2 §3.5.4.2; MySQL 8.0 Locking Reads (앞선 답변에서 조회한 공식 문서).
