## 추가 학습 계획 — Kotlin Redis·Kafka 호환 서버

사용자는 Kotlin 경험이 없다고 밝혔으며, AI를 튜터로 두고 Kotlin으로 Redis와 Kafka를 직접 만들어 실제 Redisson·Spring Kafka를 연결하고 유량 제어 등을 실험하는 학습 계획을 요청했다.

[계획](../plans/kotlin-redis-kafka-lab.md)을 학습 목록에 추가했다. 공식 프로토콜 문서와 Redisson 소스를 검토해, 단일 노드·지정 버전·선택 기능 호환을 목표로 Kotlin 입문→Redis→Redisson 유량 제한→Kafka→Spring Kafka→그룹·통합 실험 단계를 제안했다.

사용자 핵심 구현·AI 테스트/환경 준비, 기존 구현을 이어서 확장하는 방식을 계획에 반영했다. 현재는 미착수이며 기간은 추정이다. 실제 클라이언트 연결·구현·부하 검증은 수행하지 않았다. 사용자 회상 답변이나 학습 완료 판정은 없고 복습 일정·자동화는 변경하지 않았다.

### Day4 — 사용자 애너테이션 재시도 제출 확인

사용자가 ReservationService.reserve에 @Retryable(OptimisticLockingFailureException, maxAttempts=3, backoff100ms/2배)을 추가하고 기존 @Transactional을 유지했다. RetryingReservationService의 3인자 진입점은 TODO 상태다. 업무 코드는 수정하지 않고 실제 Spring 빈을 호출하는 AnnotatedReservationRetryTest를 추가했다. MySQL에서 커밋 직전 충돌1회 후 새 엔티티로 성공·중복 예약 없음, 충돌3회 소진·전체 원복, 정상 반환 즉시 종료의3개 검사가 통과했다. 기존 예약/취소 회귀14개도 통과, 합계17/17. 외부 트랜잭션 없는 Spring 빈 호출 조건의 고정3회 재시도는 동작한다. 원래 B004의 요청별 maxAttempts1~3 및 범위 검증/새 진입점 계약은 미완료다. 기존 단일시도 원복 fixture는 원본 서비스가 재시도하게 된 변경으로 기대가 달라졌으므로 그 실패를 재시도 결함으로 해석하지 않는다. 사용자 질문: 요구사항을 충족하는지, 트랜잭션 설명은 무슨 뜻인지 모르겠다고 했다. 트랜잭션 경계 독립 이해는 미확인이고 직전 제공 예시를 활용한 수정이며 독립 구현 Pass로 기록하지 않는다.


### Day4 — 사용자 요청: 실제 재시도 성능 비교

사용자는 요청별1~3회 선택 조건의 업무 근거가 없다고 지적했고 고정 최대3회 기준을 수용했다. 요청별 maxAttempts와 새 TODO 진입점을 필수 과제로 요구했던 조건은 철회했다. 기존 ReservationService의 사용자 @Retryable 구현을 보존하고 그 코드로 재시도 성능을 측정해 달라고 요청했다. 질문은 실제로 재시도가 충돌 자체를 개선하는가였다.

기존 load-comparison 어댑터와 Nginx/k6/관측 도구를 확장했다. RetryObservation은 테스트에서 retry advisor만 OFF로 제거할 수 있고 ON에서는 실제 사용자 annotation과 backoff를 그대로 사용한다. 트랜잭션 바깥·retry 안쪽에서 각 시도의 커밋 충돌을 집계하고 최상위 요청·첫 충돌·재시도 복구·최종 실패를 별도로 수집한다. 테스트2개에서 내부 충돌 집계/복구와 retry OFF에서도 롤백 유지가 통과했다. 첫 테스트의 Mockito stubbing 호출이 계측에 포함된 것은 계측 설치를 stubbing 후로 옮겨 수정했다. 사용자 main 코드는 변경하지 않았다.

MySQL8.4.9·DB풀32·HTTP worker128·Nginx유휴1024·JDK유휴2048. 단일 이벤트 정원100만·조회 인덱스·고유 사용자 예약만 초당200회, 각40초. k6클라이언트 재시도 없음. OFF→ON→ON→OFF, 각 독립 MySQL. 전용 워밍업 없는 탐색이며 동시1000VU 유지 실험이 아니다.

OFF 합산16,001요청/14,705성공/1,296충돌·최종실패. ON 합산16,002요청/20,463시도/14,731성공/5,732충돌/첫충돌2,648/복구1,377/최종실패1,271. 첫시도 충돌률8.10%→16.55%, 최종실패율8.099%→7.943%, 성공/부하주입초183.81→184.14. 성공HTTP p95는 OFF 각6.28·7.55ms, ON 각115.96·120.00ms. 지연분포를 합치지 않고 실행별 p95 범위를 보고한다. 사용자 코드 SHA-256은 네 실행에서 동일하다.

### Day4 — 낮은 경합의 재시도 전후 비교

사용자는 경합이 드물게 발생하면 재시도 이득이 클 것이라는 가설로 전후 비교를 요청했다. 앞선 단일 이벤트 결과를 모든 낙관적 락 재시도의 일반적 결론으로 해석하지 않도록 범위를 구분했다.

전체200req/s는 유지하고16개 이벤트에 고정 해시로 분산했다. 총 재고100만(각62,500), 같은 요청 인덱스는 같은 이벤트, 고유 사용자ID, 원본 예약 코드는 보존했다. 테스트 HTTP 어댑터에 이벤트 입력·이벤트별 재고 불변식/요청 카운터를 추가하고 응답 시도 횟수로 첫시도 성공/재시도 복구 지연을 나눴다. 공유 테스트 코드 컴파일, 실제 MySQL3초 스모크(301요청·불변식0·오류0), 계측2개 검사가 통과했다.

초기 워밍업 없는4회 OFF→ON→ON→OFF를 sparse16-*에 보존했다. 첫 OFF의345충돌 중227이 시작 약4초에 몰렸다. 초기 구동 영향을 분리하려고 같은200req/s로15초 워밍업 후40초 본 측정을 하는 별도4회 sparse16-warm-*를 수행했다. 워밍업 데이터는 삭제하지 않고 사용자ID 영역을 분리, baseline 이후 누적 카운터 차이만 본 측정에 사용했다. 본 측정 k6 지연분포는 워밍업 요청을 제외한다. 전용 머신/통계적 정상상태를 입증한 실험은 아니다.

워밍업 후 합산 OFF/ON 모두16,001요청. OFF 성공15,847·첫충돌/최종실패154(0.962%). ON 성공15,985·전체시도16,239·첫충돌189(1.181%)·전체충돌254·복구173·최종실패16(0.100%). ON 추가시도238회(+1.49%), 최종실패율 상대89.6% 감소(절대0.862%p). ON 첫충돌189 중173 복구(91.5%). 성공 p95 실행별 범위 OFF6.55~8.16ms/ON5.91~11.58ms, p99 OFF17.73~26.65ms/ON27.51~138.53ms, p99.9 OFF48.76~148.71ms/ON150.67~435.60ms. 복구 요청 평균은 각146.78·217.24ms다. 실행별 분위수를 평균내거나 합친 분위수로 보고하지 않았다.

해석: 이번 낮은 경합 모델은 적은 추가 DB 시도로 최종 실패를 크게 줄이는 효과를 보여준다. 첫충돌/전체충돌 감소를 보여주지는 않는다. 속도나 모든 상황의 자원 효율 개선, 비관적 락 대비 우위를 증명하지 않는다. 두 조건 각각2회이며 초기 워밍업 없는 단일 이벤트 실험과 정확한 효과 크기를 직접 비교하지 않는다. 사용자의 가설과 측정 근거를 구분하며 독립 학습점수/회상 성공은 새로 만들지 않는다.

검증: 워밍업과 본 측정 모두 k6 exit0·예상 밖 HTTP오류0·dropped iterations0. 최종 및 표본 이벤트별/전체 재고 불변식 위반0. 요청=성공+실패, 시도=성공+충돌, 첫충돌=복구+실패, 측정성공=DB예약증분을 확인했다. 동일 요청 수 실행의 이벤트별 분포 일치 및 사용자 코드 SHA동일을 확인했다. 실행 원본은 기존 결과와 별도 보존한다. ### Day4 마무리 — 재시도 결론, 최종16건 재확인, 다음 과제 방향

사용자 요지: 비관/낙관 락 비교가 반복돼 과제가 단조롭고 실무에서 생각할 문제가 필요하다. 재시도 학습을 기록해 달라고 요청했다. 낮은 경합에서 Retry로 낙관적 락을 방어할 수 있다고 정리했으며, 재고100만·이벤트16개 분산·총3회 시도에도 최종16건 실패가 발생한 이유를 질문했다. 이는 실제 사용자 질문/자기 설명이며 일반 상황 전체에 대한 실험적 증명과 구별한다.

원본 재확인: sparse16-warm-on1 본 측정은 최종0건, on2는16건이다. on2 baseline 최종실패3(워밍업), 종료19이며 본 측정16이라는 차이 집계가 정확하다. reserve_conflict_count와도 일치한다. 현재 RetryObservation은 재시도 내부의 충돌과 최종 외부 충돌을 구분하며 사용자 설정은 총3회다. 본 측정 CONFLICT16건의 HTTP 지연은359.19~577.78ms, 평균461.75ms로100+200ms 대기를 포함한 설정과 부합한다. 개별16건의 시도별 SQL/버전/이벤트 trace는 수집하지 않아 각각의 충돌 상대 및 직접 원인은 확정하지 않는다.

시계열: on2의 측정2.04~4.07초 구간에 최종실패2건, 4.07~6.09초13건, 6.09~8.15초1건.16건 모두 약2~8초 구간에 집중됐고 이후 종료까지 추가 최종실패0건이다. 따라서 낮은 평균 충돌률이 시간 전체에 균일하게 적용된 독립 실패라고 보고 확률을 세제곱하는 해석은 맞지 않는다. 짧은 집중 경합/처리 지연은 가능하지만 평균/2초 표본만으로 GC·DB·스케줄링 중 어느 원인인지 특정하지 않는다.

코드 확인: Event 하나당 remaining 숫자와 @Version 하나가 있는 구조다. 총100만 재고는16행에 각62,500이라는 값으로 저장되며 물리적인 재고100만행이 아니다. 같은 이벤트 예약은 같은행/version을 갱신하므로 재고 수량과 버전 경합 대상 수는 다르다. 예를 들어 남은62,500/version10을 A/B가 함께 읽으면 A 성공 후 B는 남은자리가 충분해도 이전version10으로 갱신할 수 없어 충돌한다. Hibernate 공식 optimistic locking 설명 확인: https://github.com/hibernate/hibernate-orm/blob/main/documentation/src/main/asciidoc/userguide/chapters/locking/Locking.adoc .

학습 결론은 "재시도는 희소한 일시 충돌을 적은 추가시도로 복구할 수 있다. 이번 모델에서 최종실패154→16, 시도+1.49%였지만 충돌예방/무조건 성공/일반 트래픽 전체의 효율을 보장하지 않는다"로 남긴다. Retry 범위는 마무리하고 이후 같은 락 변경·재측정을 기본 과제로 반복하지 않는다.

다음 과제 후보(미발행): 기존 예약에서 이어지는 외부 결제 응답 유실. 결제사 승인 성공 후 응답 timeout, 사용자 재요청, 늦은/중복 승인 알림을 주고 중복청구 방지·결과 미확정 응답·예약/주문 최종상태를 설계/구현한다. 정답 패턴은 선제공하지 않고 가짜 결제사/장애/콜백 테스트는 AI가 준비한다. 새 Day/추가 숙제로 발행하지 않았고 현재 사용자 선호를 다음 설계에 반영한다.

### Day4 후속 질문 — 대규모 서비스의 낙관적 동시성 제어

사용자는 전체 TPS가 높은 서비스에서 동시 구매와 최종 실패가 늘지 않는지, 실제 기업은 낙관적 락을 어디에 어떻게 사용하는지 질문했다. 공식 기업 기술 글과 API 문서를 조사했다. 아래는 제공한 설명이며 사용자 독립 이해/회상 성공으로 기록하지 않는다.

- 전체 TPS보다 같은 갱신 대상에 몰리는 쓰기 빈도, 읽기부터 조건부 갱신까지의 시간, 순간 집중도가 중요하다. 다른 주문/고객에 분산된 요청과 같은 재고 행에 집중된 요청을 구분한다. 재고 숫자를 키우는 것만으로 version 경합이 분산되지 않는다.
- [Shopify 재고 API CAS](https://shopify.dev/changelog/finalizing-compare-and-swap-redesign-for-inventory-set-quantities): API 2026-04의 changeFromQuantity로 예상 현재 수량을 조건으로 갱신한다. 값이 달라졌으면 충돌을 반환해 오래된 상태의 덮어쓰기를 막는다. JPA @Version과 구현은 다르며 Shopify 구매 전체가 낙관적 락이라는 근거가 아니다.
- 같은 회사의 [실제 재고 예약 설계](https://shopify.engineering/scaling-inventory-reservations)는 단일 수량 행 경합을 피하려고 재고 단위별 행의 제한된 풀과 MySQL SKIP LOCKED를 사용한다. 품목/위치당 풀 상한 1,000행이며 원장으로 보충한다. 같은 회사도 API 갱신과 집중 예약 경로에 다른 동시성 제어를 쓴다.
- [Uber The Accounter](https://www.uber.com/au/en/blog/the-accounter/): 차량 호출이 아닌 인프라 작업 승인 시스템이다. etcd 조건부 트랜잭션으로 작업 그룹 상태를 확인하고 낙관적 충돌은 제한 재시도한다. 메모리 상태로 명백한 거절을 미리 걸러내고, 동시 실행/속도 제한 및 거절 후 호출자의 재시도를 결합한다. 글의 초당 3,000~4,000 claim 시도 요구에는 대부분 dry-run이 포함되므로 성공 DB 쓰기 TPS로 인용하지 않는다.
- [채널톡 DynamoDB 사례](https://aws.amazon.com/blogs/database/how-channel-corporation-modernized-their-architecture-with-amazon-dynamodb-part-3-user-and-badge/): 배지 갱신의 트랜잭션 충돌과 재시도 비용 때문에 User와 UserBadge를 분리했다. 배지 트랜잭션 제거/분산 락은 향후 검토 사항이며 이미 적용한 것으로 설명하지 않는다.

설명 요지: 낙관적 충돌 한 번과 최종 업무 실패는 다르지만 제한 재시도도 성공을 보장하지 않는다. 기업 규모 자체가 선택 기준이 아니며 경합 단위 분리, 짧은 처리 구간, 진입량 제어와 업무별 복구 정책을 함께 설계한다. 이번에는 실험 재실행이나 사용자 업무 코드 변경 없이 출처 조사와 학습 기록만 추가했다.
