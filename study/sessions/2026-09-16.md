# 2026-09-16 학습 기록

## C007 — 이진 탐색 구현 해설 요청

사용자는 O(n) 기본 풀이를 간단하게 만들었다고 말했으며, 이진 탐색의 접근·구현 방법을 모르겠다고 질문했다. 튜터가 가운데 값이 조건을 만족하면 답 후보를 기억하고 왼쪽을 확인하는 설명을 제공했으나, 사용자가 “아 모르겠다 구현좀 알려줘”라고 명시적으로 해답을 요청했다.

현재 SizeSearch.java에는 가운데 인덱스와 비교 조건만 작성된 이진 탐색 시도가 있다. O(n) 완성본은 현재 파일에서 확인하지 못했으므로 해당 정확성·테스트 통과는 사용자 자기보고와 구분한다. 사용자 파일은 수정하지 않고, 대화에서 left/right의 양끝 포함 범위와 answer 후보를 사용하는 Java 정답 및 범위 축소 이유를 제공한다. 빈 배열은 반복문을 건너뛰어 -1, 조건을 만족하면 후보 저장 후 더 앞을 탐색하며 만족하지 않으면 가운데까지 제외한다.

이번은 AI 해답 제공 단계이며 독립 이진 탐색 구현·이해 완료·코딩 마감으로 평가하지 않는다. 사용자 시도는 그대로 보존했다. 실제 시간·정답 적용 후 테스트·자료 없는 재설명은 아직 미확인이다. 추가 숙제나 퀴즈를 발행하지 않는다.

### C007 — 최초 접근 설명: 가운데에서 재귀로 이어가기

사용자는 처음에 `mid = length / 2`로 시작하고 이를 재귀로 어떻게 만들지 고민했다고 설명했다. 이는 잘못된 접근이 아니며, 튜터는 재귀와 반복 모두 남은 탐색 범위의 양끝(left/right)이 필요함을 설명한다. 매번 전체 길이의 가운데를 계산하는 대신 현재 범위의 가운데를 구하고, 재귀에서는 줄인 범위를 다음 호출의 인자로 넘기며 반복에서는 변수를 갱신한다. 오늘 구현의 양끝 포함 범위·종료 조건과 다른 경계 규칙을 섞지 않도록 설명한다. 재귀 구현을 직접 완성하거나 독립 이해를 검증한 것으로 기록하지 않는다.


### C007 코딩 마감·커밋 요청

사용자는 설명 후 “이해했어”라고 말했고 커밋·푸시 후 백엔드 과제를 진행하겠다고 요청했다. 실제 파일에 반복형 이진 탐색 구현이 작성되어 공개9/9를 통과했다. 구현의 시간 O(log n), 추가 공간 O(1)을 확인했다. AI 해답을 본 뒤의 구현 통과이며 독립 도출·지연 회상 성공으로 평가하지 않는다. 실제 소요시간은 미확인이다.

커밋 전 검사: C007 9/9, C006 9/9, Day6 상태/알림5/5, 제공 환경9/9, 기존 필수15/15 통과. B007 가격 확인8개 중4개는 미구현 실패로 유지했다. 전체 성공으로 표시하지 않고 백엔드 업무 답안은 변경하지 않는다. 커밋 범위는 challenge-120의 Day6·7 변경과 관련 세션 기록이다.

## FORM 계층 경계 개선 — 사용자 설계 피드백

사용자는 Optional 파라미터, 서비스 내부 중첩 Command, 서비스 조회 결과의 API 응답 직접 노출을 지적하고 API 입력·응답과 내부 Command/Query/Result를 분리하는 방향을 제안했다. 실제 Optional 파라미터는 OrderQueryService.details 한 곳에서 확인했다. 이는 사용자의 실제 설계 판단이며 점수·독립 구현 성공으로 확장하지 않는다.

AI가 제공 환경의 경계를 정리했다. CreateOrderRequest→독립 CreateOrderCommand, OrderDetailsResult→OrderDetailsResponse로 분리하고 주문 객체는 OrderResponse로 변환한다. 상품·결제 공개 API에도 별도 Response를 적용했다. Optional 반환형은 유지하면서 Optional 파라미터·orElse(null)을 제거했다. ID 하나로 찾는 메서드와 조건 없는 목록에는 빈 Query/단순 복제 Result를 만들지 않았다. 개발용 PG 제어 API의 infra 직접 참조는 이번 변경에서 제외했다. 트랜잭션·저장소·일괄 결제 조회 방식·JSON 형태·가격 판단 TODO는 유지했다.

검증: 변경 전후 주문 HTTP 응답 검사2/2 통과, Day6 상태/알림5/5 통과, make check-study(환경9+기존필수15) 성공, Palantir 포맷·diff 공백 검사 통과. B007 가격 확인은 기존과 동일한4개 실패이며 아직 사용자가 풀 과제다. 쿼리 수를 계측하거나 MySQL·브라우저를 새로 검증하지 않았다. 이전 커밋 efb947e 이후 로컬 변경으로 남겨 두었으며 이번 수정의 커밋·푸시는 수행하지 않았다.

## JPA Entity 공유 예외 확정 및 적용

사용자는 JPA Entity가 infra 격리의 유일한 예외이며 Service·Reader뿐 아니라 Saver 등 유사한 업무 객체 전체로 전달할 수 있다고 명확히 정정했다. 중복 모델·변환 비용을 줄이려는 기준이다. 이 지시를 기존 AGENTS.md·챌린지 README·학습 가이드에 반영했다.

AI가 제공 환경을 정리했다. Product/PurchaseOrder/Payment 복제 모델을 제거하고 기존 infra/db의 ProductEntity·ProductOptionEntity·OrderEntity·PaymentEntity를 저장소 인터페이스와 업무 객체가 공유한다. Day6 사용자 confirmApproval 구현은 PaymentEntity에 그대로 옮겼다. 관리 중인 결제 객체의 변경은 서비스 트랜잭션에서 반영하므로 saveChanges→재조회→reflect 단계는 제거했다. 상품·옵션을 묶는 ProductResult와 주문·결제 요약 OrderDetailsResult는 의미 있는 조합 결과로 유지한다. HTTP Response 분리, JpaRepository·EntityManager·쿼리의 infra 격리, DB 테이블·컬럼·승인 정책·B007 TODO를 유지했다.

검증: 전체 활성 커머스25개 중21개 통과·기존 B007 미구현4개 실패 유지. Entity HTTP 조회 검증2/2 통과: 상품3→13개, 주문1→3개에서도 각각 SQL2회이며 OSIV=false에서 응답 변환 이후 추가 조회 없음. 변경 전 구조는 일괄2조회였으나 변경 전 실행 SQL 계측을 별도로 수행한 것은 아니다. make check-study의 환경9개·기존필수15개와 포맷·문서 링크 검사 통과. MySQL·동시성·새 브라우저 검증은 수행하지 않았다. 이번 정리는 AI가 제공 환경에 적용한 것으로 사용자 B007 구현 성과가 아니다. 커밋·푸시는 수행하지 않았다.
