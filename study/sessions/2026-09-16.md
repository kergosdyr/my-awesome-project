## C007 — 이진 탐색 구현 해설 요청

사용자는 O(n) 기본 풀이를 간단하게 만들었다고 말했으며, 이진 탐색의 접근·구현 방법을 모르겠다고 질문했다. 튜터가 가운데 값이 조건을 만족하면 답 후보를 기억하고 왼쪽을 확인하는 설명을 제공했으나, 사용자가 “아 모르겠다 구현좀 알려줘”라고 명시적으로 해답을 요청했다.

현재 SizeSearch.java에는 가운데 인덱스와 비교 조건만 작성된 이진 탐색 시도가 있다. O(n) 완성본은 현재 파일에서 확인하지 못했으므로 해당 정확성·테스트 통과는 사용자 자기보고와 구분한다. 사용자 파일은 수정하지 않고, 대화에서 left/right의 양끝 포함 범위와 answer 후보를 사용하는 Java 정답 및 범위 축소 이유를 제공한다. 빈 배열은 반복문을 건너뛰어 -1, 조건을 만족하면 후보 저장 후 더 앞을 탐색하며 만족하지 않으면 가운데까지 제외한다.

이번은 AI 해답 제공 단계이며 독립 이진 탐색 구현·이해 완료·코딩 마감으로 평가하지 않는다. 사용자 시도는 그대로 보존했다. 실제 시간·정답 적용 후 테스트·자료 없는 재설명은 아직 미확인이다. 추가 숙제나 퀴즈를 발행하지 않는다.

## Spring Cache의 TTL 분산과 조기 갱신 질문

사용자는 한 키의 만료 전 갱신과 여러 키의 만료 시점 분산을 구분해 확인하고 Spring Cache에서 두 기능을 지원하는지 질문했다. 튜터는 확률적 조기 갱신은 보통 요청마다 미리 갱신할지를 결정하며, 만료 전 갱신 전체가 반드시 랜덤인 것은 아니라고 설명했다.

튜터 설명: Spring Cache 추상화 자체의 옵션이 아니라 구현체 기능을 사용한다. Spring Data Redis 3.2 이상에서는 TtlFunction으로 저장 시 TTL을 270~330초처럼 분산할 수 있지만, 이 설정이 DB 사전 조회를 수행하지는 않는다. Redis의 확률적 조기 갱신은 별도 구현이 필요하다. Caffeine LoadingCache의 refreshAfterWrite는 고정 시간이 지난 뒤 요청이 오면 비동기 갱신을 시작하며 확률적 갱신과 구분한다.

근거: [Spring Cache 정책](https://docs.spring.io/spring-framework/reference/integration/cache/specific-config.html), [Redis Cache](https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html), [Caffeine Refresh](https://github.com/ben-manes/caffeine/wiki/Refresh). 설명 요청과 당일 교정으로 기록하며 독립 회상 성공이나 간격 승급으로 처리하지 않는다. 기존 캐시 하위 일정 유지.
