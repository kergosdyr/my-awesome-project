# 2026-08-25 학습 세션

## 오늘 다룬 것

- 주제: Shopify가 재고 관리 시스템을 Redis 중심 구조에서 MySQL 중심 구조로 옮긴 사례
- 공부한 이유: 커머스 재고 예약의 동시성, 만료, Redis–MySQL 간 일관성과 MySQL 경합 해결 방식을 이해하기 위해
- 사용한 자료: YouTube 영상과 영상의 기반으로 보이는 Shopify Engineering 원문. 영상 링크는 아직 없음.

## 자료를 보지 않고 쓴 첫 회상

> 아래는 사용자가 자료를 다시 확인하기 전에 적은 첫 회상이다. 맞춤법만으로 내용을 추정하거나 사실을 보완하지 않았다.

- 기존 Redis와 MySQL 두 시스템을 함께 관리하는 구조도 아주 나쁘지는 않았다.
- Redis에서 재고가 `10 → 9`가 되는 것은 실제 재고 차감이라기보다 주문 예약에 가깝고, 실제 재고는 MySQL에 있으며 구매 완료 시점에 차감한다고 이해했다.
- Redis만 사용해 동시성 문제를 풀 때 Lua 스크립트로 조회 후 업데이트 사이의 경쟁을 막고 일관성을 제공했다고 기억한다. 이 패턴의 이름은 기억나지 않는다.
- 구매하지 않고 나가거나 노트북을 닫으면 Redis에서 잡아 둔 예약을 되돌려야 하므로 세션 관리가 중요하다.
- 예약 만료 시각을 기준으로 Redis Sorted Set에 세션을 넣고 현재 점유 인원을 추적한다고 기억한다.
- 예약 수와 실제 재고 수를 어떻게 함께 관리하는지, 이 부분을 Lua 스크립트로 원자적으로 처리하는지는 확실하지 않다.
- 만료 세션을 10초마다 cron job 같은 작업으로 지우는 동안 재고가 계속 0으로 보일 수 있는 문제가 있었다고 기억하지만 정확한 조건은 기억나지 않는다.
- 실제 구매 시 Lua 스크립트로 현재 재고 등을 한 번 더 확인했다고 기억한다.
- Redis와 MySQL은 서로 다른 시스템이어서 둘 사이의 일관성을 유지하기 어려운 점이 MySQL 중심으로 돌아간 이유라고 이해했다.
- MySQL에서 재고를 한 행의 조건부 쓰기로 차감하면 같은 행에 경합이 집중될 수 있다.
- 이를 피하려고 재고 수만큼 여러 행을 만들고, `SKIP LOCKED`와 `LIMIT 1`을 사용해 잠긴 행을 건너뛰며 하나를 잡는 방식이라고 기억한다.
- 재고가 매우 많을 때 행 수가 커지는 문제 때문에 최대 1,000개 정도만 만들고 리프레시한다고 들었지만, 무엇을 어떤 기준으로 채우는지는 기억나지 않는다.

## 지금 드러난 불확실성

- Redis의 숫자가 `판매 가능 재고`, `예약 가능 토큰`, `활성 예약 수` 중 정확히 무엇을 의미하는가?
- 예약 생성, 만료 회수, 구매 확정 각각에서 Redis와 MySQL 중 어느 쪽이 기준 데이터인가?
- 10초 청소 주기가 만드는 정확한 실패 또는 품절 오판 시나리오는 무엇인가?
- MySQL의 여러 행이 실제 상품 단위 재고인지, 제한된 수의 동시 접근 슬롯인지?
- 1,000개 상한과 리프레시가 어떤 알고리즘으로 동작하는지?

## 튜터 점검

### 사실 검증 상태

- Shopify Engineering 원문으로 Redis의 `DECR/INCR`, reserve/claim 경계, MySQL bounded pool과 인라인 replenishment를 확인했다.
- 영상에서 언급됐다고 회상한 Sorted Set, Lua, 10초 cron 세부는 Shopify 원문에는 나오지 않아 아직 미확인이다.

### 꼬리 질문과 내 답

1. 질문: 실제 재고가 10개일 때 A·B·C가 각각 하나를 예약했고, A는 구매 완료, B는 이탈, C는 아직 예약 시간 안이라면 그 순간 Redis와 MySQL에는 각각 어떤 숫자와 상태가 있어야 하는가? 두 저장소 사이에서 절대로 깨지면 안 되는 불변식은 무엇인가?
   - 내 답: "Redis는 8이고 MySQL은 9 아닐까? 절대로 깨지면 안 되는 불변식은 잘 모르겠다."
   - 피드백: `Redis=8, MySQL=9`는 B의 예약이 이미 감지되어 반환됐다는 가정에서는 일관된다. 이때 A의 구매로 MySQL 재고가 9가 되고, C의 활성 예약 하나를 제외한 판매 가능 수량이 Redis의 8이다. B가 이탈했지만 아직 만료 청소 전이라면 Redis 숫자는 달라질 수 있다.

2. 질문: 진행 중
   - 내 답: "거짓 품절이겠지?"
   - 피드백: 맞다. B의 이탈이 아직 청소되지 않았다면 Redis는 B와 C의 예약을 모두 유효한 것으로 보아 판매 가능 수량을 7로 유지하지만, MySQL은 A의 구매만 반영해 9다. 이 지연은 재고를 실제보다 보수적으로 작게 보여 초과 판매보다 거짓 품절을 만든다.

3. 질문: 진행 중
   - 내 답: "결제 단계에 진입 못하면 의미가 없으려나? 언제 하는지는 기억이 애매하다."
   - 피드백: 맞다. 구매 시점의 재검사만으로는 Redis에서 이미 품절 응답을 받은 새 고객 D가 결제 단계에 도달하지 못하는 문제를 해결할 수 없다. 만료 예약 회수는 새 예약을 거절하기 전 경로에서도 일어나야 한다. 이것이 영상의 정확한 구현인지는 링크로 원문을 확인해야 한다.

4. 질문: 진행 중
   - 내 답: "고객에게 재고를 바로 보여주면 안 될 것 같다. 현재 Redis 재고를 먼저 확인하고, 없다면 Sorted Set에서 시간순으로 만료된 예약이 있는지 확인한 다음 예약해야 하지 않을까?"
   - 피드백: 설계 흐름은 타당하다. 화면의 수량은 참고값으로 보여줄 수 있지만 실제 예약 가능 여부는 예약 요청의 성공으로 확정해야 한다. `재고 확인 → 필요할 때 만료 예약 회수 → 재확인 → 새 예약 생성` 전체가 하나의 원자적 Lua 실행이어야 한다. 여러 명령으로 나누면 확인 결과와 갱신 사이에 다른 요청이 끼어드는 check-then-act 또는 read-modify-write 경쟁이 생긴다. 영상의 실제 최적화가 재고 0일 때만 회수하는 방식인지는 아직 미확인이다.

5. 질문: 진행 중
   - 내 답: "더블 부킹이 발생하겠지."
   - 피드백: 맞다. D와 E가 같은 만료 예약을 각각 회수 가능한 한 개로 판단하면 하나의 물리 재고에 두 활성 예약이 생길 수 있다. 깨지는 핵심 불변식은 `한 재고 단위에는 동시에 최대 하나의 활성 예약만 존재한다`이다. 집계 관점에서는 `완료된 판매 수 + 활성 예약 수 <= 확보 가능한 전체 재고`로 표현할 수 있다.

6. 질문: 진행 중
   - 내 답: "그러면 당연히 에러 나겠지?"
   - 피드백: 에러가 아니다. `SKIP LOCKED`는 D가 잠근 행을 기다리지 않고 건너뛴 뒤, 조건에 맞는 다음 잠기지 않은 행 하나를 `LIMIT 1`로 선택한다. 다른 후보가 하나도 없으면 일반적으로 행을 찾지 못한 빈 결과가 된다.

7. 질문: 진행 중
   - 내 답: "기본적으로 조건부 쓰기만 해도 충분히 경합이 발생하지 않고, 잠겼으면 다음 행으로 넘어가기 때문 아닌가?"
   - 피드백: 조건부 쓰기와 경합 분산의 역할을 구분해야 한다. 단일 행에서 `UPDATE ... SET quantity = quantity - 1 WHERE quantity > 0`을 사용하면 음수 재고는 막을 수 있지만 모든 요청이 같은 행의 잠금을 획득해야 하므로 경합은 남는다. 다음 행으로 넘어갈 수 있는 것은 재고를 여러 후보 행으로 나누고 `SKIP LOCKED`를 사용했기 때문이다. 조건부 쓰기는 정확성을, 다중 행과 `SKIP LOCKED`는 대기와 hot-row 경합 완화를 담당한다.

8. 질문: 진행 중
   - 내 답: "SKIP LOCKED는 SELECT FOR UPDATE를 해야 걸리는가? 조건부 쓰기로는 해결이 안 되는 것인가? 단일 행에 100개 트랜잭션이 오면 조건부 쓰기라도 행이 없다고 뜨고 한 개만 성공하는 것 아닌가?"
   - 피드백: `SELECT ... FOR UPDATE`와 `UPDATE` 모두 대상 행에 쓰기 잠금을 잡는다. `SKIP LOCKED`는 독립적으로 잠금을 만드는 기능이 아니라 `FOR UPDATE` 같은 잠금 읽기가 이미 잠긴 행을 기다리지 않고 결과에서 제외하도록 하는 옵션이다. 단일 카운터가 `quantity=100`이라면 동시 요청은 같은 행 잠금 앞에서 사실상 직렬화되지만, 각 트랜잭션이 최신 수량에 `quantity > 0` 조건을 적용해 하나씩 차감하므로 최대 100개까지 성공할 수 있다. 수량이 1일 때만 한 개가 성공한다.

9. 질문: 진행 중
   - 내 답: "최종 수량은 0이고, 제일 마지막 요청만 실패한다."
   - 피드백: 맞다. D와 E는 각각 행 하나를 갱신해 성공하고 F는 `quantity > 0` 조건을 만족하지 못해 영향받은 행이 0개가 된다. 최종 수량은 0이며 음수로 내려가지 않는다. 다만 세 요청 모두 같은 행 잠금 순서를 통과하므로 정확성과 별개로 hot-row 대기는 남는다.

10. 질문: 진행 중
   - 내 답: "어차피 각각 두 개의 행이 잠기는 것 아닌가?"
   - 피드백: 맞다. 다만 한 요청이 두 행을 잠그는 것이 아니라 D와 E가 서로 다른 재고 행 하나씩을 동시에 잠근다. D가 첫 행을 잡으면 E는 그 행을 건너뛰고 둘째 행을 잡으며, F는 잠기지 않은 후보가 없어 빈 결과를 받는다. 단일 카운터에서는 D가 끝날 때까지 E와 F가 같은 행 앞에서 기다리지만, 다중 행에서는 D와 E의 작업이 서로 직렬화될 필요가 없다.

11. 질문: 진행 중
   - 내 답: "트랜잭션을 잡고 먼저 보충한 다음 499개만 채우고 바로 처리하면 되지 않을까? ledger가 원장인가? 원장은 한 개만 줄여야 하는 것 같다."
   - 피드백: ledger는 실제 재고의 source of truth인 원장이다. 다만 bounded pool 보충은 판매 확정이 아니라 예약에 사용할 단위 행을 materialize하는 작업이므로 ledger를 보충 개수만큼 영구 차감하면 안 된다. 한 보충자가 item/location 단위의 보충 잠금을 잡고 최대 풀 크기와 아직 예약되지 않은 원장 재고를 기준으로 행을 채운 뒤 커밋한다. 그 요청은 같은 트랜잭션에서 자기 예약 단위도 확보할 수 있고, 나머지 499개 요청은 보충 커밋을 기다렸다가 각자 `SKIP LOCKED`를 다시 실행한다. 실제 ledger 감소는 성공적으로 claim되는 구매 수만큼만 일어나야 한다.

12. 질문: 진행 중
   - 내 답: "800개 아닌가? 원장은 아직 결제되지 않았으니 줄이지 않는다."
   - 피드백: ledger를 줄이지 않는다는 답은 맞다. 그러나 Shopify의 1,000 상한은 활성 예약과 pool의 합이 아니라 item/location별 available pool 자체의 상한이다. 주어진 조건에서는 `200 active + 1,000 pool = 1,200 <= 50,000 ledger`이므로 pool을 1,000행까지 보충할 수 있다. 800은 `active + pool <= 1,000`이라는 별도 상한을 가정했을 때의 답이다.

13. 질문: 진행 중
   - 내 답: "격리 수준이 아직 헷갈린다. Oracle이나 다른 DB와 비교해서 더 구체적으로 알고 싶다. 검색 범위가 비어 있어야 한다는 생각과 빈 결과인데 무엇을 잠근다는 것인지 이해하기 어렵다. 다른 트랜잭션이 커밋한 행이 다음 조회에서 나타나는 것은 정상 아닌가?"
   - 피드백: 맞는 반박이다. Phantom은 항상 버그라는 뜻이 아니라 격리 수준이 허용하거나 금지하는 현상의 이름이다. `READ COMMITTED`에서는 다음 문장이 새 snapshot을 보므로 정상이다. MySQL `REPEATABLE READ`의 범위 locking read는 이를 막기 위해 gap lock을 사용할 수 있지만, Shopify의 빈 pool에서는 replenishment가 넣은 새 행을 다음 예약 시도가 봐야 하므로 오히려 이 보호가 방해가 됐다. 그래서 해당 트랜잭션을 `READ COMMITTED`로 낮추되, 동시 보충의 정확성은 별도의 명시적 잠금으로 지킨다.

14. 질문: 진행 중
   - 내 답: "READ COMMITTED에서는 phantom read가 자연스럽고 REPEATABLE READ에서는 그렇지 않다는 이야기인가? 보충 잠금을 기다린 요청은 pool을 다시 확인해야 한다. 그런데 빈 pool에 INSERT하기 위한 잠금을 SELECT FOR UPDATE로 잡을 수 있는가? 행이 없는데 잠금이 가능한가?"
   - 피드백: MySQL InnoDB 맥락에서는 첫 이해가 대체로 맞다. 다만 SQL 표준의 Repeatable Read는 phantom까지 반드시 금지하지 않으며 DB 구현별 보장이 다르다. MySQL RR은 locking range에 next-key/gap lock을 사용하고 PostgreSQL RR은 snapshot isolation으로 phantom을 보이지 않는 더 강한 구현이다. READ COMMITTED에서 빈 pool을 SELECT FOR UPDATE해도 조정에 쓸 실제 행이 없으므로 안정적인 row mutex가 되지 않는다. item/location별 ledger 또는 별도 replenishment_guard처럼 항상 존재하는 행을 먼저 FOR UPDATE로 잠근 뒤 pool을 재확인해야 한다.

15. 질문: 진행 중
   - 내 답: "처음 조회 결과를 믿기에는 중간에 다른 요청이 행을 넣을 수 있으므로, 다시 확인하지 않으면 두 번 보충될 수 있다."
   - 피드백: 맞다. E의 첫 조회와 guard 잠금 획득 사이에 D가 보충하고 커밋할 수 있다. E가 잠금 획득 후 재확인하지 않으면 동일 item/location에 또 1,000행을 넣는 중복 보충이 발생한다. `확인 → 잠금 대기 → 재확인 → 필요할 때만 실행`으로 TOCTOU 경쟁을 닫아야 한다.

16. 질문: 진행 중
   - 내 답: "MySQL에서는 PK가 일종의 테이블이고 secondary index는 이것을 가리킨다는 것까지는 이해했다. 하지만 왜 secondary index만 잠그면 부족하고 composite PK가 잠금 수를 줄이는지는 아직 모르겠다."
   - 피드백: Secondary entry만 잠그면 같은 논리적 행을 PK로 직접 찾아온 다른 트랜잭션과 공통 잠금 지점이 없다. 예를 들어 T1이 `(shop,item,location) → id=101` secondary entry만 잠그고, T2가 `UPDATE ... WHERE id=101`로 clustered row를 직접 변경하면 서로 다른 물리 record를 잠그게 된다. `FOR UPDATE`는 실제 행의 변경을 직렬화해야 하므로 secondary entry뿐 아니라 최종 clustered record도 잠가야 한다. 조회 키를 composite PK로 만들면 검색 entry가 곧 전체 행이 있는 clustered record이므로 별도 secondary record를 거치지 않아 하나의 공통 record lock으로 끝난다.

17. 질문: 진행 중
   - 내 답: "Secondary index는 결국 PK를 가리키는 것이라고 이해했다. Secondary entry가 정확히 무엇인지 궁금하다. T1이 secondary entry만 잠근다는 가정은 T1과 T2 사이에 경합이나 실패가 없어 둘이 동시에 진행할 수 있다는 뜻인가?"
   - 피드백: 맞다. 가정상 T1은 secondary B-tree의 물리 record S를, T2는 PK B-tree의 clustered record C를 잠그므로 잠금 대상이 달라 서로 기다리지 않고 진행할 수 있다. 다만 이것은 위험성을 설명하는 반사실적 가정이다. 실제 InnoDB의 secondary-index locking read는 clustered record도 함께 잠가 공통 잠금 지점 C를 만들기 때문에, T2의 PK UPDATE는 C에서 대기한다. Entry는 B-tree leaf page 안에 정렬되어 저장된 index record 한 건이며 secondary entry는 보통 `(secondary key columns, primary key columns)` 형태다.

## 세션을 마치며

### 오늘 설명할 수 있게 된 것

- Redis의 숫자는 실제 판매 완료 수량보다 결제 중인 재고 예약을 표현하며, 실제 원장은 MySQL inventory ledger다.
- 만료 예약 회수가 늦으면 초과 판매보다 실제 재고를 숨기는 거짓 품절이 생긴다.
- `확인 → 갱신`을 여러 Redis 명령으로 나누면 check-then-act/read-modify-write 경쟁이 생기며 Lua로 원자화할 수 있다.
- 단일 MySQL 카운터의 조건부 `UPDATE`는 음수 재고를 막지만 hot-row 경합은 남긴다.
- 여러 unit row와 `FOR UPDATE SKIP LOCKED`를 사용하면 요청들이 서로 다른 행을 잠가 병렬로 예약할 수 있다.
- 1,000행 bounded pool은 실제 전체 재고가 아니라 item/location별 예약 가능 unit의 작업 풀이고, 비면 한 요청만 보충한 뒤 다른 요청들이 다시 확인한다.

### 오늘은 보류한 심화 주제

- MySQL `REPEATABLE READ`의 next-key/gap/supremum lock 세부
- PostgreSQL·Oracle과 MySQL의 격리 수준 구현 차이
- InnoDB secondary entry와 clustered record의 정확한 잠금 동작
- Composite primary key가 secondary-index 크기와 쓰기 비용에 미치는 영향

위 항목도 오늘 실제로 다뤘으므로 복습에 포함한다. 다만 오늘 설명한 수준까지만 확인하고 더 깊은 파생 질문은 만들지 않는다.

### 다음 복습 질문 묶음

#### A. 핵심 흐름

1. Shopify가 Redis의 성능 문제가 아니라 Redis 예약과 MySQL 원장의 경계 때문에 MySQL 중심 구조로 옮긴 이유를 `reserve`와 `claim`으로 설명해보자.
2. 만료된 예약이 늦게 회수되면 왜 초과 판매보다 거짓 품절이 생기는가?
3. 단일 카운터의 조건부 `UPDATE`와 여러 unit row의 `SKIP LOCKED`는 각각 정확성과 경합을 어떻게 다르게 해결하는가?
4. bounded pool을 최대 1,000행으로 제한하는 이유와, 빈 pool을 여러 요청이 동시에 보충하지 못하게 해야 하는 이유는 무엇인가?

#### B. 오늘 다룬 내부 동작

## 원문 대조로 수정된 부분

- 예약은 일반적인 브라우저 세션 진입 시점이 아니라 구매자가 결제를 시작할 때 생성되는 짧은 hold다.
- 기존 Redis 모델은 예약 시 `DECR`, 해제 시 `INCR`이었다. 핵심 문제는 Redis의 예약과 MySQL inventory ledger의 claim을 하나의 원자적 트랜잭션으로 묶지 못한 것이었다.
- MySQL 풀의 행은 재고 수량 버킷이 아니라 하나의 sellable unit을 나타낸다.
- 풀은 item/location 조합마다 최대 1,000행으로 제한하며, 예약이 행을 소비하면 inventory ledger에서 replenishment process가 다시 채운다.
- 풀이 비었지만 ledger에 재고가 남아 있으면 예약 경로가 인라인 보충을 시작한다. 하나의 트랜잭션만 보충 잠금을 잡고 나머지는 기다려 thundering herd를 막는다.
