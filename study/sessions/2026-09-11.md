AI가 Day 3에 이를 재사용하지 않고 빈 TODO를 제공한 것이 문제였다.
Day 3에 기존 두 서비스와 반환 타입을 이어받고 엔티티 동작/Repository 메서드를 합쳤다.
서비스 구현 본문은 양일 원본과 동일함을 비교 확인했다. Day 1/Day 2 원본은 수정하지 않았다.

앞으로 같은 백엔드 주제는 현재 구현을 이어서 확장한다. 새 학습 완료/독립 성과 평가는 하지 않았다.

### 사용자 질문 — MySQL 비관적 락과 k6 부하 검증

사용자가 “비관적 락이 같은 event에 걸려 있어서 될 것 같다”고 추론했다.
이는 현재 두 업무 경로의 보호 대상에 대한 사용자 설명이며, 전체 독립 구현 Pass와 구별한다.
사용자가 추가로 대용량 동시성 검증에 k6를 제안하고 FD 한계를 궁금해했다.
AI는 OrbStack을 시작하고 Testcontainers MySQL8.4.9에서 기존 테스트를 실행했다.
19개 중18개 통과. 실패는 없는 이벤트의 응답 계약1개이며 동시성 검사는 모두 통과했다.
서비스 수정 없이 src/test에 로컬 HTTP 어댑터와 k6 실행기를 추가했다. 준비 시간은 풀이 시간에서 제외한다.
첫 부하225,698요청 중 HTTP오류3.417%, 업무 예외0, 표본 불변식 위반0. 연결 끊김으로 취소1건이 완료되지 않아
최종 예약1·잔여0으로 부하 종료 기준은 실패했다. 첫 결과를 보존하고 HTTP 어댑터의 기본 유휴연결 상한200을2048로 조정해 재검증한다.
사용자 코드의 락 결함/FD 고갈로 단정하지 않았다. 테스트 설정과 런타임 제어는 AI가 담당한다.

재검증 완료: 동일한 60초·최대1,000VU 부하에서 k6 exit0, 총170,779요청(약2,841 req/s),
HTTP오류0%, 응답/종료 검사170,779회 모두 통과. HTTP전체 p95=458.13ms, 최대855.42ms.
예약 성공1,236건, 정상 매진168,304건. 취소 성공1,237건은 초기 예약 취소1건을 포함한다.
최종 예약0·잔여1, 업무 예외0, 2초 표본 불변식 위반0.
FD 표본 최대: 서버1,146/k6 1,009, DB연결 최대32. FD 고갈은 관찰되지 않았으며 OS 제한은 변경하지 않았다.
첫 실행의 연결 단절 실패와 테스트 HTTP 설정 수정 후 성공을 구별한다. 새 동시성 해법을 구현한 결과가 아니다.
실행 중 MySQL lock-wait 표에 대기 관계가 관찰됐다(첫 실행 한 시점465행, DB연결33은 진단 연결1개 포함).
이는 행 잠금 경합의 근거지만 모든 지연의 원인이 DB임을 단독 증명하지는 않는다.
원본 결과: [최종 수치](../challenge-120/exercises/day-003/build/load/result.json), [k6 원본](../challenge-120/exercises/day-003/build/load/k6-summary.json), [첫 실행](../challenge-120/exercises/day-003/build/load-attempt-001/result.json).
